## Owner decisions and preferences (do not relitigate)

- Everything is a plugin; the kernel is scaffolding only (ADR 12 and its contract). Tuna's own plugins get no privileged access.
- No arbitrary limits such as line-count caps. Make every kernel addition deliberate and justified instead.
- Buffer positions are 1-based. Ordinary browser tabs are first-class; reserved keys are simply rebound. Layout belongs to the browser; mixed monospace and proportional text must be possible (no cell grid).
- Buttons and clickable UI resolve through node keymaps via the input plugin; the client never names a command. Hooks stay in the kernel.
- Window management is a replaceable plugin; the default is the owner's recursive layout tree (ADR 11, `docs/ideas/window-management.md`).
- Divergence from Emacs is welcome when better, but must be recorded in an ADR and `docs/emacs-equivalents.md`.
- Owner-facing documents follow AGENTS.md "Documents for the owner": briefs before architecture work, plain language, rendered and checked D2 diagrams, a walkthrough, a code sample, decisions with recommendations, new terms.
- Delegate substantial implementation to agents in their own worktrees (`tuna__<task>`), merge locally with `--no-ff`, never push. The owner talks only to the primary agent.
- Commit work as it lands; the owner wants things committed.
- Tuna has no "standard" setup (2026-10-12). The plugins in this repository are ordinary plugins; users need not use any of them and may use completely different keybindings and input models. Recovery from a broken configuration comes from the user's own configuration (skip only what fails, or return to the last known-good one), never from a built-in default plugin set; the exact design is being researched for the configuration brief.
- No magic (2026-10-12): Tuna never creates, copies or edits the user's configuration on its own; explicit commands only.
- Rendering is immediate mode, UI = function(state) (2026-10-13): every redisplay streams the whole visible UI as one Datastar fat morph (ADR 7); no protocol that patches individual node ids, because it risks the browser drifting out of sync with the server. Two optimizations are wanted, both behind that model: render only what is in view, and do not recompute HTML for parts whose state has not changed (server-side memoization, e.g. keyed by node revision), while still streaming everything visible. Scrolling (inside buffers and in layout scroll containers) should probably be native browser scrolling with content rendered only when in view, as in Anders Murphy's hyperlith virtual scroll (/home/jay/Code/hyperlith, `hyperlith.extras.ui.virtual-scroll`, used by examples/billion_cells); ideally one mechanism serves buffers and layout. Open; needs its own design. The owner is separately replacing Gerbil's SXML writer with a typed XML module for speed.

- Focus is state (2026-10-13): every layout container remembers its last-focused child (as in i3 and niri), stored in the layout tree.
- A buffer is generically a UI element (2026-10-13): a named tree of UI nodes, e.g. a VS Code-style sidebar of buttons is a buffer pinned to the side. "Saving" is not a buffer concept; writing to a file belongs to a text node that visits a file. Restoring the UI after a restart persists each plugin's state and lets the owning plugin redraw, never the node tree itself. The owner is open to a better name than "buffer"; settle it in the "buffers, views and layout" brief.

- Tuna has no users yet (2026-10-13): do not ask about or preserve saved sessions, state files, or other compatibility with earlier builds until the owner says he is using Tuna day to day. Drop or reset them freely.

- Mouse interaction (2026-10-13): next after the buffers, views and layout milestone (hooks and advice deferred). Dragging sends one input item on drop, not a stream; the drag must still look good in the browser, done with Datastar attributes and CSS. Text-node mouse interaction (selection, clicking into text) is deferred; it may become a Rocket component. Research and a spike report in `agents/research/mouse-input/` (spike branch `mouse-spike`, worktree `tuna__mouse-spike`, not for merge; delete after approval). Brief `docs/briefs/2026-10-mouse-input.md` approved 2026-10-13, trimmed to clicks and node keymaps; plan `agents/plans/mouse-input.md`. All dragging moves to the layout outline work. Owner, 2026-10-13: every part is draggable and rearrangeable, not just tabs (a tab is one kind of container; keep the model topologically correct); the brief now says so. Idea recorded: a layout outline sidebar (`docs/ideas/layout-outline.md`).
- The server processes everything (2026-10-13): every state-changing action, including mouse input and typing, goes to the server and takes effect when its screen arrives. No browser-owned editor state, no client-side prediction or optimistic UI, no CRDT/OT, no text-owning client component. The browser owns only pure presentation (hover, drag previews, scroll, animations).
- Polish matters (2026-10-13): Tuna must not look like a terminal; hover states and a polished, designed UI are wanted (the owner sees Emacs's plain UI as hurting adoption). A design pass comes later; keep markup and classes friendly to it.

- Priorities (2026-10-13): UI before files. Files wait until the text buffer is fully designed (scroll state and the rest of what a text view needs); the owner wants the UI settled first.

## Lessons recorded from this attempt

- Task briefs named what to build but not where; reviews checked tests, not placement; agents' reports of kernel additions were accepted. AGENTS.md "Keep the kernel small" now requires naming the owning layer in every task and checking placement at every merge.
