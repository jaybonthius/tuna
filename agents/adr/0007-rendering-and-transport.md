# 7. Server-rendered HTML screens over Datastar; layout belongs to the browser

Status: accepted (2026-10-11); amended after the [capability audit](../research/capability-audit/README.md) (ordinary tabs first-class, layout ownership, input proxy, event identity, "screen" terminology); amended 2026-10-13 by [ADR 13](0013-views-layout-and-frames.md): a redraw walks the layout from the frame's target, still sending the whole visible screen, and reuses the HTML of unchanged parts; amended 2026-10-14 by the approved [input brief](../../docs/briefs/2026-10-input-without-waiting.md): concurrent numbered input, one tab, no client identity. Amended 2026-10-16 by the approved [stylesheets brief](../../docs/briefs/2026-10-stylesheets.md): Tuna is a hypermedia application and HTML is its only presentation language. Amended 2026-10-17 by [ADR 15](0015-scroll-state.md): layout facts for scrolling are settled (the browser reports measured scroll facts as special events; the server places items; screens wait for `/applied`; nothing is guessed). Amended 2026-10-22 by [ADR 16](0016-several-tabs-mirror-one-editor.md): several tabs mirror one editor; each tab has a server-made tab id, its own input numbering and its own screen, drawn from shared state plus what that tab measured. Amended 2026-10-22 by [ADR 17](0017-memo-and-sources.md): a screen is still sent whole, but is drawn from pieces (screen, views, nodes, lines) each reused while nothing it read has changed, kept as UTF-8 bytes and written straight into the screen event.

## Context

The browser is the primary display, used like a terminal: every user action is sent to the server, and the server sends back the new view. Datastar supports this with command `POST`s and a long-lived server-sent-event stream that morphs HTML into the page ([vendored docs](../reference/datastar/docs.md)). Weevil proved the approach in Racket, including server-side viewport slicing.

The audit found that the server cannot know layout (wrapping, proportional fonts, images, variable line heights), that ordinary browser tabs never deliver some keys (`C-w`, `C-n`, `C-t`), and that composition input, dead keys, mobile keyboards, and screen readers require a focused editable element ([lanes 1, 2, 5](../research/capability-audit/README.md)). The owner requires ordinary browser tabs to remain first-class (remote development) and requires buffers to mix monospace and proportional text, even within one buffer.

Datastar's Rocket (beta) defines web components with typed props, local signals, and events: "props down, events up". It is a candidate for local-only behavior such as scrolling and wrapping.

## Decision

- **Terminology.** One complete rendering of what a browser tab shows is a **screen**. **Frame** keeps its Emacs meaning: a top-level window with its own window tree.
- **Input.** A small Datastar plugin captures browser input and sends each item immediately to `/commands`, without waiting for previous responses. Keys and clicks share numbers 1, 2, 3, … from page load, with no browser storage or client id. The web plugin holds early arrivals and submits contiguous numbers to the editor's input queue in order; the kernel is unchanged. It ignores executed or waiting duplicates. Serving the page (`GET /`) resets the expected number to 1 and clears waiting items. *2026-10-16:* the screen stream does not: Datastar reopens it without a reload, and resetting there froze all later input because the page kept counting. After a server restart, when no page has loaded yet, the first item's number becomes the start. More than 64 waiting items are dropped with one log line. One tab is assumed.
- **Acknowledgement and retry.** Every `/commands` request passing the Host/Origin checks gets `204` immediately, before parsing or submission, including malformed, duplicate and dropped items (which are logged, never reported in the echo area). Responses carry no UI. The browser resends the same body and number after 250 ms only when fetch fails without an HTTP response; any response ends retrying. Pointer items still name the revision of the screen they were computed on.
- **Input proxy.** The page may keep one hidden, focused editable element to receive composition, `beforeinput`, and paste events and to give assistive technology a focus target. It forwards what it receives and clears itself. Buffer text is never edited by the browser.
- **Keys.** Ordinary browser tabs are a first-class client. Key capture is best-effort: keys the browser reserves are unavailable in that client, and users bind other keys. Tuna does not require a special launch mode; app windows or native shells are optional conveniences.
- **Output.** The page holds one `GET` SSE stream. After the editor loop decides to redisplay, it renders the screen and the stream's writer thread sends the newest one as a Datastar element patch (a "fat morph"). A slow stream skips intermediate screens; it never blocks the editor.
- **Hypermedia; HTML is the presentation language** (owner decision, 2026-10-16). Tuna is a hypermedia application: plugins render their nodes to HTML and the browser draws them. Buffers stay trees of nodes with text and positions; HTML is how they are shown, never how they are stored. A terminal frontend, if one is ever wanted, would render that HTML as text; it is not a second render target. Node renderers therefore take no target: `(context-define-node-renderer! ctx kind render)`, where RENDER returns SXML.
- **Rendering pipeline.** Editor state → renderer service → SXML → HTML. The `Renderer` is a `std/interface` service, so another HTML renderer can replace the default (a bare test double proves the slot). Node kinds supply their own render procedures. ~~so a terminal renderer can be added later~~ *Superseded 2026-10-16:* there is no second presentation language.
- **Layout belongs to the browser.** The server decides content and styling, never pixel or cell layout, and the core must not assume a fixed-width grid. Monospace and proportional text may mix within one buffer. Commands that depend on layout (visual-line motion, page scrolling, `current-column` in proportional text, popup placement) obtain layout facts from the client. *2026-10-17:* for scrolling this is settled by [ADR 15](0015-scroll-state.md): the browser reports what it measured (the item at a scroller's top and its offset, the last item wholly in view, the drawn pixels), and the server places items; other layout-dependent commands (visual-line motion, popup placement) remain open. The mechanism was an open research item; candidates are layout facts attached to events as signals, a task suspending to request a measurement, and Rocket components that perform local-only behavior (scrolling, wrapping, perhaps some navigation) from server-supplied props and report results as events.
- **Presentation-only browser state.** Authoritative editor state lives on the server. The browser may own purely presentational state (hover, cursor blink, scroll within already-rendered content, layout) and report what the server needs.
- **Identity.** Rendered elements carry stable node identifiers so pointer events map back to nodes and positions. Popups are anchored to node identifiers with CSS, not computed pixel positions.
- **Client-owned widgets.** Later, node kinds such as terminals, canvases, and document viewers may own a client-side widget with its own data channel, excluded from morphing.
- **HTML.** Semantic elements, CSS custom properties for design tokens, and no CSS class soup ([html-css guide](../guides/html-css.md)). Text is always escaped; only renderer code creates elements.
- **Stylesheets** (approved [stylesheets brief](../../docs/briefs/2026-10-stylesheets.md), built 2026-10-17). Each plugin styles its own HTML with CSS files it registers through the stylesheets contract (`add-stylesheet`), usually its semantic tokens and its rules; the `stylesheets` plugin ships the raw scale. Gerbil holds no colours or styles, only which files are on the page, their owners and order. Themes and `init.ss` replace files by owner and name (`replace-stylesheet`); turning a plugin off removes what it added and restores what it replaced. The web transport renders the page's head from the registry and sends it whole, before the screen, when it changes. This replaces Emacs's faces and themes; the divergence is recorded in [Tuna and Emacs](../../docs/emacs-equivalents.md).
- **Client scope.** One browser tab, displaying the server's frame. Multiple-tab identity and coordination are not designed here ([ADR 10](0010-security-clients-and-trust.md)).

## Consequences

- The browser holds no authoritative state; reconnecting simply receives the current screen.
- Whole-screen morphs are simple but cost bandwidth and render time proportional to visible content. Keydown-to-patched-screen latency is measured from the first prototype; finer-grained patches are an optimization behind the same pipeline.
- Until the layout research is done, screen-relative commands cannot be written correctly; logical-line commands can.

## Alternatives considered

- **Client-side editor component (CodeMirror, Monaco).** Rejected: splits editor state between client and server.
- **Fixed-width cell grid with server-side wrapping.** Rejected by the owner: buffers must mix proportional and monospace text.
- **App window or native shell as the only supported client.** Rejected by the owner: ordinary tabs are needed for remote development.
- **WebSocket protocol with custom diffing.** Rejected for now: Datastar's SSE morphing already works and keeps the client small.
