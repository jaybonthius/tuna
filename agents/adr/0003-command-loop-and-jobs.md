# 3. One editor loop, interruptible direct-style commands, tasks, and jobs

Status: accepted (2026-10-11); amended 2026-10-22 by drawing stage 5 (jobs post several results; `off-thread`, `sleep-for`, sources, and `C-g` on waiting commands); amended after the [capability audit](../research/capability-audit/README.md) (quit lane, tasks, yield points, input-target stack, job validity policies, macros), and again the same day to make quitting cooperative first; amended 2026-10-12 after the [concurrency prior-art research](../research/concurrency-prior-art/README.md) (cooperative job cancellation, mapped spans, edit results, settle-by items); amended 2026-10-14 by the [kernel alignment brief](../../docs/briefs/2026-10-kernel-cordis.md) (commands owned by their plugin).

## Context

Typing must reach the screen without waiting for syntax highlighting, language servers, search, or other follow-up work. Emacs serializes Lisp with a global lock and redisplays only when no input is pending; its commands can block in direct style (`read-string`, `y-or-n-p`) through recursive edits; and `C-g` sets `quit-flag` when the key arrives, not when it is read, so it can interrupt running Lisp. Emacs freezes when a command or process filter computes for a long time without checking for quit.

Gambit threads are preemptive green threads. Today Gerbil runs them on one OS thread; the Gerbil developers are enabling SMP, after which threads may run in parallel. Gerbil's MOP still marks some paths as not SMP-safe, so Tuna must not rely on shared mutable state between threads. On Gerbil `v0.19-dev-63`, `thread-interrupt!` runs a thunk in the target thread: raising from it unwinds that thread, running `dynamic-wind` cleanups, even when it is blocked on a channel; `thread-terminate!` skips cleanups. When the thunk escapes, the caller of `thread-interrupt!` receives an `abandoned-mutex-exception` that must be caught ([lane 1](../research/capability-audit/01-command-loop-and-input.md)). The Gerbil maintainers treat cancellation in the standard library as cooperative and deliberately avoid injecting exceptions into threads (`src/std/AGENTS.md` in the Gerbil checkout), so interrupting code that is inside the standard library, for example holding one of its locks, can leave that state inconsistent.

## Decision

- **Editor baton.** Exactly one thread at a time holds the editor baton and may touch live editor objects ([ADR 4](0004-state-ownership.md)). The editor loop owns the baton and lends it to one command or task at a time.
- **Input.** Browser events are acknowledged with `204` on receipt and enqueued per input session ([ADR 8](0008-input-keymaps-and-command-composition.md)). The loop dequeues input items and has the `Input` service resolve each one to a named task, which it runs; the kernel never looks inside an item ([ADR 12](0012-kernel-boundary-and-replaceability.md)), and for key presses the keys plugin finds the command in its keymaps.
- **Quit lane.** The input service classifies each arriving item before queuing; the keys plugin classifies the quit key as an interrupt, which requests a quit. A quit request is cooperative first: it sets the baton holder's quit flag, which every yield point checks and which long-running loops check with `check-quit` (as Emacs checks `quit-flag`); the task then raises `quit` and unwinds with cleanups. A quit is not a callback failure: inside a task, `run-hook` lets a quit from a callback pass through to unwind the task and keeps the callback. A plugin activation or deactivation, with everything it cascades into and its lifecycle announcements, is atomic with respect to quitting: it runs with quit inhibited (a third interrupt still overrides this), and a quit raised inside it anyway that reaches one of the kernel's failure catchers is held, the interrupted step counts as done (a plugin whose own activation quit is rolled back), and the quit is raised in the task once the operation has finished. Outside a task (the loop thread, startup, shutdown), where nothing can unwind, a held quit is dropped and a quit from any other hook callback counts as that callback failing. If the task does not stop within a short grace period, or the quit key is pressed again, the loop interrupts the thread with `thread-interrupt!` to raise `quit` immediately, and reports that a forced quit may have left plugin or library state inconsistent. A thread-scoped `inhibit-quit` defers quitting to the end of the inhibited region; pressing the quit key three times overrides it, as in Emacs. *2026-10-23 (drawing stage 5, bug fix):* a quit request is not lost when the task it reached ends without a quit check (a short task that never checks, such as a source's apply): its interrupt item is then queued as input, exactly as if it had arrived with no task running, so it resolves in the sending client's session (`keyboard-quit`, or a prompt's binding), as Emacs keeps `quit-flag` set until something checks it; a task that quit, cooperatively or forced, consumed it and nothing is queued. Running code can test `input-pending?` and call `discard-input`. A watchdog may report commands that hold the baton too long. Calls into foreign code cannot be interrupted.
- **Commands and tasks.** A command is a task started by input. A **task** is any code that holds the baton in its own Gambit thread: commands, timer and idle-timer callbacks, process callbacks, completion functions, and hook work that must wait. Tasks are registered through a plugin context and cancelled when it deactivates. *2026-10-14:* a command's task belongs to the plugin that defined the command (the commands contract runs its body with `call-with-task-owner`), so turning that plugin off quits the command, even one waiting at `read-string`, without turning off the minibuffer. Cordis aborts only between steps; this is a kept divergence ([ADR 2](0002-plugins-contexts-and-services.md), D4).
- **Suspension.** A task may suspend only at documented **yield points**: prompts (`read-string`, `completing-read`, `read-key`, `y-or-n-p`), waits on job results, process output, or timers (`sit-for`, `sleep-for`, `accept-process-output`), explicit `(redisplay)`, and blocking I/O such as `call-process`, which releases the baton while waiting by default (`with-baton-held` keeps it). Suspending returns the baton to the loop; resuming takes it back. An `atomic` region makes any yield an error. Code that suspends must re-read state afterwards, as with Emacs recursive edits. *2026-10-22 (drawing stage 5):* `off-thread` and `sleep-for` (`tuna/lib/background.ss`) are built on `suspend`, not on timers: `(off-thread proc input)` runs PROC on plain data in a root thread and resumes the task with its value or error (no extra task per call); `sleep-for` resumes after the delay; leaving either wait sets the worker's cancellation check (`background-cancelled?`) and leaves no waiting thread behind. `C-g` with no task running is resolved by the input provider: the keys plugin's `keyboard-quit` quits the most recent wait in `off-thread` or `sleep-for` of a command started from the same client, otherwise of any client's command, unless that `C-g` only cancelled a pending prefix; waits of tasks that are not commands (timers, sources) are never quit by `C-g`, as Emacs runs timers with `inhibit-quit`. The kernel's quit lane is unchanged.
- **Input-target stack.** Prompts push input targets. Only the innermost waiting prompt receives input and answers are delivered innermost-first, matching Emacs's nested recursive minibuffers. `let`-style state is thread-scoped ([ADR 9](0009-settings-and-scoped-values.md)), never saved and restored in shared slots.
- **Errors.** A task error is reported through the `Messages` service (the echo area by default), or to stderr when no plugin provides it, and the loop continues. There is no rollback ([ADR 4](0004-state-ownership.md)).
- **Redisplay.** After a task completes or suspends, the loop marks the screen dirty. Rendering happens when the input queue is empty, or after a time cap under sustained input, and coalesces: only the newest state is rendered ([ADR 7](0007-rendering-and-transport.md)).
- **Jobs.** Long or blocking computation runs as a job: inputs and outputs are plain serializable data (text snapshots, revisions, values; no closures over live objects), so a job can run in a thread today, in parallel under SMP, or in a subprocess, without API changes. Jobs start with a cleared dynamic environment. A job may post several results (*2026-10-22, drawing stage 5:* its procedure receives `post!` beside its cancellation check; each posted result passes the validity check on its own; a job either queues every post or, with `coalesce: 'latest`, keeps only the newest not yet applied, so a slow editor costs one task, not a backlog; `job-sleep` waits on the job's thread and wakes as soon as the job is cancelled; a job without a target applies every result until cancelled; a *source*, `context-start-source!` in `tuna/lib/background.ss`, is such a job that reads something outside the editor every few seconds, its read receiving the previous reading, and posts a reading only when it compares unequal to the last, so an unchanging source costs the editor no task; its apply runs with quit inhibited, as Emacs runs process filters). Each job declares a validity policy for its results: `exact-revision` (default; discard if the inputs changed), `target-alive` (apply while the target buffer, marker, or node exists; for streams such as terminal or LLM output), or `rebase` (the target maps result positions through its change journal since the snapshot by the same rule that moves highlights with edits, so a span an edit lands inside grows or shrinks and a span that is empty after a change is dropped, including an already-empty span after any change; for highlighting and diagnostics). Jobs have keys, such as `(highlight buffer-7)`, and a new job with the same key cancels the pending one. A running job with the same key is not cancelled, so results keep arriving during continuous typing (Zed installs a stale result, then reparses), unless it is `exact-revision` and the target has changed since it started, because then its result can no longer apply; a plugin that wants Lapce's cancel-and-restart calls `job-cancel!` on the job it holds before starting the next. Jobs are a shared library (`tuna/lib/jobs.ss`, [ADR 12](0012-kernel-boundary-and-replaceability.md)): a plugin creates a job group from its context (`new-job-group`) and starts jobs in it (`job-group-start!`); keys apply within the group, deactivating the plugin closes the group and cancels its jobs, and a closed group refuses new ones; the kernel only posts results back to the editor thread, as a name and a procedure from which the loop thread builds the result's task.
- **Cooperative job cancellation.** A job's procedure receives a cancellation check, a procedure of no arguments that turns true once the job is cancelled: by `job-cancel!`, by a newer job of the same key replacing it while pending or, for a running `exact-revision` job, starting after the target changed, or by its group closing. The check reads state the baton sets under a lock, so it stays correct when threads run in parallel. A long job calls it now and then and returns early; a cancelled job's result is never applied, and its thread is never interrupted.
- **Results that are edits** (format, rename, code actions) use `exact-revision` only: they apply at the exact revision they were computed for, as one undo group, and are otherwise dropped, as Helix and Lapce do. Background work never merges its text edits with typing.
- **Too old to rebase means re-run.** When a target can no longer rebase a result (its change journal no longer reaches back to the job's revision), the result is dropped, and re-running is the starting plugin's job, normally from its change hook; the jobs library does not report drops.
- **No CRDT or OT** for single-user editing: one writer plus revisions and change records suffices, as in Helix and Lapce. Revisit only for real-time collaboration or for workers that must edit text concurrently with typing.
- **Hooks schedule, they do not compute.** Change hooks run synchronously on the baton and must be cheap; expensive reactions schedule jobs or tasks.
- **External processes.** Subprocess reader threads coalesce output into one pending message per process with a size bound, and stop reading when it is reached (backpressure).
- **Priority.** User input is processed before job results and process output, but pending results are still applied before each render so output cannot starve.
- **Keyboard macros.** Replay is an input source feeding the same loop, not a nested loop. During replay, job results, process output, and timers are deferred except at explicit waits, so replay is deterministic.

## Consequences

- A keystroke's latency is the command plus one render. Highlighting and diagnostics arrive later as separate, cheap renders and survive continuous typing through rebasing.
- Runaway Scheme code can always be stopped: cooperatively at polling points, and forcibly anywhere else as a last resort.
- When SMP lands, jobs gain real parallelism with no API change, because they share only plain data.
- Persistent text ([ADR 6](0006-buffers-nodes-and-text-store.md)) makes job snapshots free.
- The loop must be careful around `thread-interrupt!`: core data-structure updates run with quit inhibited, and the abandoned-mutex quirk is swallowed in one helper.
- Still to settle, each before the milestone named ([research](../research/concurrency-prior-art/README.md), recommendations 6, 7, and 9):
  - before syntax highlighting: a time-budgeted inline fast path, so cheap work (a small buffer's parse) lands in the same render instead of one frame late, as Zed, Helix, and Neovim do. It is a plugin policy, not a kernel feature;
  - before any out-of-process worker: replicas receive ordered deltas with a revision check, accepting only revision + 1, as Lapce's proxy does;
  - before the minibuffer and completion milestone: a test of a task whose text changes between its yield points, the main hazard Tuna has that those editors do not;
  - before the first diagnostics producer: whether an empty span (such as a language server's zero-width diagnostic) that an edit does not reach is kept, mapped as a point, instead of dropped.

## Alternatives considered

- **Callback- or promise-style prompts.** Rejected: hostile to porting Emacs code, and needless in a language with cheap threads and continuations.
- **Polling a quit flag only (Emacs).** Rejected as the only mechanism: loops that never poll cannot be stopped.
- **Interrupting immediately on every quit.** Rejected: injecting exceptions into code that is not prepared for them is unsafe, which is why the Gerbil standard library avoids it.
- **One actor per buffer.** Rejected for now: cross-buffer commands are common and would need distributed coordination.
- **Shared mutable state with locks.** Rejected: fragile under SMP and with arbitrary extension code.
