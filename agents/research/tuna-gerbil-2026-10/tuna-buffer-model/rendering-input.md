# Research: Tuna target-neutral nodes and HTML input boundary

## Summary
Represent Tuna’s UI as a small semantic node algebra, rendered through a target context—not as HTML-shaped nodes or custom tags. For the first usable text editor, prefer a native `<textarea>` as the browser-owned input surface and a semantic HTML adapter; keep the mutable text store opaque and synchronize edits through explicit input/selection events. Treat server morphing of a live editor as a special case: preserve the same stable editor node and suppress patches during IME composition, then reconcile authoritative state afterward. This proposal does not establish usable editing until the browser matrix below passes.

## Findings

1. **Node vocabulary and render contract (recommendation).** Start with a deliberately small set: `Document`/`Group` (structure only), `Text` (escaped text), `Action` (native button/link, with explicit action meaning), `TextInput` (native editor surface), and `Status` (live feedback). Avoid generic `Div`, custom elements, slot/projection nodes, and layout primitives in the domain vocabulary. Each node implements a rendering contract such as `render(node, target-context) -> target output`; context carries target-specific capabilities/configuration, not editor state. HTML adapter maps nodes to semantic native elements and escapes all text/attribute data by default. Any raw/trusted markup must be a separate, explicitly constructed type with a narrow trusted producer; never treat buffer text as markup. A later terminal adapter can map the same semantic nodes differently without claiming HTML DOM equivalence. **Inference:** this minimizes coupling while leaving layout details to the HTML adapter; no source prescribes this exact node set.

2. **Semantic markup, ordering, and styling hooks.** Use real `<main>`, headings, `<section>` only where sectioning is meaningful, buttons for actions, and a labeled `<textarea>` for editing. Custom-element-shaped tags are not semantic controls; the HTML Standard says autonomous custom elements represent their children, not an intrinsic role. The owner article correctly warns that an ordinary `slot` attribute without a shadow root is only a CSS convention, not projection. Avoid both mechanisms for node composition. Preserve source order as reading, keyboard-focus, and visual order; do not CSS-reorder interactive content. Style broad defaults by semantic element and expose only a few stable, domain-named classes where a component hook is needed; use a small set of CSS custom-property design tokens for shared color/spacing/typography, not a framework/token product. **Sources:** [HTML custom elements](https://html.spec.whatwg.org/multipage/custom-elements.html); [owner article](https://dev.to/stuffbreaker/css-only-custom-elements-go6); skill guidance: `/home/jay/Code/shux/.agents/skills/html-css/SKILL.md` (HTML/CSS/Datastar); `/home/jay/Code/job-getter/.agents/skills/html-css/SKILL.md`; `/home/jay/Code/lipstink/.agents/skills/html-css/SKILL.md`. **Support:** direct standards + local practice; these skills’ Stellar/Stario constraints are not Tuna requirements.

3. **Input acquisition: textarea first, alternatives are materially different.** A `<textarea>` is a native, labeled, keyboard-accessible multiline editor with `value`, selection start/end/direction, and native clipboard/editing behavior. This is the smallest useful first adapter. Keep the browser-facing textarea as a projection/input surface, not the mutable store itself: on `input`, reconcile its complete value or a verified edit into the opaque text model; capture selection as model positions/anchors; never expose gap positions. If text repainting is needed, update the textarea value only when it is not actively composing and preserve selection explicitly. `contenteditable` provides rich DOM editing but introduces DOM-to-model mapping, browser-generated markup, selection normalization, paste sanitization, and accessibility complexity; defer unless plain textarea is experimentally insufficient. `EditContext` separates OS text input from rendering and supports custom editor surfaces, but MDN documents a specialized API; it shifts selection, rendering, accessibility, and clipboard responsibility into Tuna. Do not make it the baseline or assert broad browser support. **Sources:** [textarea selectionStart (MDN)](https://developer.mozilla.org/en-US/docs/Web/API/HTMLTextAreaElement/selectionStart); [EditContext (MDN)](https://developer.mozilla.org/en-US/docs/Web/API/EditContext); [Input Events Level 2](https://www.w3.org/TR/input-events-2/). **Recommendation confidence:** medium; browser experiments are required.

4. **Events, composition, paste, selection.** Treat `input` as the post-edit source of truth; `beforeinput` can describe/cancel some operations, but should not be the sole capture path. Input Events Level 2 defines `inputType` and composition-related events; composition updates are not a safe point for rewriting the editor value or selection. Track `compositionstart`/`compositionend`; while composing, defer server/model-driven DOM writes and disruptive normalization. Track selection changes and convert DOM offsets to stable logical positions; define newline/UTF-16 offset semantics explicitly before exposing positions across implementations. Prefer native paste into textarea and ingest resulting text through input; if implementing custom paste handling, read clipboard text and insert as plain text, never parse it as trusted HTML. Native copy/cut should remain available initially. Screen-reader label, visible keyboard focus, and logical document order are mandatory. **Direct evidence:** [Input Events Level 2](https://www.w3.org/TR/input-events-2/); [textarea selection](https://developer.mozilla.org/en-US/docs/Web/API/HTMLTextAreaElement/selectionStart). **Inference:** these event rules favor native textarea for initial scope.

5. **Stable identity and Datastar morph boundary.** Give editor and independently patched regions stable, content-derived IDs (identity, not CSS hooks); keep tag and identity stable across renders. Datastar documents `data-ignore-morph` as skipping an element and descendants during morphing. Put it on the active editor subtree when local input/composition must not be overwritten; still morph surrounding state-derived UI. After composition ends, reconcile and remove/relax suppression through an explicit state transition so authoritative content can render. Do not assume morphing preserves IME session, caret, or browser selection merely because a node ID matches: this remains an experiment-dependent behavior. **Sources:** [Datastar attributes reference](https://data-star.dev/reference/attributes); `/home/jay/Code/shux/.agents/skills/html-css/SKILL.md` says stable live-fragment IDs and recommends broad server morphs; the task requires state-derived Datastar morphs. **Unresolved factual input:** exact Tuna Datastar version/morph algorithm and its guarantees are not established by this research.

## Contradictions
None found in primary evidence. The dev.to article’s key distinction—custom tags lack native semantics and ordinary `slot` is only convention without shadow DOM—is consistent with the HTML Standard. Its CSS-only examples are not evidence that such tags suit Tuna’s editor semantics.

## Missing evidence
No Tuna-specific browser experiment, Datastar-version guarantee, target browser/OS/accessibility support policy, or definition of position encoding was supplied. Do not claim usable editor behavior until composition, selection restoration, paste, undo/redo, focus, and morph interactions are tested. `EditContext` suitability/support remains intentionally unsettled.

## Focused browser test matrix
Run on current Chromium, Firefox, and WebKit desktop; additionally test at least one mobile browser/OS and a screen reader once Tuna names its supported environments. For each: (1) type, delete, multiline, select/replace; verify model/value equality and caret/selection after rerender; (2) IME composition (e.g. Japanese), emoji, dead keys; provoke server/Datastar updates during composition and verify no lost/duplicated text or interrupted candidate session; (3) paste plain text and rich clipboard content, cut/copy, undo/redo; check no markup ingestion; (4) keyboard-only focus/order, label/name, screen-reader announcement, zoom; (5) stable IDs under structural edits/reorder, focus and selection retention; (6) reload/reconnect and stale authoritative update conflict. Record exact browser/OS/version and failures—no cross-browser claim from standards text alone.
