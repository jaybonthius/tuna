# Research: Emacs-inspired Tuna app state and recovery

## Summary
GNU Emacs is not a persisted application snapshot: it is a live, mutable runtime with resource-scoped state and several selective persistence subsystems. Its useful design cues for Tuna are explicit ownership scopes, a serialized mutation boundary, derived redisplay, and independently versioned persistence; do not reproduce Emacs’s ambient current-buffer model, Lisp-evaluated desktop files, or runtime complexity. An in-memory committed state plus periodic Scheme-data checkpoints is a reasonable Tuna-specific choice, but checkpoint inclusion, privacy, conflict, and recovery policy remain owner decisions.

## Findings

1. **Ownership: selection state is not one monolithic “current UI”.** **Claim:** Emacs separates buffer-owned data (text, local variables/modes and marks), window-owned display state (including point where window-specific), and frame/window-tree configuration. Global symbol values are another scope. **Sources:** [buffer.h](https://github.com/emacs-mirror/emacs/blob/master/src/buffer.h#L303), [window.h](https://github.com/emacs-mirror/emacs/blob/master/src/window.h), [window.c](https://github.com/emacs-mirror/emacs/blob/master/src/window.c), [frameset.el](https://github.com/emacs-mirror/emacs/blob/master/lisp/frameset.el#L825). **Support:** direct evidence; buffer structure stores marks/modes/local values, frameset saves filtered frame parameters and root-window state. **Confidence:** high. Point and mark are restored per desktop buffer in `desktop.el` (~1630-52); frameset saves window state separately. **Inference/recommendation:** define Tuna state scopes now (application-global vs future buffer/view/window/mode owners), but implement only extant concepts; never make a view’s transient selection silently global.

2. **Mutation ordering: Emacs’s command loop is a convention, not a universal transaction lock.** **Claim:** normal commands execute pre-command → command → post-command; timer/process callbacks can run at wait/safe points, and process filters may recurse if they wait/process output. **Sources:** [keyboard.c](https://github.com/emacs-mirror/emacs/blob/master/src/keyboard.c#L1426), [Timers manual](https://www.gnu.org/software/emacs/manual/html_node/elisp/Timers.html), [Filter Functions manual](https://www.gnu.org/software/emacs/manual/html_node/elisp/Filter-Functions.html). **Support:** direct evidence; local historical note cites the exact Emacs 30.2 ranges `src/keyboard.c:1511-1692`, `doc/lispref/os.texi:2210-2240`, `processes.texi:1978-1987`. **Confidence:** high. **Inference/recommendation:** Tuna’s single serialized mutation lane can be stronger and simpler: timer/IO completions enqueue intents; reducers/commands commit once; rendering reads committed state. Guard against nested mutation/reentrant callbacks even with one lane.

3. **Redisplay/revisions: Emacs renders from live state and uses invalidation generations, not a universal event log.** **Claim:** buffer text tracks `modiff`, character, save, and overlay modification counters; these support dirty/invalidation checks, not replay. **Sources:** [buffer.h](https://github.com/emacs-mirror/emacs/blob/master/src/buffer.h#L95), [dispnew.c](https://github.com/emacs-mirror/emacs/blob/master/src/dispnew.c). **Support:** direct evidence; local note gives insertion and revision ranges (`src/insdel.c:894-927`, `src/buffer.c:1595-1657`). **Confidence:** high. **Inference/recommendation:** Tuna may use a committed-state revision to request redisplay; keep it distinct from persistence format version and event history. Make rendering a pure projection, avoid render-side mutation.

4. **Desktop persistence is an explicit subset.** **Claim:** `desktop.el` saves eligible file-visiting buffers, selected buffer-local variables, global allowlist, and optional frameset; conventional minor modes are restored specially, while non-file buffers require a mode-provided save/restore handler. It does not serialize the Emacs process/runtime wholesale. **Sources:** [desktop.el globals/locals](https://github.com/emacs-mirror/emacs/blob/master/lisp/desktop.el#L317), [GNU Desktop Save Mode manual](https://www.gnu.org/software/emacs/manual/html_node/elisp/Desktop-Save-Mode.html), [frameset.el](https://github.com/emacs-mirror/emacs/blob/master/lisp/frameset.el#L825). **Support:** direct evidence. **Confidence:** high. Source specifics: globals default to tags/search/register/file-name history; locals include display/edit preferences, and documented rule says conventional minor modes auto-restored rather than listed. Saved buffer records include filename/name/major mode, point/mark/read-only and minor modes; load handlers run before point/mark restoration (desktop.el ~1505-1652). Frameset stores filtered frame params plus `window-state-get` root tree; restore offers reuse/filter/onscreen/cleanup policies. **Recommendation:** deliberately enumerate Tuna checkpoint fields; excluded data is as important as included data.

5. **Desktop format/order and resilience.** **Claim:** desktop is readable Emacs Lisp data with header, format and Emacs version; default/current formats 206/208 include compatibility choice. Startup reads desktop, checks lock, suppresses autosave while loading, and restores buffers (optionally eager/lazy); file/version errors can disable autosave to avoid overwriting a broken desktop. **Sources:** [desktop.el](https://github.com/emacs-mirror/emacs/blob/master/lisp/desktop.el#L1088), [desktop.el restore](https://github.com/emacs-mirror/emacs/blob/master/lisp/desktop.el#L1295), [desktop manual](https://www.gnu.org/software/emacs/manual/html_node/emacs/Saving-Emacs-Sessions). **Support:** direct evidence. **Confidence:** high. Desktop saves only when it owns the lock, asks/declines on locked desktops per configuration, and checks modification time before overwriting; concurrent external edits still require careful policy. **Inference/recommendation:** Scheme-data serialization should be data-only and schema-versioned, never executable Scheme; validate before applying, preserve last-known-good checkpoint, report failures, and define stale-lock/corrupt/unknown-version handling. These are Tuna recommendations, not Emacs claims.

6. **Periodic desktop saving is idle-triggered and conditional.** **Claim:** when enabled, desktop schedules an idle timer after window-configuration change; on firing it saves only if mode enabled, timeout positive, not lazy-restoring, it owns the lock, and directory is known. **Sources:** [desktop.el timer](https://github.com/emacs-mirror/emacs/blob/master/lisp/desktop.el#L1432). **Support:** direct source evidence. **Confidence:** high. **Interpretation:** this is not a hard periodic durability guarantee: busy sessions can defer idle timers; separate exit save exists. Tuna should select wall-clock interval vs idle debounce explicitly and test crash-loss window.

7. **`savehist` and autosave/recovery solve different durability needs.** **Claim:** savehist writes selected history variables as readable Lisp expressions; default timer interval is 300 seconds, file mode defaults to 0600, autosave avoids identical rewrites and uses precious-write behavior, warns on file errors, and attempts to reconcile changed file timestamps with another Emacs. **Sources:** [savehist.el](https://github.com/emacs-mirror/emacs/blob/master/lisp/savehist.el#L53), [savehist save](https://github.com/emacs-mirror/emacs/blob/master/lisp/savehist.el#L286), [manual](https://www.gnu.org/software/emacs/manual/html_node/emacs/Saving-Emacs-Sessions). **Support:** direct evidence; source. **Confidence:** high. Ordinary buffer auto-save is recovery of unsaved file contents, not desktop/session state. `recover-session` reads a separate session index of visited-file/autosave-file pairs, ignores absent autosave files, then asks per file and invokes `recover-file`; malformed entries can be skipped/produce no recoverable files. **Sources:** [files.el recovery](https://github.com/emacs-mirror/emacs/blob/master/lisp/files.el#L7540), [Auto-Saving manual](https://www.gnu.org/software/emacs/manual/html_node/elisp/Auto_002dSaving.html). **Recommendation:** distinguish app-state checkpoint from user-content recovery and user history; don’t conflate checkpoint restoration with recovering unsaved documents.

8. **Tuna plan implications.** **Direct user constraints:** UI = function(committed app state); one mutation lane; memory-first with periodic Scheme-data checkpoints; future buffers/views/window layout/modes, not prematurely implemented; Emacs-inspired, not replicated; no custom macros/live bindings for new state code. **Researcher inference:** preserve those constraints with one ordinary explicit state value and ordinary procedures, narrow commands that return/commit next state, and pure rendering. Establish stable identities and ownership vocabulary without creating unused abstractions; add revision only for invalidation; make persistence an explicit whitelist/schema. Do not adopt Emacs’s Lisp-expression files, dynamic current-resource lookup, global interpreter lock, or wholesale object-graph persistence.

## Contradictions

None found in reviewed sources. Do not interpret “desktop session restore” as persistence of buffer text: visited files are reopened from their files; autosave/recover-file is a distinct path for unsaved file content.

## Missing evidence

- No separate source audit of every desktop minor-mode handler or platform-specific frame parameter; exact restorable modes depend on installed mode handlers.
- Did not inspect every autosave scheduling/cleanup path in C and Lisp; this brief covers session recovery’s index/selection behavior, not a guarantee of autosave durability.
- Emacs source checkout is newer than release tag used in historical note; source line references here are path anchors, not immutable release line references.
- Need owner policy for what Tuna checkpoints may contain (history, paths, user content, secrets), permissions/location, restore prompt/automatic behavior, corruption fallback, and multi-process conflict/locking. Privacy/recovery behavior is a product decision, not derivable from Emacs.
