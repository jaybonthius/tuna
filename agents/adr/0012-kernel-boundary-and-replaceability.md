# 12. A small fixed kernel; every editor feature is a plugin, in three tiers of replaceability

Status: accepted (2026-10-11); amended 2026-10-12 with the kernel contract (owner-approved brief: [`docs/briefs/2026-10-kernel-contract.md`](../../docs/briefs/2026-10-kernel-contract.md); research: [`agents/research/kernel-contract/`](../research/kernel-contract/), [`kernel-audit-2026-10-12.md`](../research/kernel-audit-2026-10-12.md)). The "Kernel contract" section below supersedes the kernel list in the Decision section where they differ. Amended 2026-10-14 by the owner-approved [kernel alignment brief](../../docs/briefs/2026-10-kernel-cordis.md) (three sections at the end of the kernel contract; kept divergences from Cordis are recorded in [ADR 2](0002-plugins-contexts-and-services.md)).

## Context

The owner wants Tuna itself to be little more than scaffolding, with everything else (state, command loop, window management, buffers) supplied by plugins, as in Cordis-based systems. The alternative is a functional core that exposes replaceable parts through contracts.

The two differ in one respect that matters: whether Tuna's default implementations use the same contracts as third-party plugins. Where defaults live in a privileged core, contracts decay unnoticed (VS Code's and Neovim's editing cores are not replaceable for this reason). Where everything is a plugin, contracts are exercised daily, but some things cannot be plugins: the machinery that loads plugins, and the concurrency rules every plugin's safety depends on. Editor subsystems are also more tightly coupled than Cordis's original domain (chat bots); Eclipse/OSGi shows the cost of fine-grained extension points nobody can follow.

## Decision

- **Defaults are plugins.** Every editor feature is a plugin, and Tuna's own defaults (text store, buffers and views, command-loop policy, minibuffer, window manager, renderer, persistence, transport) use only public contracts, with no privileged access. Tuna ships a standard plugin set so it works out of the box. (Superseded 2026-10-12: there is no standard set; Tuna ships a starter `init.ss` the user copies, and with no configuration it turns nothing on. See the configuration brief.)
- **The kernel** is the only part that is not a plugin. It contains:
  1. the plugin runtime: contexts, receipts, the service registry, manifests, and dependency activation ([ADR 2](0002-plugins-contexts-and-services.md));
  2. the execution rules: the baton, tasks and yield points, jobs, and the quit lane ([ADR 3](0003-command-loop-and-jobs.md)) (the kernel contract below keeps only posting results; jobs are a shared library);
  3. shared vocabulary that contracts depend on: identities, revisions, and change records ([ADR 4](0004-state-ownership.md)) (the kernel contract below moves change records to the buffers contract and keeps only identities; revisions belong to the objects that carry them).

  It contains no editor features.
- **Three tiers of replaceability.**

  | Tier | What | How it is replaced |
  |---|---|---|
  | Fixed | The kernel | Only by upgrading Tuna |
  | Startup | Command-loop policy (key resolution, keymap stack, input sessions; [ADR 8](0008-input-keymaps-and-command-composition.md)), settings resolution ([ADR 9](0009-settings-and-scoped-values.md)), persistence format ([ADR 5](0005-persistence.md)), client transport ([ADR 7](0007-rendering-and-transport.md)) | Select another provider in configuration and restart |
  | Live | Text store, texts/buffers/views, window manager ([ADR 11](0011-window-management-is-a-plugin.md)), renderer, minibuffer and prompts, completion, modes, themes, and everything else | Swap at runtime: the provider and its dependents restart and restore their saved state (*2026-10-14*; formerly the outgoing provider handed its state over) |

  A service declares its tier. ~~Startup-tier services refuse live replacement.~~ *2026-10-14:* the tier is a label; start-up code's reload policy, not the kernel, defers a change that touches a startup-tier provider to the next start.
- **Few, coarse contracts.** Contracts sit at subsystem boundaries (text store, buffers, window manager, renderer, input), not around individual functions, and contracts between coupled subsystems are designed together.
- **Proving contracts.** Each contract is designed while its default is built and proven by swapping in a deliberately small second implementation.
- **Versioning.** Contracts carry versions; plugin manifests declare which versions they support.
- **Recovery and visibility.** Recovery from a broken configuration comes from the user's own configuration, not from a built-in default plugin set, and Tuna keeps no stored history of it (configuration brief, 2026-10-12). Built (configuration stage 1): start-up turns each declared plugin on separately, so a failure is undone and reported, plugins that need it are skipped, and the rest come up; a start-up report on the terminal and in `$XDG_STATE_HOME/tuna/startup.log` lists what came up, failed, or was skipped; `tuna check` loads and validates a configuration without starting anything. Built (configuration stage 2): reloading a fixed configuration into the running editor (`reload-config` inside Tuna, `tuna reload` from a terminal) applies only what changed and turns the running version back on when a new one fails. Built (configuration stage 3): after a start-up with problems, the echo area shows a one-line summary naming the log file and, when the configuration plugin is on, the `show-config-report` command, which shows the last start-up or reload report again. A `describe-services` command shows which provider fills each service, its tier, and its dependents.

## Kernel contract (amendment, 2026-10-12)

The skeleton let the kernel drift from about 1,050 to 1,800 non-test lines by absorbing pieces of features (hooks table, timers, session slots, a command registry, a browser keyboard event type, text ranges for one job policy, latency data). This section is the authoritative statement of what the kernel is.

**Four layers**, each using only the layers below it: plugins (Tuna's own and users'), contracts (*2026-10-14:* each concept package's `plugins/<concept>/contract.ss`, beside its default plugin, plus Tuna's own `tuna/configuration.ss`; formerly `tuna/services/`: interfaces, service values, vocabulary types, thin dispatchers only), shared libraries (`tuna/lib/`: conveniences built only on the public kernel API, with no special access; today timers and jobs), and the kernel (`tuna/kernel/`, facade `tuna/kernel.ss`).

**The kernel contains exactly:**
1. **Plugin runtime:** plugins, `defplugin`, contexts and receipts (`context-defer!` is the one primitive every registration is built from), owner-tagged entries, activation and deactivation, services with one provider each, tier labels, and required dependents that restart. Swap orchestration, state restoration and startup-only reload policy live outside the kernel.
2. **Execution rules:** the baton, tasks, suspension at yield points, the quit lane, the input queue, `input-pending?`, `discard-input`, and posting a result to the editor thread from another thread (`result-poster`). Input reaches the queue through a procedure captured from the kernel (`input-submitter`, which replaced `submit-input!`): the kernel object is private, so only the kernel can bind a submission to its own loop, and a transport's request threads never select a kernel.
3. **Hooks and identities:** one generic hook mechanism (each hook object owns its callbacks; no kernel table), which the kernel also uses to announce its own lifecycle events (`plugin-activated-hook`, `plugin-deactivated-hook`, `service-changed-hook`, `task-started-hook`, `task-finished-hook`; each runs after its state change is complete, and its callbacks must not activate or deactivate plugins; while the editor loop runs they may queue a task that does); and `next-id!`.
4. **Consumed seams:** the `Input`, `Display`, and `Messages` services the kernel calls.

**The kernel must never know about:** keys, mouse, browsers, HTTP, clients, text, characters, positions, ranges, changes to text, buffers, views, windows, frames, screens, rendering, a command registry, keymaps, settings, files, saving and sessions, timers, profiling or measurement, the demo, or the name of any plugin. `tuna/kernel/` imports nothing from `tuna/services/` or `tuna/plugins/`.

**Input:** the kernel queues opaque input items and never looks inside them. The `Input` service has two duties: classify an arriving item as "queue" or "interrupt" (on the arriving thread, without touching editor state; this is how the quit key works), and resolve a queued item to the task it starts, as a name and a thunk (on the baton; for keys, the command registry in the keys plugin supplies both). Key presses are resolved through keymaps by context and mode. Clickable UI (buttons, menu items, mouse clicks) sends "activate node N with gesture G"; the input plugin checks that node N is still current and resolves the gesture through the node's keymap, which the server bound when it rendered the node (for example `activate` to a command with captured arguments). The client never names a command. This follows Emacs, where buttons and menus are events resolved through keymaps. Purely presentational interaction (scrolling, disclosure) may stay in the browser.

**Changes to the kernel:** there is no size limit. Every new kernel export, data field, or interface method requires an amendment to this ADR saying why no plugin or library could own it, and every merge review states whether the kernel changed and why. `make test` includes mechanical checks: a search of `tuna/kernel/` for the forbidden nouns above, a check that the kernel imports no service or plugin module, a check that libraries import only `:gerbil`, `:std`, the kernel facade `:tuna/kernel`, and other libraries, and a check that only tests import test support (`tuna/test-support/`, which holds the test-only way to make a fresh kernel), amended 2026-10-13: tests and the development-only demo (`demo/`) may use test support, the demo only its plugin fixtures and contract doubles (its own tests, in `demo/tests/`, as any test; added 2026-10-24 when the hungry-delete demo's test moved there), and nothing in `tuna/` or `starter/` may use `demo/`.

- **The configuration plugin (then `reload-config`) imports program code (2026-10-13, configuration stage 2).** Not a kernel change, but an exception to "each layer uses only the layers below it": `tuna/plugins/reload-config.ss` imports `:tuna/boot`, the program's start-up and reload code, because the reload operation has no contract yet and a contract for one consumer would be shaped around it. `tuna reload` itself lives in program code (`tuna/control.ss`, started by `tuna/main.ss`), not in a plugin, because it must work when no plugin, or a broken one, provides input. `tuna/kernel/boundary-test.ss` checks that no other non-test module imports `:tuna/boot`, `:tuna/control`, or `:tuna/main`. Stage 3 adds a configuration contract (`tuna/services/configuration.ss`: reload, the start-up report) once its second consumer, a command that shows the start-up report again, exists; the exception then goes away. **Resolved 2026-10-13 (configuration stage 3):** `tuna/services/configuration.ss` defines the configuration service (reload, and the last start-up or reload report); the start-up code provides it through its own `config-service` plugin; `reload-config` and `show-config-report` use the service, no plugin imports program code, and the boundary test has no exception.
- **`plugin-requires` (2026-10-12, configuration stage 1).** The facade now exports the accessor for the services a plugin declares it requires, an existing field of the plugin value (ADR 2's manifests already list required services). The start-up code (`tuna/boot.ss`) uses it to turn a declared plugin on only once its services are provided and to report a plugin it skips as "needs X, which no plugin provides". Nothing outside the kernel can recover this from the plugin value otherwise. It adds no behavior and no state.

### Declared use and owner lifetime (amendment, 2026-10-14, Cordis stage 1)

The approved [kernel alignment brief](../../docs/briefs/2026-10-kernel-cordis.md) extends items 1–3 above, without changing provider priority, tiers, adapters or handover:

- **Declared use belongs to the plugin runtime.** A plugin lists required external services in `requires:` and guarded external services in `optional:`. Only required services affect activation and dependent restarts. A provider may use its own service once it owns a provider entry, even when another entry is effective. `service-provider` and contract dispatchers reject other undeclared use, naming the plugin and service. The kernel's `message` facility needs no declaration: it dispatches to Messages when available and otherwise writes to stderr. Direct access to the Messages service still follows the declared-use rule. The plugin value carries the optional list and an exemption flag. Unowned calls, and the generated owners of the user's `init.ss` body and `config:` blocks, remain unchecked: this checks plugin authors' code, not the user's customization. Config blocks retain their existing follower-managed receipts and turn off with their target plugin. No session owner is added in this stage.
- **Execution attribution is shared runtime machinery.** `call-with-context` and `context-bind` carry a callback's owner; `call-with-service-provider` checks the caller and selects the provider from one registry lookup, then runs it under its own context; an already-current context needs no new parameterization. `with-service-provider` is the small typed-dispatch form shared by contracts. Provider internals cannot borrow their caller's declarations. The kernel's own consumed seams run under their providers rather than under the plugin asking the kernel to redisplay or start its loop. These scopes belong in the kernel because it alone owns contexts and the provider registry.
- **Entry ties use declaration order, not registration time.** Each plugin record has an owner-order value, shared by its context and entries. `set-plugin-order!` and the `order:` activation argument let the activator supply that rank; start-up supplies each declaration's position in `init.ss`. Later declarations win equal priorities; equal unspecified ranks use plugin name for a deterministic result. Reloading an earlier declaration cannot promote it. Shared order values also let a configuration reorder retained entries without restarting them. Ordering owner-tagged entries is a runtime rule, not an editor feature.
- **A live task body can belong to a context.** `call-with-task-owner` adds a temporary cancellation inverse to that context's receipt and removes it when the body returns. The Commands contract uses this generic execution rule for command bodies, including direct-style waits. Turning off their plugin quits its waiting commands without turning off the prompt provider. The kernel still knows nothing about Commands or prompts.
- **Named registrations replace.** An entry table retains one contribution per owner and slot name. A hook retains one callback per kernel, owner and callback name; replacing it preserves its equal-depth position, while a changed depth repositions it. Receipt inverses remove by identity, so an old inverse cannot remove a replacement. `context-add-hook!` is a registration macro: named functions are called through their live binding; closure expressions intentionally capture their value. With separate compilation, redefining a named callback takes effect without re-registering it. These rules belong to the existing generic entry and hook mechanisms.

*Superseded later on 2026-10-14:* the per-call check, the context switching in dispatch, `unchecked:`, and the attribution-only `context-bind`/`call-with-context` sites are removed (kernel −55 non-comment lines; dispatch 132 → 59 ns). The check of declared use moved to start-up code, run when any plugin is turned on ([ADR 2](0002-plugins-contexts-and-services.md)). `activate-plugin!` is no longer exported by the kernel facade; turning a plugin on goes through the configuration code's checked path. Kept: receipts, owner-tagged entries, implicit registration during activation, command tasks cancelled with their plugin.

### One provider and saved-state replacement (amendment, 2026-10-14, Cordis stage 2)

- `defplugin` declares `provides:` alongside `requires:`. Configuration rejects two declared providers of the same service, naming both plugins. `context-provide!` checks this declaration and refuses a second provider even from the same owner. Unchecked user code remains exempt from the declaration check, not from the one-provider guard.
- Provider priorities, hand-back, handover, adapters and stranded-adapter state are deleted. Required dependents deactivate and reactivate; optional use does not create a dependent.
- The read-only `plugin-deactivation-closure` query exposes the active plugin definitions that would turn off, in activation order. Only the kernel can compute this closure from its dependency records. `plugin-provides` exposes the declared service list so configuration can reject duplicates before activation and pair a removed provider with its replacement.
- Program code uses one restart path for reload, swap and restart: the session plugin captures the closure's slots before any receipt runs; program code turns off the closure and activates the replacement; the session plugin restores its saved data. Failure restores the old definitions and captured data. A provider uses its own saved slot when present, otherwise its contract's neutral saved slot. Session state never enters the kernel.
- `startup` remains a service label, not a kernel prohibition. Reload policy defers a change whose closure includes a startup-tier provider while the editor loop runs.

### The session owner (amendment, 2026-10-14, Cordis stage 3)

No kernel change. Interactive evaluation belongs to one always-on owner, `session-owner`: the start-up code's own plugin, which also provides the configuration contract, uses the stage 1 `unchecked:` exemption, is not a declaration in `init.ss`, and is therefore never diffed, replaced or restarted by `reload-config`. The configuration contract gains `evaluate-form` and `evaluate-forms`, which run under that owner in a persistent top-level environment importing `:tuna/config`; a sequence stops at the first error and keeps earlier effects, as in Emacs. Its entries take the greatest declaration order, so they win equal-priority ties with the configuration even after a reload.

### Two read-only accessors (amendment, 2026-10-15, review cleanup)

- `plugin?`: configuration validates declaration data without using a failing type cast as a predicate.
- `context-plugin-name`: registration diagnostics name the owning plugin without creating a registration to learn it.

### Reaching the right loop from any thread (amendment, 2026-10-22, drawing stage 5)

A bug fix, approved with the [background work brief](../../docs/briefs/2026-10-background-work.md); no export, signature or message changes. `resume!`, `resume-quit!`, `spawn-task!`, `cancel-task!` and `call-on-editor-loop` were documented as callable from any thread, but found their loop through the kernel parameter, which a root thread (a job's, a worker's) does not have: under a test kernel they raised or did nothing, and in production they reached the right loop only because it was the default kernel's.

- An operation on an object goes to that object's loop: a suspension records its loop's thread (`suspension-loop-thread`, set by `suspend`), and a task records the loop it was queued on (`task-loop-thread`, set when it is queued or started). Both fields are private to the kernel.
- An operation without one goes to the caller's loop: the loop thread runs in its own Gambit thread group, named by the loop, which every thread it starts inherits, root threads included; `caller-loop` walks up the calling thread's groups and falls back to the kernel parameter.

No plugin or library could own this: only the kernel knows which loop a suspension or task belongs to.

A second quit-lane bug fix in the same stage (2026-10-23): a task now records the interrupt item that asked it to quit (`task-interrupt`, private), and when it ends without having quit, the loop queues that item as input instead of dropping it (ADR 3). And a task asked to quit between `suspend`'s quit check and its suspension now quits that wait at once. Before, a `C-g` that reached a short task which never checked for quit was lost, which sources made frequent, and one that reached a task about to wait was held until the wait ended. No export, signature or message changes; only the loop sees the quit lane.

## Consequences

- "State management" is not a replaceable component: each plugin owns its state objects, the kernel enforces ownership, and saving state is the persistence plugin's job.
- The kernel stays small enough to understand completely; most of Tuna's code lives in plugins that users can read, fork, and replace.
- Every default costs a contract and a toy second implementation. This is the price of honest replaceability and is paid once per subsystem.

## Alternatives considered

- **Functional core with replaceable parts.** Rejected: defaults inside the core bypass the contracts, so replaceability erodes.
- **Literally everything a plugin, including execution rules.** Rejected: plugins cannot load themselves, and swapping concurrency rules mid-session would invalidate every running task.
- **Every service live-replaceable.** Rejected: large design cost for things changed perhaps once.
