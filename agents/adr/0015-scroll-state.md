# 15. Scroll state on items: measured, placed, scrolled natively

Status: accepted (2026-10-17); amended 2026-10-21 (stage 4: the browser's own scroll bar, over spacers sized by the measured average item height). Owner-approved briefs: [`docs/briefs/2026-10-scroll-state.md`](../../docs/briefs/2026-10-scroll-state.md) (the model) and [`docs/briefs/2026-10-scrolling.md`](../../docs/briefs/2026-10-scrolling.md) (native scrolling; its spacer and height-guess design is superseded). Plan: [`agents/plans/scrolling.md`](../plans/scrolling.md). Evidence: [`agents/research/scrolling/`](../research/scrolling/README.md), including the stage reports. Settles the scrolling part of ADR 7's layout-facts research item.

## Context

A buffer can be gigantic; drawing all of it cost 489 ms and 3.35 MB per key on a 50,000-line text (resource audit, 2026-10-15). Tuna must draw only what is near what the user looks at, keep scrolling smooth on desktops and phones, work over a slow link, and leave commands like `C-v` and session restore able to say where a view is. Layout belongs to the browser (ADR 7): only the browser knows how big anything is. Buffers are trees of arbitrary UI nodes (ADR 6, ADR 13), so nothing may assume uniform lines.

Prototypes tried every family of solution, on desktop Chrome and the owner's iPhone, at 0 and 80 ms round trips (research README):
- **The server moves the pixels** (Emacs-style; wheel and finger deltas go to the server, which redraws). Even with compressed, pipelined frames and server-side smoothing it trails input by one round trip; over lag the owner found it unacceptable.
- **Native scrolling over spacers** (a scroller covering the whole buffer, empty blocks standing in for undrawn content, sized by estimated heights). Smooth, but every bug came from the estimates: blank regions when estimates drifted, a scrollbar thumb sliding away from the pointer as the estimated total changed, special cases for unknown heights.
- **Native scrolling over drawn items only** (this decision). Smooth, and nothing is guessed.

## Decision

- **Items.** A scroller lays out *items*. A node kind says how it opens into items (`items:` on the kind: its children's items, or whole); a text node's items are its lines; any other node is one item. Each item has an identity that survives edits around it (a node, or a text position that relocates as point does), and a token the page carries on its element. Scrolling code knows items, never lines, rows or nodes.
- **Scroll state** per scroller (today each view): the item at the top edge and the px of it above the edge, as the browser measured. It lives on the view in the buffers contract with the last measured facts (last item wholly in view, visible count, size) and the derived before/after counts of items to draw, which are only a fetching step and are never saved.
- **Positions are always measured.** The only estimate is the height of the *spacers*, the empty blocks standing in for the items not drawn before and after the drawn run: the number of items each stands for times the view's average item height, as the browser measured it (drawn height over drawn items). It exists so that the browser's own scroll bar can cover the whole buffer: an owner decision (2026-10-21) after comparing four options on his phone, the spacer demo on branch `spacers-demo` among them, which he found "perfect". The average lives on the view with the other measured facts, is never saved, and changes only on the view's first report and on a report from a spacer, so spacers do not swing between reports. No position is ever worked out from it; it sizes spacers and counts items across one. Until the browser has measured a view, it has no spacers. How many items to draw on each side follows the density the browser measured, toward the `drawn-screens` setting (view heights beyond what is visible, default 2, chosen by the owner on his phone); near an end of the buffer every item to that end is drawn rather than a spacer shorter than that.
- **Two flows.** The browser *reports* what it measured (one report in flight; a report removes its trigger, and the next screen restores it). The server *places* an item (top, centre, bottom, or an exact offset) once per placement, through a marker element whose id carries the placement number; reports measured before the newest placement are ignored. A refresh places the current scroll state, so it keeps place; a restart restores the saved newest placement. A spacer in view asks for a report (`data-on-intersect`); one that comes while a report is in flight is dropped, and the next screen observes again.
- **A report from a spacer.** When the top edge is in a spacer, the report names the drawn item next to it and how far the edge is from that item (above: up from the first drawn item; below: down from the end of the last). The server counts items from that item by the average the spacer was drawn with, takes the item whose share of the spacer holds the edge as the scroll state, with the rest as its offset (past the first or last item, that item with the rest as offset), and the view's placement names it exactly. If nothing drawn was in view and the view has not moved since, the browser puts that item at its top; a view that moved on is left where the browser has it, and its next report says where it is. Counting starts at the nearest drawn edge, never at the top of the buffer, so no estimate of everything above adds up.
- **The browser moves the pixels.** Native scrolling, momentum and touch, on the compositor thread, with the browser's own scroll bar; its drags and track clicks are ordinary scrolling, handled by reports. The browser holds the measured top item still when items are added above it (scroll anchoring; spacers are never the anchor), and the page corrects where Chrome does not anchor: at scroll offset 0 (measured 2026-10-21), the reported item goes back where the scrolling since the report took it. Screens are sent only once the page applied the last one (`/applied`), and the page reads every input body before it is answered.
- **Scroll reports are special events** (Emacs's `special-event-map`): handled as soon as they arrive through `call-special-command`, never `this-command` or `last-command`, no command hooks, a pending prefix untouched. The event kind decides. Scroll commands are ordinary commands.
- **Point and the view: whichever moved last wins.** After a command that moved point or edited its text, a point outside the measured visible items is placed: at the edge it passed, or the centre when more than a screen away. After scrolling, point moves into view keeping its column, unless `scroll-moves-point` is off. `C-v`/`M-v` keep two items of context; `C-l` cycles centre, top, bottom. Splitting copies the placement; showing a buffer places point.
- **Placement in plugins:** items, scroll state, placements, facts, the average item height and `drawn-screens` in the buffers contract; the report event (with its spacer fields) in the keys contract; parsing and the browser actions (`tunaScroll`, `tunaPlace`) in the web plugin; drawing the item run, the spacers with their intersect trigger, and the marker in the renderer; `view-scrolled` (counting across a spacer, the average), the commands and the point policy in the scrolling plugin; saving placements with the layout's view data. The kernel is unchanged.

## Consequences

- No position is estimated, so drawn content never lands in the wrong place; the estimate only sets how far the browser's scroll bar thumb is for a given item, and which item a far jump lands on. Places nobody has seen cost nothing.
- A fast scroll can outrun the two view heights drawn ahead and show the spacers' faint lines until the next screen (desktop Chrome at an 80 ms round trip and 9,000 px/s: about half the frames; at 3,000 px/s none). A drag of the scroll bar far away shows spacer for one round trip.
- The scroll bar's thumb is the browser's: its position follows the spacers, so tall and short items weigh by the measured average, and it moves a little when the average is re-measured after a far jump.
- Each key redraws every drawn item: at two view heights about 10 ms of server CPU and 25–36 KB per screen on `*long*` (was 39 ms and 370 KB at 20,000 px). Per-item HTML reuse and stream compression are follow-ups (`TODO.md`, roadmap item 8).
- The spacers' total height is bounded by the browser's largest element (about 33 million px in Chrome): at 25 px an item, a little over a million items.
- Items taller than the view scroll by whole items with the commands (Emacs scrolls inside a tall line with vscroll).
- Node scrollers (a node scrolling in its own box) and the layout's scroll containers use the same model; they are built with their first user.

## Alternatives considered

- **Server-moved pixels** (three variants, including pipelined compressed frames, server-side smoothing, and a local preview that slides the frame by unshown input). Rejected: one round trip behind the finger; the preview variant is client-side prediction, which the owner ruled out.
- **Spacers sized by estimates**, with per-item estimates and remembered measurements (CodeMirror's height map). Rejected for positions: still estimates, and the owner judged guessing sizes unacceptable for arbitrary UI. Adopted on 2026-10-21 for sizes only (above): one measured average per view, positions measured, counting from the nearest drawn edge.
- **Tuna's drawn scroll bar** (the decision from 2026-10-17 to 2026-10-21). The renderer drew a bar beside each view, its handle from the top item's index over the item count, sized by the items in view; dragging placed the item at that fraction (`scroll-bar-drag`), clicking the track paged (`scroll-bar-page`), through scroll bar events in the keys contract (`<vertical-scroll-bar> <drag-mouse-1>`, `<vertical-scroll-bar> <mouse-1>`) and a page action (`tunaScrollBar`) with a drag preview; on phones a thin indicator while scrolling; the browser's bar was hidden. Exact, with nothing estimated. Replaced: on his phone the owner preferred the browser's own scroll bar over spacers (touch, fast dragging and the platform's look come for free), and the drawn bar was a second scrolling model with its own events, commands and browser code. Its cost, one estimate used only for sizes, was judged worth it.
- **Hyperlith's fixed-size virtual scroll.** The pattern this decision adapts (native scroll, server windowing, threshold reports, one in flight), without the fixed item size.
