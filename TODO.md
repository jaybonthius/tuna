## Report or fix upstream (Gerbil / Gambit)

- [ ] **`gxc -O` hangs on an empty self-loop.** Compiling a module containing `(let lp () (lp))` with the optimizer never finishes; without `-O` it compiles. Found in stage 1 on Gerbil v0.19-dev-63 / Gambit v4.9.8; reproducible with a one-line module. Tuna works around it by giving such loops a body.
- [ ] **`thread-interrupt!` blocks its caller** until the target thread runs the interrupt, and raises `abandoned-mutex-exception` in the caller when the interrupt escapes. Check whether this is intended Gambit behavior and documented; if so, note it for Gerbil users, otherwise report it. Tuna interrupts from a helper thread.
- [ ] **`append-map` in `:std/list/list` reverses each sublist.** `(append-map (lambda (x) [x (* 10 x)]) [1 2 3])` returns `(10 1 20 2 30 3)` on Gerbil v0.19-dev-63: the final fold conses each result's elements onto the accumulator. Found in stage 4. Tuna's plain-text renderer avoids it; `buffer-texts` (order of several text nodes) and the kernel's dependency closures (order irrelevant) still use it.
- [ ] **`gerbil test` exits 0 when tests fail.** `run-tests` in `src/tools/gxtest.ss` (lines 44–67 in the Gerbil checkout) returns 42 when the harness fails, but the `gerbil` binary's `tool-main` (`src/gerbil/main.ss`, lines 201–212) only returns that value from the program's `main` (lines 239–254, installed with `##main-set!`), which never passes it to `exit`, so the process exits 0. Confirmed on the installed v0.19-dev-63-g1cfb032c with a one-check failing suite. Tuna's `make test` works around it by requiring `OK` as the last line of the test output (`Makefile`, `test` target); remove that once fixed upstream.
- [ ] **A killed build leaves a lock that hangs the next one.** Gerbil's compiler driver (`gerbil/compiler/driver.ss`, lines 280–293 in the checkout) retries forever while `<object>.lock` exists; a build killed during the exe link leaves `.gerbil/bin/tuna__exe_.o.lock` and an empty `tuna__exe_.o`, which later counts as up to date, so the next `gerbil build` hangs at the link step. Seen in configuration stage 2. Workaround: delete `.gerbil/bin/*.lock` and the empty `*.o`, then build again.

## Tuna

- [ ] **Jobs that post several results** (carry-over from stage 3). A job's `run` returns one result. Posting partial results (for example a highlighter coloring a large text in chunks) needs a way for `run` to post through the job's validity check without finishing; deferred until a job needs it.
- [ ] **Autosave runs on the baton.** Each changed text is written synchronously while idle. Texts are persistent, so a large text could be written from a job over a snapshot instead.
- [ ] **No `fsync` before the atomic rename** of session and autosave files: a crash of the machine (not of Tuna) shortly after a save could leave an empty file on some file systems. Gambit has no portable `fsync`.

- [ ] **Session restore order is implicit.** Slots restore in the order plugins registered them; the configuration activates autosave before the layout so buffers exist before views refer to them. Make restore order explicit (dependencies between slots) before more stateful plugins arrive.
- [ ] **A buffers swap still restarts the plugins that make buffers** (stage 2). The layout now adapts and keeps its views, but plugins that own buffers (`*welcome*`, the demo's `*sidebar*`) restart, so their buffers are killed and rebuilt: an ordinary view of one falls back to another buffer, a dedicated one closes, and waiting prompts are cancelled. Such plugins could adapt too, rebuilding nothing.
- [ ] **A text's list of text nodes never shrinks** (stage 1). Detached nodes stay referenced; make it weak or prune it when a node leaves its tree.
- [ ] **Text reads allocate through the provider** (stage 1): each size, substring, or line read goes through one snapshot method. Measured in stage 3 (`/home/jay/Code/workbench-gerbil/scratch/tuna-views/render-bench.ss`, a 5,000-line, 405,000-character text, 40 redraws): drawing its text node costs about 64 ms, of which the text reads alone (line start, end and characters for every line) are about 22 ms; HTML reuse now makes a redraw with nothing changed about 2 ms (64 ms before), but moving point or typing still redraws the whole text node (64 ms before and after). Drawing only what is in view, or reusing HTML per line, is what would cut the rest.
- [ ] **Kept HTML for removed nodes** (stage 3): the HTML renderer keeps each node's HTML per view until the view stops being drawn or is drawn from another node, so nodes removed from a buffer that stays shown are kept meanwhile. Prune by node when rich buffers churn.
- [ ] **Closing *Help* does not bring back what its view showed** (stage 3): when `display-buffer` reused an ordinary view for *Help*, `C-h q` kills *Help* and the view shows another buffer, not the one it showed before (Emacs's `quit-restore`). Also `q` inside *Help* waits for buffer keymaps.
- [ ] **A waiting question keeps its keys when you leave it** (stage 3). The prompt's keymap is an input target pushed on the stack, so after `C-x o` away from the minibuffer, `RET` still answers the question while other keys go to the selected view. Emacs scopes the minibuffer's keys to its buffer; Tuna needs buffer-local (or view-local) keymaps from ADR 8.
- [ ] **The demo sidebar does not return after a restart** (stage 3): its buffer is rebuilt only by `C-c d`, so the restored layout drops its view. Plugins that own buffers need a way to rebuild them on restore.
- [ ] **No command creates a nested container** (owner, 2026-10-13: a fundamental gap). `C-x t 2` always adds to the nearest tab group above, so tabs can only be made at the top of a branch, never nested; nothing wraps a selected container in a new one or changes a container's kind or direction. Add i3-style commands: wrap the selected part (`C-x w a` widens) in a new tabbed or fit container, and change a container's kind (fit ↔ tabbed) and direction. Not to be fixed until the owner schedules it.
