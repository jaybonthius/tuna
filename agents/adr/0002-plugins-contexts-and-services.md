# 2. Everything is a plugin; plugin contexts revert what they register

Status: accepted (2026-10-11); amended after the [capability audit](../research/capability-audit/README.md) (owner-tagged effects, manifests, reload, multi-provider services, provenance), and after stage 2 (dependents that adapt instead of restarting). Amended 2026-10-14 by the owner-approved [kernel alignment brief](../../docs/briefs/2026-10-kernel-cordis.md) ([Cordis alignment research](../research/cordis-alignment/README.md), divergences D1–D12): one provider per service, swap is restart plus restore, declared service use, ties by configuration order, commands owned by their plugin, named registrations replace, the session owner; adapting dependents and handover are removed. The amendments are marked *2026-10-14*; the section "Divergences from Cordis" records what Tuna keeps differently and why.

## Context

Emacs extensibility is a set of unrelated mechanisms: symbol cells, advice, hooks, registries and alists, and best-effort `unload-feature` ([research](../research/live-extensibility-racket/research/emacs-extension-architecture.md)). Nothing owns a package's contributions, so disabling or reloading a package rarely restores the prior state.

Cordis ([source](https://github.com/cordiverse/cordis), [paper](https://arxiv.org/abs/2608.25512)) structures a program as plugins that receive a context. Every effect registered through that context carries its inverse (temporal composability), and plugins declare the services they depend on, activating and deactivating as those services come and go (spatial composability).

The owner requires that as much as possible be user-replaceable, including the text data structure behind buffers.

## Decision

- **Plugin.** A plugin is a named unit with an activation procedure that receives a context. Tuna's own features (basic editing, minibuffer, files, windows, the HTML renderer) are plugins with no privileged access; the kernel and the tiers of replaceability are defined in [ADR 12](0012-kernel-boundary-and-replaceability.md).
- **Context and receipt.** Every contribution goes through the context: commands, key bindings, hooks, advice, settings values, services, renderers, jobs, tasks, timers, subprocesses, persisted-state slots (kept by the session service; [ADR 5](0005-persistence.md)). The context records an inverse for each in the plugin's **receipt**. Deactivating a plugin runs the receipt's inverses in reverse order. Contributions made outside a context are the package's own responsibility.
- **Owner-tagged effects.** Slot-like effects (a key binding, a setting value, an advice entry, a service provider) are stored as entries tagged with their owning plugin and a priority; the effective value is the highest-priority live entry. *2026-10-14:* equal priorities go to the plugin declared later in `init.ss` (start-up supplies each declaration's position), never to whichever registered last, so a reload ends where a fresh start would; an owner keeps one entry per name, so registering the same name again replaces its entry instead of adding one (as rebinding a key does in Emacs). An inverse removes only its owner's entry, so deactivation order between plugins never matters. This also lets help commands show who set what.
- **Provenance.** Every registration records its plugin, source location, and documentation, so `describe-key`, `describe-function`, jump-to-definition, and `where-is` work uniformly.
- **Manifest.** Declarative forms also produce a static manifest per plugin (commands with documentation, key bindings, file patterns, required services) at build or install time. Inactive plugins can therefore appear in `M-x` and help; invoking a stub activates its plugin first (Emacs autoload).
- **Dependencies.** Plugins declare required plugins and services; configuration that depends on another plugin attaches to it and is reverted when it deactivates (replaces `with-eval-after-load`).
- **Services.** A service is a named slot holding an implementation of a `std/interface` interface (for example `TextStore` or `Renderer`). Plugins declare the services they require. ~~When a provider is replaced, each dependent either restarts or adapts (migrates its own state in place).~~ *Superseded 2026-10-14:* a service has **one provider**. A plugin declares the services it fills (`provides:`), the services it needs (`requires:`) and the services it uses only when present (`optional:`); configuration rejects two declared providers of one service, naming both, and the kernel refuses a second `context-provide!`. ~~Using a service the plugin did not declare is an error naming the plugin and the service (checked on every call).~~ *Superseded later on 2026-10-14 (independent review, `agents/research/code-review-2026-10-14.md`):* Tuna checks declarations **when a plugin is turned on**, by any route (start-up, `reload-config`, `tuna check`, a swap, evaluated code): a plugin whose package imports a contract must declare that contract's service, or it is refused with a report line naming plugin, contract and service. The user's own code is exempt. There is no per-call check; the ambient "which plugin is calling" tracking it needed had to be re-set by hand at every thread and callback boundary and crashed correct code twice. Replacing a provider **restarts** everything that requires it, and state survives only through session slots ([ADR 5](0005-persistence.md)): start-up code captures the slots of every plugin that will turn off, turns them off, turns the new provider and its dependents on, and restores, each plugin from its own slot when it has one and otherwise from the contract's neutral slot; a failure turns the old versions back on. Swap, reload and restart all use this one path, which lives in start-up code, not the kernel, and plugins reach it through the configuration contract. In-memory state not held in a slot (undo history, for example) is lost, which the owner accepted. The dependency is visible in `describe-services`. Some services dispatch among several implementations by key: one plugin owns the file-system or process service and chooses a registered backend by path, so remote files can be added later without touching their callers ([ADR 5](0005-persistence.md)).
- **Reload.** Reloading a package means: save its session slots, deactivate its plugins, reload its modules, activate them again, restore the slots. State not held in a slot does not survive reload. Fine-grained redefinition through `set!` remains available ([ADR 1](0001-language-and-extension-surface.md)).
- **Hooks and advice.** Hooks are named, ordered (depth, then registration order) lists of named callbacks. *2026-10-14:* registering a callback name again for the same owner replaces it in place, as Emacs `add-hook` does not add a function already present; a callback given as a named function calls the function's current definition, so redefining it takes effect without registering again. An erroring callback is disabled individually and reported, not the whole hook. Advice is described in [ADR 1](0001-language-and-extension-surface.md). Both are registered through contexts.
- **Configuration.** `init.ss` is itself a plugin, which is activated last; editing and re-evaluating it reverts its previous contributions first. ~~Code evaluated interactively from a plugin's source buffer registers into that plugin; code evaluated elsewhere registers into a user-visible "eval" plugin.~~ *Superseded 2026-10-14:* interactive evaluation works as in Emacs: it evaluates into the live session, effects stay until changed, and nothing is tracked per buffer. Everything it adds belongs to one always-on **session owner** (the start-up code's own plugin, `session-owner`), which `reload-config` never touches; its entries take the latest declaration order, so they win equal-priority ties with the configuration. `evaluate-form` and `evaluate-forms` in the configuration contract evaluate in a persistent top-level environment that imports `:tuna/config`, as `init.ss` does. `reload-config` is not `eval-buffer`: it replaces the configuration's plugins and code with the new version.
  - *Amendment (2026-10-12, configuration stage 1; brief `docs/briefs/2026-10-configuration.md`).* `init.ss` is written in `#lang :tuna/config`. Loading it only collects `use-plugin` declarations; the rest of its code becomes the body of the plugin `init`. Tuna turns the declared plugins on afterwards, each separately: a failure is undone and reported, plugins that need it are skipped, and the rest come up. A `(use-plugin p config: ...)` block is a plugin of its own that is on while `p` is on. Definitions in `init.ss` are local to `init`; helpers shared with blocks go in a module imported by a path relative to `init.ss`. Imported modules' bodies and macro code run at load and must not change the editor. These are divergences from Emacs, where `init.el` takes effect form by form, stops at the first error, and defines globals (`docs/emacs-equivalents.md`).
  - *Amendment (2026-10-13, configuration stage 2).* Reloading `init.ss` (`reload-config` inside Tuna, `tuna reload` from a terminal) loads it again as a trial; a file that does not load changes nothing. Otherwise only the difference is applied, by plugin name: a plugin no longer declared is turned off, a new one on, one whose value is a different object (its module, a user module imported by path, was read again because its file changed) is replaced; `config:` blocks and the user's code are replaced when their code as written changed or a user module was read again. A replacement that fails is undone and the running version, still in memory, is turned back on; Tuna keeps no copy on disk. This guarantee holds for `init.ss`, its blocks, the user's code, and plugins from compiled modules. It does not hold for a user module imported by path: Gerbil names a source module's definitions after its file, and offers no supported way to load a new version under another namespace without rewriting the file, so a changed module is evaluated again in place and its definitions replace the running version's as soon as it loads, even when the reload then fails (`tuna/reload-test.ss` pins this). Loading each generation under its own namespace would need a copy on disk or expander internals; it belongs with the later work on reloading plugin code. While the editor loop runs, a change that would remove or take over a startup-tier service is reported as taking effect at the next start. Tuna's own compiled plugin modules are never reloaded. Emacs has no equivalent: `load-file` on `init.el` re-runs every form on top of what is already there, so removed settings stay and a failure leaves half the file applied (`docs/emacs-equivalents.md`).
- **Trust.** Plugins are trusted in-process code with the user's privileges. There is no sandbox. See [ADR 10](0010-security-clients-and-trust.md) for who may reach them.

## Function advice (amendment, 2026-10-15)

The approved hooks-and-advice brief adds owned composition in `tuna/lib/advice.ss`, not the kernel. `advise!` accepts an imported open function or `(function module name)` for a private one; `unadvise!` removes that owner's named contribution. Function advice changes the shared module definition, as Emacs's `advice-add` does; owner cleanup is not per-editor function isolation. Evidence: `agents/research/hooks-advice/advice-scope.md`.

The cell separates latest base, installed advice records and effective procedure. Adding/removing advice or redefining the base recomposes the chain; removing the final advice reveals the newest base. Lower depth is outermost, then earlier configuration declaration, then advice name within one owner. Startup refreshes cached chains after its declaration-rank batch, so retained plugins can be reordered without restarting. Inspection returns the installed order. Each owner/target uses one entry and one recomposition inverse; repeated replacement adds no inverse. Explicit removal releases callbacks; the two callback-free receipt notes remain until deactivation.

Callbacks run with their registering context; an around-advice's original function restores the caller's registration context without changing task ownership. Callback failures name the advice and owner; original-function failures and quits retain their identity. `after` runs only after normal return, not on unwinding. Before/after preserve original multiple values; `filter-return` receives all original values as arguments and may return any number. Conditional predicate positions require exactly one value and only `#f` is false. The ordinary `advice-help` plugin implements `describe-advice` using public commands/completion/help contracts, with no kernel additions. Command/service targets are subsequent parts of the same approved effort.

## Consequences

- Disabling, reloading, and replacing packages become routine operations, not best-effort cleanup.
- Every core API that creates a long-lived effect must be context-aware. This is the main tax on core authors and must stay small.
- ~~Replacing a service while state exists requires a migration path through the interface.~~ *2026-10-14:* replacing a service while state exists restarts its dependents and restores them from session slots; the layout and buffers contracts define neutral saved forms so a different provider can restore another's data.
- The architecture skeleton validates this: activating, deactivating and reactivating a plugin must leave no stray commands, keys, hooks, timers, or jobs, and overlapping key bindings from two plugins must survive either deactivation order.

## Divergences from Cordis (2026-10-14)

Each kept difference from Cordis (paper arXiv 2608.25512 v1, source `a71c658`), with its reason; numbers refer to the [Cordis alignment research](../research/cordis-alignment/README.md).
- **D3, startup-only services.** Cordis can retire any fiber. Tuna labels a few services (key resolution, settings lookup, the persistence format, the client transport; [ADR 12](0012-kernel-boundary-and-replaceability.md)) `startup`: replacing them mid-command would invalidate running tasks. It is reload policy in start-up code, not a kernel rule: a change touching one is deferred to the next start.
- **D4, the editor thread and `C-g`.** Cordis transitions are asynchronous and abort only between steps. An Emacs-style editor needs direct-style commands that pause at `read-string` and a quit key that interrupts running code ([ADR 3](0003-command-loop-and-jobs.md)). A command's task now belongs to the plugin that defined the command and is cancelled with it, which restores Cordis's "turning off undoes everything" for running commands.
- **D5, hooks in the kernel.** Owner decision; Cordis puts events in its core too. Hooks are ordered chains, which are not order-independent the way entry tables are (paper p. 29): callbacks of equal depth run in registration order, so a reload can reorder them. Callbacks that care declare a depth, as in Emacs.
- **D8, receipts.** A receipt is Cordis's accumulator of inverses under another name.
- **D9, contracts checked when a plugin provides.** Cordis checks only the service name and relies on TypeScript types. Tuna checks the provider against the contract's Gerbil interface (method names, not arity) when it provides; an improvement, kept.
- **D10, reload applies the difference.** Sound once one provider per service, declared use and configuration-fixed ties hold (Cordis Thm. 80).
- **D11, teardown by activation time.** Turning plugins off in reverse activation order is equivalent to Cordis's guard plus committed view.
- **D12, Messages called by the kernel.** The kernel must report failures before any plugin is on; it calls the Messages service when one exists and otherwise prints to stderr. Like Cordis's built-in logger, `message` needs no declaration.
- **Saved data outlives the plugin.** In Cordis, state dies with its fiber unless a longer-lived dependency holds it. Tuna's session store keeps a turned-off plugin's slots, which is what lets a swap restore them.
- **The user's code is unchecked.** As Cordis's root context, `init.ss`, `config:` blocks and the session owner may use and provide any service; the one-provider rule still applies to them.
- **Declarations checked at load, not per call (2026-10-14).** Cordis checks every access (§5.1.4). Tuna checks a plugin's imports against its declarations once, when it is turned on, because Tuna's Emacs-style global dispatchers (`(insert "x")`) cannot know their caller without ambient tracking, which proved fragile. What restarts need (an honest `requires:`) is decided by imports; use reached through another contract is covered by the transitive restart closure. Lost: checks of service objects obtained at run time without importing their contract. Plugins shipped without source are refused, since the check reads source.

## Alternatives considered

- **Emacs model (global mutable registries plus `unload-feature`).** Rejected: no reliable reversal.
- **Restore-previous-value inverses.** Rejected: incorrect when two plugins set the same slot.
- **Redefinition only (macros or `set!`).** Rejected as the primary mechanism: it cannot express "remove everything this package added".
- **Out-of-process plugins.** Rejected as the default: latency and API friction. Long-running external work still runs in subprocesses ([ADR 3](0003-command-loop-and-jobs.md)).
