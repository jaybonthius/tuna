## Bottom line

- **Fact:** the web-specific coupling has gone: web declares `--port` itself and logs its own URL (`tuna/plugins/web.ss:445–450`); main parses program commands and uses generic configured flags (`tuna/main.ss:85–95`, `tuna/boot.ss:58–105`). But **main still names 21 other plugins** in empty `only-in` imports (`tuna/main.ss:20–44`). “Main names no plugin” is not yet true.
- **Fact:** the remaining nontrivial package back-edges are keys → layout (`tuna/plugins/keys.ss:20`), Tuna → session (`tuna/boot.ss:26`, `tuna/main.ss:18`), and Tuna → commands/keys/settings through the package/config language (`tuna/prelude.ss:10–12`, `tuna/config.ss:33–36`), plus main’s command lookup (`tuna/main.ss:133`). Moving directories alone cannot satisfy the agreed direction.
- **Inference:** no separate package for every contract is required by the stated owner direction. A concept package can contain `contract.ss` and its default `plugin.ss`; a replacement imports only `…/contract`, although its package dependency includes the default’s package. This does **not** import the implementation module.
- **Fact:** ADR 2 and ADR 12 now specify one provider, static `provides:`, checked required/optional use, restart plus session restore, and the always-on configuration/evaluation owner. The parked brief/research still discuss handover, a web flag decision and central contracts; those are historical, not the current direction (`agents/adr/0002-plugins-contexts-and-services.md:3,21–26`; `agents/adr/0012-kernel-boundary-and-replaceability.md:59–75`; `agents/STATUS.md`, owner decisions “Repository and package layout”, “Get the foundations right now”, “Plugins own their command-line flags”).

### Exactly what keys asks today

**Fact:** `keys-plugin` provides input, requires commands, and declares `optional: [settings-service buffers-service layout-service]` (`tuna/plugins/keys.ss:362–373`). Optional services do not gate activation or restart dependents (ADR 12 amendment; only `requires:` does).

- Keyboard focus: when buffers exists, get `selected-view`; choose its `view-node`, else its buffer root (`tuna/plugins/keys.ss:143–147`).
- Click focus: when layout exists, call `posn-node`; otherwise/failing that, call `posn-view` and take its buffer root (`tuna/plugins/keys.ss:149–155`). Layout finds a view by `posn-part` in `view-list`, then searches that view’s buffer tree for `posn-node-id` (`tuna/services/layout.ss:257–273`). It does not select a view or mutate layout. Missing node with a surviving view falls back to root; missing view gives no node maps, not an unconditional rejection of the click.
- Climb `node-parent`, collecting `node-keymap` from the starting node upward; append only the innermost input target’s map, then global map (`tuna/plugins/keys.ss:134–165`). For clicks, try the pending prefix plus area/event-name variants in each map before the next (`tuna/plugins/keys.ss:252–278`). `where-is` uses the same focus stack (`tuna/plugins/keys.ss:304–319`). Settings are only the two Option-key policies (`tuna/plugins/keys.ss:51–76`).

**Inference:** a minimal inversion registers `(posn -> Maybe node)` from layout through keys, retaining the existing buffers-based parent walk and keyboard focus path. Layout’s callback performs today’s `posn-node`/`posn-view`/root fallback. Its context owns and removes the registration; run it with `context-bind` so layout’s service calls use **layout’s declared services**, not keys’ declarations. Layout already requires input, so replacing input restarts and re-registers layout. No registration means today’s no-layout fallback. Remove keys’ optional layout declaration; keep optional buffers/settings. This changes no client payload, click precedence, focus selection, or revision policy. Keys’ contract still imports buffers for the typed `where-is` argument (`tuna/services/keys.ss:39,154–178`). Eliminating that edge as well would require a second inversion (focus/keymap-stack API), which is not necessary to break a cycle.

### A cycle to avoid when assigning shared seams

**Inference:** splitting `CompletionUI` into the vertical-list package would create **completion ↔ completion-vertical**: the engine imports `CompletionUI`/its service, while UI imports `CompletionSession` and requires completion (`tuna/plugins/completion-engine.ss:8`; `tuna/services/completion.ss:29–62`; `tuna/plugins/completion-vertical.ss:8` and its `defplugin`). Keep that extension-point contract with the completion concept that calls it, or co-locate all completion plugins. Its default provider is vertical, but its vocabulary is introduced by the engine’s completion session.

## 7. Risks / genuinely unresolved points

- **Inference — owner placement question:** Tuna’s plugin-free `#lang :tuna/config` cannot continue implicitly importing editor forms from commands/keys/settings while those are independent concept packages. Options: explicit contract imports in configuration plus explicit `evaluate-form` imports into the live environment; or an opt-in editor-language package and generic bootstrap registration. Current evaluation tests expect `keymap-set`/`defcommand` without those imports (`tuna/integration/session-evaluation-test.ss:47,66–80`). Preserve their live accumulating effects/ownership, not necessarily an unapproved implicit-language dependency. No choice was implemented here.
- **Inference — literal boundary question:** the embedded starter is plugin-naming data compiled into boot, even though it activates nothing implicitly (`boot.ss:1433–1435`). Decide whether “Tuna knows no plugin” excludes that data or requires a separate installed template/distribution entry point. Existing owner-approved `tuna init` behavior must remain deliberate, not silently disappear.
- **Inference — ownership choices:** completion UI’s engine-owned extension point versus packaging all selectable completion pieces together; algorithm-neutral `text-store`/`renderer` package names versus current default implementation names; HTML-specific Renderer promise versus future transport-neutral ambitions (§4). These are named options/evidence, not recommendations to change product behavior.
- **Fact / Inference:** package loops and activation loops differ. Engine’s optional UI + vertical’s required engine is intentional (`completion-engine.ss`, `completion-vertical.ss`, their defplugin forms). Do not turn optional edges into required ones merely to order builds; only required dependents restart. Registration callbacks must execute under their owning context and have receipt inverses; no default-only access.
- **Inference:** lifecycle inversion needs explicit error/order tests: initial restore once after all slot owners; snapshot failure before teardown; successful and failed swap/reload restoration; save before deactivation; failed plugin and empty-config cases; summary notification after report finalization; second interrupt bypass. The existing session restart/evaluation/integration suites are behavior evidence to preserve, not authorization for storage in kernel.
