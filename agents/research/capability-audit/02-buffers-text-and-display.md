# Lane 2: Buffers, text model, and display

Scope: ADR 4 (state ownership), ADR 6 (buffer = node tree + `TextStore`), ADR 7 (rendering), plus the ADR 3 pieces that touch them (change hooks, jobs). Method: read ADRs 1–7, `docs/overview.md`, owner notes (`layout.org`, `window-layout-topology.org`), the old `buffer-model-spec.md`; checked Emacs mechanisms in `/home/jay/Code/emacs` (541f693) and the Elisp manual. Not run: no prototype code exists, so every "Tuna today" statement is about ADR text only. Cited Emacs facts are `file:line` or manual node. Items marked *(inference)* are mine.

**Shallow areas:** treesit internals, bidi/glyphless/display tables (rows are present but only reasoned from manual headings, not source), pixel-scroll-precision, tab-bar/tab-line, font-lock keyword semantics. Everything else was reasoned from the manual nodes listed in Sources plus source spot-checks.

## Summary

1. **CR-1 Per-window point / views (ADR 6 "Focus": "A buffer's focus is a node plus … a point").** Emacs keeps a separate point and start per window (`struct window` has `pointm`, `start` markers, `src/window.h:160-171`); the buffer's own point is authoritative only for the selected window's buffer. Same buffer in two windows = two cursors, two scroll positions. ADR 6 puts one point on the buffer. Fix: buffer keeps a default point (for `current-buffer`), windows own a per-window *view* (point, start, hscroll, narrowing-independent). Must be settled before the window code is written.
2. **CR-2 Propertized strings are a missing type.** Emacs strings carry text properties (`buffer-substring`, kill ring, `propertize`, `concat`, `format`, `insert`, completion candidates, mode-line strings, `message`). ADRs put properties inside a *text node* only (ADR 6 "A text node holds a `TextStore` value plus text properties"). Without a "styled text" value that `insert`/`buffer-substring` exchange, copy/paste, completion UI, mode lines and most packages cannot carry faces/`help-echo`/`keymap`.
3. **CR-3 Server cannot know layout (ADR 7 "browser holds no editor state", "Scrolling is a server command", viewport slicing by lines).** Wrapping, proportional fonts, images, variable line heights, percent-sized windows (owner layout notes) are decided by the browser. Server-side `window-end`, `pos-visible-in-window-p`, `recenter`, `scroll-up`, `next-line` goal column, `vertical-motion`, `move-to-window-line`, `window-body-height`, `posn-at-point` need metrics. ADR 7 needs an explicit client→server *measurement/viewport report* channel and a layout-metrics contract, otherwise screen-relative commands cannot be written.
4. **CR-4 Dynamic binding of settings (ADR 4 last bullet: "implemented as ordinary data in owning objects, not as dynamic variables").** Core Emacs idioms are `(let ((case-fold-search nil) (inhibit-read-only t) (inhibit-modification-hooks t)) …)` and `with-current-buffer`. ADR 3 also allows several suspended command threads, so `current-buffer` must be per-command-thread. Need a thread-local (Gambit parameter) *dynamic layer* above node/buffer/mode/global resolution.
5. **CR-5 Share text between buffers (indirect buffers, multi-view).** ADR 6 says a buffer "owns" its node tree; the old spec explicitly excludes "indirect buffers, independent views" (`buffer-model-spec.md:28`). `clone-indirect-buffer`, outline/narrowed-subtree workflows, and "same file in two windows with different narrowing/overlays" need a shared *text object* distinct from the buffer. Emacs shares text+props, separates point/narrowing/markers/overlays/locals (`src/buffer.c:894` shares the undo list too).
6. **CR-6 Positions across a node tree (ADR 6 "Coordinates: zero-based code-point offsets"; "Markers are buffer-owned positions").** Whose offsets, if a buffer has many text nodes? Single-text-node case is fine; undefined otherwise. Without a rule, `(point)`/`goto-char`/markers/overlays/`save-excursion` for rich buffers will be ambiguous. Fix: positions are *per text node*; a buffer designates a primary text node used by all Emacs-style API; `(node, offset)` pairs elsewhere.
7. **Job rejection by whole-buffer revision (ADR 3/4) starves highlighting under continuous typing.** Better: carry the change log since the snapshot revision and rebase results (this is a divergence that also makes jit-lock cheaper).
8. **Best opportunities:** persistent text gives native undo *tree*/redo and free version history (no undo-tree package); browser rendering gives real images, SVG, proportional text, per-window pixel layout, child frames as overlays/popovers, rich mode lines as node trees; a *view* layer gives per-client cursors for free.
9. Display/`invisible`/`display`/overlays/faces fit ADR 7's span-based SXML renderer; they need an explicit "effective properties at position" pipeline (merge text props + overlays + priority + remapping) that ADRs do not name — *later*, not blocked.
10. Zero-based offsets (ADR 6) are a deliberate divergence from Emacs's 1-based positions: cheap now, costs mechanical-port friction for literal `1`/`(point-min)` constants.

## How the node-tree model maps onto Emacs semantics (assessment)

**Can a node-tree buffer express text properties/overlays/invisible/display?** Yes, for a text node, trivially: a text node is the Emacs buffer minus its identity: text + intervals + markers + overlays + narrowing. All of §C/§D live there. What the ADRs leave unspecified (and must be decided before code):

1. *Where properties live*: inside the persistent version value (so `snapshot` = text + props, rope nodes can cache run-lengths for lookups; jobs and undo see a consistent pair) vs a side structure. Recommendation *(inference)*: one persistent "styled rope", properties as a persistent interval map keyed by position, sharing the same revision; text-only vs prop-only edits bump separate ticks (#8).
2. *Overlays/markers*: mutable per-buffer-view objects (not persistent) that relocate through change records on the editor thread; this agrees with ADR 4 (mutable objects, baton) and ADR 6 (markers buffer-owned).
3. *What is the render input*: a "run list" for the visible range: `(offset, text, effective-properties)` computed by `effective-property-at` over text props + overlays + priority + face remapping + region/cursor decorations. The renderer service (ADR 7) consumes the run list. This must be specified as the contract between buffer layer and renderer; ADR 7 says only "text nodes render only the lines visible in their window".
4. *Invisible and display*: require a server-side logical→display mapping for motion (invisible skipping, `line-move`), so they must be resolved on the server, not by CSS-only hiding. HTML is expressive enough to show them.

**Per-window point and views.** The current text ("focus belongs to the buffer") cannot represent two cursors in one buffer. Emacs's own answer, which works: the buffer has one point (used when it is current), each window has `pointm`; on `set-buffer`+`select-window` they sync (`window.c`, `window.h:160-171`; manual *Window Point*). Tuna should name a **view** object explicitly:

```
Text (store version + props + change log + undo)   [shared by indirect buffers]
  └─ Buffer (name, locals, modes, markers, overlays, narrowing, mark, default point)
       └─ View (per window: point, start, hscroll, per-node focus/collapse state, window-specific overlays/decorations, display settings like line-numbers)
```

For ordinary plain editing, `Text`, `Buffer` and `View` have 1:1:1 fan-out and cost nothing. This keeps ADR 6's "single text node behaves like Emacs" promise honest.

## Corner risks

### CR-1: Point/focus belongs to the buffer (ADR 6 "Focus")
- **Sentence:** "A buffer's focus is a node plus, for a text node, a point."
- **Scenario:** `C-x 3` splits into two windows on `foo.ss`. User moves to line 400 in the right window and edits line 10 in the left. In Emacs both windows keep their own point and start; after an edit above, each window's point marker shifts. With a single buffer point, either both windows show the same cursor (and scrolling is shared) or the non-selected window's point is lost at every `select-window`. `display-buffer` reusing a window for compilation output, `next-error`, `follow-mode`, `compare-windows`, `window-configuration` restore, and diffs side by side all assume per-window points.
- **Smallest change:** amend ADR 6: "Point and scroll position of a *displayed* buffer belong to the window's view; the buffer keeps a default point used when no view is current. `(point)` in code returns the current buffer's point, synced from/to the selected window's view per Emacs's rules." Plus: node focus/collapse state is view state.

### CR-2: No propertized-string value
- **Sentence:** ADR 6 "A text node holds a `TextStore` value plus text properties." (properties are confined to node storage). `TextStore`'s "slicing" is silent about properties.
- **Scenario:** `kill-region` over a fontified/linked area then `yank` into another buffer must carry `face`, `keymap`, `help-echo`, `invisible` (Emacs filters some via `yank-excluded-properties`); completion candidates need faces; `message` with `(propertize … 'face 'error)`; mode-line `:propertize`; `format` with properties. Gerbil strings have none.
- **Smallest change:** ADR 6: "`TextStore` slices and `insert` operate on *styled text*: a string plus a property interval map; `buffer-substring-no-properties` returns a plain string." Make styled text the type used by kill ring, minibuffer, echo area, mode-line.

### CR-3: Layout is decided by the browser, but commands need it
- **Sentences:** ADR 7 "The browser holds no editor state", "Text nodes render only the lines visible in their window, plus a small margin. Scrolling is a server command for now." and owner layout notes (percent-sized windows).
- **Scenario:** `C-v` (scroll-up-command) must scroll by "window height − next-screen-context-lines" screen lines; with wrapped lines or images the server doesn't know how many text lines fit. `C-n` in a wrapped line (visual motion), `recenter`, `M-r` (`move-to-window-line`), isearch keeping the match visible, `corfu`/`company` placing a popup at point, `pos-visible-in-window-p`, `window-end`, `window-body-height` all fail or return guessed values. Percent-sized windows plus scroll tiling cannot report body height in rows.
- **Smallest change:** ADR 7: "The client reports *metrics* (viewport size, cell size for the window's monospace grid, optional per-line wrap counts or block heights for the rendered slice) as events; the server keeps them as read-only window attributes (`window-body-height`, `window-body-width`, etc.). Layout-dependent commands read these. The default text layout is a monospace grid so columns and rows are computable on the server; proportional or wrapped text uses reported metrics (document accuracy limits)." Also allow a command to *yield for a render+measure* when it needs fresh measurement.

### CR-4: Scoped values "not as dynamic variables"
- **Sentence:** ADR 4 last bullet.
- **Scenario:** Emacs code does `(let ((case-fold-search nil)) (re-search-forward re nil t))`, `(let ((inhibit-modification-hooks t)) …)`, `(let ((inhibit-read-only t)) (insert …))`, `(let ((deactivate-mark nil)) …)`, `(save-match-data …)`, `(with-current-buffer b …)`. Without dynamic binding a port turns into set/restore pairs with `dynamic-wind`, and **suspended commands** (ADR 3) would clobber each other's `current-buffer`/match data since several threads live at once.
- **Smallest change:** ADR 4: "Resolution order is dynamic binding (per command thread, Gambit parameters, set by `with-setting`/`parameterize`) → node → buffer → mode → global. `current-buffer`, match data, and `inhibit-*` flags live in the dynamic layer." Also add *view/window/frame* scopes to the chain (see CR-7).

### CR-5: Buffers own their tree; no shared text
- **Sentence:** ADR 6 "A buffer is a named object owning a tree of nodes, a revision, undo history…"; old spec: "Do not introduce indirect buffers, independent views" (`buffer-model-spec.md:28`).
- **Scenario:** `clone-indirect-buffer` for narrowing to one function while seeing the whole file; org `org-tree-to-indirect-buffer`; two windows with different overlays or narrowing on the same file. Edits in one must appear in the other with marker relocation in both.
- **Smallest change:** ADR 6: "A text node's content (store version, properties, change log, undo list) is a separate shared object (`text`) that one or more buffers may reference; markers, overlays, narrowing, locals, mark belong to the buffer." This costs nothing for single-owner buffers.

### CR-6: Position space in a multi-node buffer
- **Sentence:** ADR 6 "Public positions are zero-based Unicode code-point offsets"; "Markers are buffer-owned positions relocated by each edit's change record".
- **Scenario:** A magit-status buffer has 40 text nodes (commit subjects). A package does `(goto-char (point-min))` / `(search-forward "Staged")` / `(point-marker)`: which offsets? If offsets are node-local, a marker without a node id is ambiguous; if buffer-global, every edit in one node shifts all later nodes' offsets (and ADR 6 defers linearization).
- **Smallest change:** ADR 6: "A position is `(text-node, offset)`; the buffer designates a *primary* text node that all one-argument Emacs-style APIs (`point`, `goto-char`, `insert`, `point-min`) address; other nodes are reached through `with-node`." This keeps flat-buffer ports mechanical and makes later linearization additive.

### CR-7 (minor): Scope chain lacks window/frame/view
- **Sentence:** ADR 4 "node, buffer, mode, global".
- **Scenario:** `display-line-numbers`, `cursor-type`, `truncate-lines` per window (Emacs: `set-window-…` / window parameters / `window-` local settings), text scale per window, frame-local `default-directory`-style values.
- **Smallest change:** extend the chain to `dynamic → view/window → node → buffer → mode → frame → global`; exact order is an implementation detail.

### CR-8 (minor): Jobs and "revision current" check
- **Sentence:** ADR 3 "applied … only if the revisions it was computed from are still current; otherwise it is discarded or restarted."
- **Scenario:** 5 MB file, user types at 10 chars/s, highlighting job takes 300 ms: *every* result is stale; highlighting never appears.
- **Smallest change:** allow results to declare a *position-mapped* application: if the buffer's change log since the snapshot revision is retained, the editor thread maps result ranges through it and drops only ranges touched by the intervening edits.

### CR-9 (minor): `(redisplay)` / render-now
- **Sentence:** ADR 3 "After a command completes or suspends, the loop marks the frame dirty."
- **Scenario:** a long command with progress display or `sit-for`-based animations, or any command that needs the screen to be current before measuring (`pos-visible-in-window-p` after `(redisplay)`).
- **Smallest change:** specify `(redisplay)` as an explicit yield point: render coalesced frame now, then resume (CR-3 pairs with this).

## Proposed divergences (improvements over Emacs)

**D1. View object separate from window and buffer (see CR-1).** Emacs: window holds point/start markers, buffer holds one point. Tuna: explicit `View` (per window) with point(s), start, hscroll, per-node focus/collapse, window-specific decorations and display settings (line numbers, cursor type). *Better:* per-client/per-window state is uniform: window-specific overlays, cursors in non-selected windows, rich buffer views can differ. *Cost:* one more object; `window-point`/`set-window-point` map directly, `(point)` stays buffer-based. *Porting impact:* none for flat packages.

**D2. Native undo tree and history from persistent versions.** Emacs: linear `buffer-undo-list`; undo-tree/vundo rebuild trees by replaying. Tuna: keep (version, change) nodes in a tree; `undo-redo` is native; branching is not lost; timestamps and per-version snapshots are free (ADR 6). *Cost:* memory policy; `buffer-undo-list` must be exposed as a compatibility view; packages that push entries directly (e.g. `(push (cons beg end) buffer-undo-list)`, `primitive-undo` callers, `undo-amalgamate-change-group`) need an adapter. *Porting impact:* medium for undo-aware packages (undo-tree, vundo, `undo-fu`); low for others.

**D3. Highlighting results as rebased, droppable cache instead of authoritative text properties.** Emacs: font-lock writes `face` props into the buffer, jit-lock fontifies on display. Tuna: jobs return `(range, face)` runs for a revision; the editor thread rebases through the change log; the renderer overlays this cache under explicit text properties. *Better:* no undo noise, no `buffer-modified` side effect, no `with-silent-modifications`, no stale font-lock state on revert. *Cost:* `get-text-property pos 'face` no longer returns the font-lock face unless the compatibility function `font-lock-ensure` writes properties; packages reading `face` (e.g. `face-at-point`, `highlight-*`) go through `get-char-property`, which must consult the cache. Font-lock matchers that run arbitrary Lisp need the immutable-view API (#68).

**D4. Folding, sections and "invisible" as node attributes plus overlays.** Emacs: `invisible` text props + `buffer-invisibility-spec`; org/outline/magit toggling. Tuna: collapsible node + keep `invisible` property for compatibility. *Better:* structure is explicit, folding state is per view, accessibility (ARIA `expanded`) and navigation are well-defined. *Cost:* two mechanisms; `reveal-mode`-style auto-unfolding must handle both. *Porting:* flat Emacs packages unchanged.

**D5. Mode line / header / tab line as SXML node trees (plus classic format constructs).** Emacs: `mode-line-format` mini-language. Tuna: accept both; `%b`-style constructs translate to SXML nodes. *Better:* real layout, icons, clickable regions without `local-map` props. *Cost:* two representations. *Porting impact:* none for packages that only set `mode-line-format`/`mode-line-misc-info`; packages that propertize strings with `keymap`, `help-echo` need CR-2 (styled text).

**D6. Zero-based code-point positions (ADR 6) vs Emacs's one-based.** *Better:* conventional with Scheme vectors/strings and rope slicing. *Cost:* literal `1` constants, `(1+ (point))` patterns, `goto-char 1`, `buffer-substring 1 n`, and any `point-min`/`point-max` inline assumptions need review. *Alternative (no divergence):* expose positions 1-based at the Emacs API layer (`point-min` = 1) while the store is zero-based internally. *(recommendation: decide before any port work; I lean toward keeping Emacs's numbering at the public API since porting accuracy matters more than purity. See OQ-1.)*

**D7. Multiple selections/cursors built into views.** Emacs: none in core; packages fake with overlays. Tuna: a view owns an ordered set of (point, mark) pairs; the primary one is `(point)`. *Cost:* every command must iterate; defaulting rule needed. *Porting:* none unless a package opts in.

**D8. Mark ring per view (optional).** Emacs: per buffer; two windows on one buffer share the mark. *Better:* per-view mark/region (so two windows can have independent regions). *Cost:* diverges from `mark-marker` identity; *recommendation:* keep per buffer for now, revisit with multi-cursor.

**D9. Popups anchored by CSS to a position/cursor span, not by pixel arithmetic.** Emacs packages (corfu, company-box, posframe) compute pixel positions with `posn-at-point`, `window-text-pixel-size`. Tuna: `show-popup` node anchored to a position/cursor span with placement rules the browser resolves. *Cost:* different API; ports of posframe-style code rewrite placement.

**D10. Client-side only-presentation effects.** Cursor blink, hover `mouse-face`, pixel-smooth scrolling, theme switching, text scale: no server round trip. *Cost:* the "browser holds no state" claim must exempt purely presentational state. *Porting:* none.

## Open questions for the owner

**OQ-1: Position numbering at the public API (0- or 1-based).** Context: ADR 6 says zero-based. Emacs is one-based, and packages contain literals. *Options:* (a) zero-based everywhere (clean; porting friction), (b) one-based at the public Emacs-shaped API with zero-based store internals, (c) zero-based but provide `1+` shims. *Recommendation:* (b) unless the owner doesn't plan to port packages, because ADR 1 promises "mechanical" ports and off-by-one bugs are silent.

**OQ-2: Is the default text layout a monospace grid per window?** Context: Emacs commands use columns/rows (`current-column`, `window-body-width`, `move-to-column`, `fill-column`, `truncate-lines`, `indent-to`). The browser can do proportional text and arbitrary widths; the owner's layout notes use percent sizes. *Options:* (a) monospace-grid default; server computes rows/cols from a metrics report; proportional/images are allowed through `display` but approximated; (b) free-form browser layout with measurements via reports. *Recommendation:* (a) for text nodes of file buffers (Emacs semantics, computable on server), (b) for rich node kinds.

**OQ-3: Per-tab cursor and selected window.** Context: ADR 7 says all tabs mirror one frame. Two people or two screens would fight over the single selected window and view. *Options:* mirrored (as ADR) with last-writer-wins; per-tab *view* state over shared text/windows; fully per-tab frames. *Recommendation:* keep mirrored for the prototype but make event records carry a client/tab id so per-tab views can be added.

**OQ-4: Text properties persisted by value?** Context: Emacs props can hold functions/keymaps; ADR 5 data files are plain data. *Options:* only data-valued props persist (faces, invisible, help-echo strings); functional props are rebuilt by modes. *Recommendation:* that.

**OQ-5: Font-lock semantics: authoritative text properties vs cache (D3).** Decide whether `face` property read-back from `get-text-property` must match Emacs, which decides how much existing font-lock code can port. *Recommendation:* cache plus `font-lock-ensure`/`get-char-property` consulting it.
