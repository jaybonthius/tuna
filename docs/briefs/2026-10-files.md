## What we're building and why

Open a file, edit it, save it: the thing that most stops Tuna from being used every day. One `files` plugin, the size of Emacs's file handling:

- **Open:** `C-x C-f` picks a file with the same completion as `M-x` (any-order matching), offering recent files and the current folder. A file opened under two names (a symlink) is still one text.
- **Save:** `C-x C-s`, `C-x s` (all), `C-x C-w` (save as). Never leaves a half-written file (see "How saving works").
- **Unsaved changes are visible:** the status line marks them; killing such a buffer, or quitting, asks first.
- **Other programs' changes:** if a file changes on disk and you have no unsaved changes, Tuna reloads it as one undoable change that keeps your cursor, marks and modes. If you do, the echo area says so, and saving asks: overwrite, or reload and discard yours (a diff view can come later). A deleted or renamed file is reported, not left silently stale.
- **Nothing lost:** unsaved changes are autosaved to Tuna's state folder, never beside your files, and come back after a crash.
- **Remembered places:** recent files and the cursor position in each.
- **Bytes kept exactly:** each file's encoding, byte-order mark, line endings and final newline are recorded when it is read and written back the same, so saving never changes lines you didn't touch.

Two facts shape the design:
- **The text visits the file, not the buffer.** A Tuna text can be shown in several buffers; the file belongs to the text, so every view agrees. Emacs's nearest precedent is the indirect buffer, which shares its base buffer's text and saves it.
- **All file access goes through a file service** whose provider is the local disk, so remote or compressed files can come later without touching every plugin, as Emacs's file-name handlers allow.

## How changes on disk are noticed

What every modern editor does (Zed, VS Code, Neovim's development branch):
- **Watch the folder, not the file.** Git and many editors save by writing a new file and renaming it over the old one; a watch on the old file dies, a watch on its folder doesn't. Linux's `inotify`, through Gerbil's `std/os/inotify`, on its own thread.
- **Absorb bursts:** one save produces several events; wait about 100 ms and handle the file once.
- **Fall back to polling** every couple of seconds where watching fails (network drives, the watch limit).
- **Re-check when the tab regains focus and before every save:** the watcher is a speed-up, the check is the truth.
- **Compare content, not only modification times,** before calling it a change: `touch` and a `git checkout` of identical content change the time but not the file (Emacs, VS Code and Kakoune all learned this).
- **Ignore our own saves:** record the new file state as part of saving.

## How saving works

1. Write a temporary file in the same folder, flush it to disk, copy permissions (and owner where allowed), rename it over the file, flush the folder.
2. **Write in place instead, after a backup copy,** when renaming would change the file's identity: it has hard links, or its owner can't be kept, or the folder isn't writable. (Neovim's rule; VS Code and Zed always write in place and can truncate the file on a crash.)
3. A symlink saves through to its target; the link stays a link.
4. `before-save-hook` (for example a formatter), a hook that can take over the save, and `after-save-hook`. An error in any of them is reported and logged, never silently swallowed.

## Encodings and binary files

- **Editable:** UTF-8, with or without a byte-order mark. Uniform Windows line endings (CRLF) are shown as plain lines and written back as CRLF; a file with mixed endings keeps its bytes exactly.
- **Read-only with a note in the echo area:** anything else (invalid UTF-8, UTF-16, other encodings) and binary files (detected from their first few kilobytes). Nothing is ever corrupted on save; VS Code and Helix can silently replace undecodable bytes.
- **No automatic encoding guessing:** a wrong guess changes bytes on save; VS Code ships its guesser off for that reason.
- **Later:** UTF-16 with a byte-order mark, declared encodings, and a lossless way to edit files with stray bytes (as Emacs does).

## A walkthrough

1. **Open.** `C-x C-f`, type `not`; `notes.txt` is near the top because you opened it yesterday. `RET` opens it, with the cursor where you left it.
2. **Edit.** You type; the status line shows `notes.txt *`.
3. **Another program edits it.** `git pull` changes `notes.txt`. You have unsaved changes, so Tuna does not reload; the echo area says "notes.txt changed on disk".
4. **Save.** `C-x C-s` asks: overwrite with yours, or reload theirs. You overwrite; Tuna writes a temporary file and renames it into place.
5. **Crash.** Later the machine loses power with unsaved edits. On the next start, the buffer comes back with them, marked unsaved.

## How it gets built

The `files` plugin and its contract. Its main parts, from the research's list of what packages rely on in Emacs:
- **the file service:** stat, read, write, replace atomically, list a folder, watch, true name;
- **a visit record on the text:** file name, true name, file identity, what was on disk at the last read or save, encoding, line endings, saved revision;
- **visiting:** one text per file, reusing existing views, with `find-file-hook` and a hand-off for modes chosen by file type;
- **saving:** the save commands and hooks above;
- **modification state:** unsaved or not, and a way to mark it saved;
- **staleness and reloading:** `revert`, which reloads by diff, with `before-revert-hook` and `after-revert-hook`;
- **`default-directory` per buffer,** and file-name helpers.

In four stages, each running in the browser:
1. **Open and save:** file service, visiting, `C-x C-f`, saving, the unsaved marker, asking before killing.
2. **Recent files and remembered places.**
3. **Changes on disk:** watching, re-checking, reloading by diff, the conflict question at save.
4. **Autosave for file buffers** and restoring them on start.

Before stage 1, check what Gerbil exposes: `inotify`'s overflow and folder events, flushing a folder, changing a file's owner. Nothing goes into the kernel.

**Not in this work:** remote and compressed files (only the seam), file locks, numbered backups, `dired`, projects and modes chosen by file type (tier 1), very large files beyond a confirmation above a size threshold.

## Decisions for you

None open. Decided by you: reload automatically when there are no unsaved changes; non-UTF-8 files open read-only for now. Two consequences to record as differences from Emacs: auto-reload is on by default (Emacs leaves `auto-revert-mode` off), and autosave files live in Tuna's state folder instead of `#file#` beside your files.

## New terms

- **Visiting:** a text is linked to a file; saving writes the text to it.
- **File service:** the replaceable layer all file reading, writing and watching goes through; today's provider is the local disk.
- **Reloading by diff:** replacing a text's contents by applying only the differences, so cursors, marks and undo survive.
