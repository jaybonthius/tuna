# Brief: files

**Date:** 2026-10-24. **Status:** proposed, awaiting the owner's approval. Tier 0 item 3 of the [roadmap](../roadmap.md). Evidence: ADR 5 (persistence: "file contents: the visited file, explicit save, files plugin"), the capability audit's files section (`agents/research/capability-audit/03-runtime-and-environment.md`, section K and CR-5), the current buffers contract and autosave plugin.

## What we're building and why

Open a file, edit it, save it: the thing that most stops Tuna from being used every day. One `files` plugin, the size of Emacs's file handling:

- **Open:** `C-x C-f` picks a file with the same completion as `M-x` (any-order matching), offering recent files and the current folder; opening a file that is already open shows its buffer.
- **Save:** `C-x C-s`, `C-x s` (all), `C-x C-w` (save as). Saving writes a temporary file and renames it over the old one, so a crash never leaves half a file; permissions are kept, and a symlink saves through to its target.
- **Unsaved changes are visible:** the status line marks a buffer with unsaved changes; killing such a buffer, or quitting, asks first.
- **Other programs' changes:** each open file is watched. If it changes on disk and you have no unsaved changes, Tuna reloads it, keeping the cursor; if you do, the echo area says so and saving asks before overwriting.
- **Nothing lost:** unsaved changes are autosaved to Tuna's state folder, as `*scratch*` already is, and come back after a crash or restart.
- **Remembered places:** recent files, and the cursor position in each file, are kept in the session.

Two facts shape the design:
- **The text visits the file, not the buffer.** In Tuna a text can be shown by text nodes in several buffers; the file belongs to the text, so every view of it agrees on what is saved. A file buffer is an ordinary buffer whose one text node shows that text.
- **File operations go through a file service** whose provider is the local disk. The capability audit (CR-5) warns that if plugins call the operating system directly, editing remote or compressed files later (as Emacs's TRAMP does) means touching every plugin. Naming the service now costs little; only the local provider is built.

## A walkthrough

1. **Open.** `C-x C-f`, type `not`; `notes.txt` is near the top because you opened it yesterday. `RET` opens it, with the cursor where you left it.
2. **Edit.** You type; the status line shows `notes.txt *`.
3. **Another program edits it.** `git pull` changes `notes.txt`. You have unsaved changes, so Tuna does not reload; the echo area says "notes.txt changed on disk".
4. **Save.** `C-x C-s` asks "notes.txt changed on disk; save anyway?". You answer; Tuna writes a temporary file and renames it into place.
5. **Crash.** Later the machine loses power with unsaved edits. On the next start, the buffer comes back with them, marked unsaved.

## A code sample (package author's view)

Format a file before it is saved, and react after:

```scheme
(context-add-hook! ctx before-save-hook 'format
  (lambda ((b : buffer)) (format-buffer! b)))
(context-add-hook! ctx after-save-hook 'notify
  (lambda ((b : buffer)) (message (string-append "Saved " (buffer-file b)))))
```

Names are illustrative.

## How it gets built

The `files` plugin with a `files` contract (the file service, `buffer-file`, `find-file`, save functions, `before-save-hook` and `after-save-hook`, `default-directory` per buffer), in stages that each run in the browser:

1. **Open and save:** the file service and local provider, visiting, `C-x C-f` with folder completion, saving atomically, the unsaved marker, asking before killing unsaved buffers.
2. **Recent files and remembered places:** session slots; recent files as a completion source.
3. **Other programs' changes:** a file watcher (Gerbil has `inotify` on Linux) as a background source; reload or warn.
4. **Autosave for file buffers:** extend the autosave plugin to unsaved file buffers; restore them on start.

Nothing goes into the kernel.

**Not in this work:** remote and compressed files (only the seam), file locking, numbered backups, `dired`, projects (tier 1), modes chosen by file type (with `modes`, tier 1), very large files beyond what the rope and drawing already handle.

## Decisions for you

1. **Reload changed files automatically when you have no unsaved changes?** Emacs leaves this off by default (`auto-revert-mode`). **Recommendation: on**, because the file on disk is the truth and git operations are frequent; a setting turns it off. A divergence to record.
2. **Files that aren't UTF-8.** Tuna's texts are Unicode; converting other encodings correctly is real work (CR-7). **Recommendation: open them read-only with a note in the echo area** for now, so nothing is silently corrupted on save; proper encodings later.

## New terms

- **Visiting:** a text is linked to a file; saving writes the text to it.
- **File service:** the replaceable layer all file reading, writing and watching goes through; today's provider is the local disk.
