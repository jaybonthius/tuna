# Plan: Pi chat (the `pi` plugin)

Brief (owner pre-approved 2026-10-28): [`docs/briefs/2026-10-pi-chat.md`](../../docs/briefs/2026-10-pi-chat.md). Research: [`agents/research/pi-chat/`](../research/pi-chat/) (`pilish.md`, `pi-rpc-and-helper.md`, `markdown.md`, `tuna-fit.md`). ADRs 6 (nodes), 7 (rendering), 12 (small kernel), 15 (scrolling), 17 (memo), 18 (helpers).

**Reference implementation: Pilish** (`~/.config/emacs/var/elpaca/sources/pilish`). Read how it does a behaviour before designing it; copy its decisions, not its Emacs workarounds (`pilish.md` §8 lists essential / defer / avoid).

## Invariants

- **Lean.** No framework without a second user; no tool overrides or Tuna extension inside Pi; no rewriting Pi's session files; no local follow-up queue (use `prompt` with `streamingBehavior`, `steer`, `clear_queue`, `queue_update`).
- **Placement.** `gerbil-md4c` (new workbench repository): md4c vendored + a C shim that returns events in one u8vector (no callbacks into Scheme) + a Scheme decoder to plain block records with source offsets. `plugins/markdown/`: contract `markdown-blocks` (text → blocks) and the node kinds, renderers, CSS and prompt styling for Markdown. `plugins/pi/`: the chat (contract, plugin, helper `tuna-pi-helper`, RPC client, menu). Shared process code (detach, private socket directory, peer check, frame/line reader) moves from `plugins/terminal/` into `tuna/lib/` (ADR 18's process library). Nothing in the kernel.
- **Contracts that grow:** buffers (`read-only` node attribute in `check-writable`), files (file completion table, `find-file-at-line`, file-reference finder moved from the terminal), program-status (report record moves here; reports keyed by buffer; notifications uses the buffer). Update every caller; no aliases.
- **Protocol rules (Pilish lessons).** Every request has an id and resolves, also on exit; idle = `agent_settled`; `prompt` disposition `handled` means no run; `message_end` and `tool_execution_*` args are authoritative over streamed previews; coalesce deltas and tool updates to one redraw per 50 ms, flushing before structural events; state first, drawing second; always answer extension dialogs (cancel on `C-g`, dismissal or `timeout`); show Pi's stderr once when it dies; minimum Pi 1.4.0 (`pi --version`).
- **Helper.** One per chat, Gerbil, plain JSONL over a private socket: a `hello` line, then Pi's lines verbatim; from Tuna, Pi commands verbatim plus `helper_*` control lines. Replay on connect per `pi-rpc-and-helper.md` §2 (snapshot by its own `get_state`/`get_messages`, then open items, sticky values, pending dialogs, then live). Idle exit after 60 s (option) with no Tuna, settled, no dialog. Session slot: `(id socket buffer-name session-file cwd draft)`; after a reboot, a new helper with `--session FILE`.
- **Drawing.** Proportional prose (`tokens.css`), monospace code. Transcript blocks are read-only text nodes (paragraph, heading, list item, quote, code) with highlight spans for inline styles; tables are one rich item. Tool blocks fold (preview 10 lines, bash 5, byte cap). The prompt is the last child, an editable text node styled live through a highlight layer from md4c offsets. Long chats: chunk messages if the profiler shows `set-node-children!` cost.
- **Testing.** A fake Pi (JSONL scripts) entered through the real start path (the `pi-command` option), so production has no test branches; a thin real-Pi smoke test is manual. Every process started is stopped by pid.
- Docs updated as each stage merges (overview, `docs/emacs-equivalents.md` rows for Pilish/transient concepts and divergences, roadmap, this plan, the brief's status).

## Stages

1. **Markdown.** `gerbil-md4c` (pinned md4c, shim, decoder, tests on GFM spec samples and a hostile-HTML corpus: `<script>`, `<img onerror>`, `javascript:` links, entities) and `plugins/markdown/` (blocks → nodes, inline spans, safe links, CSS, `markdown-style-text!` for a live prompt). Demo: a Markdown file shown rendered in `demo/`.

   **As built (2026-10-28).** `gerbil-md4c` (`/home/jay/Code/workbench-gerbil/gerbil-md4c`): md4c `f9e5eb232b95` vendored in `native/` and compiled into `private/ffi`; the shim `native/events.h` writes md4c's callbacks into one byte buffer that Scheme copies and decodes. `(markdown-parse string) => list` gives block records (`markdown-paragraph`, `-heading`, `-code-block`, `-quote`, `-list`, `-item`, `-table`, `-rule`) holding inline records (`markdown-text`, `-line-break`, `-span`, `-link`, `-image`) with character offsets (spans and links include their delimiters, blocks run line to next block); `MD_FLAG_NOHTML`, entities decoded, links that are not http/https/mailto (images: http/https) become their text. Tests: md4c's GFM spec samples (tables, task lists, strikethrough, permissive autolinks) through an HTML renderer, a hostile corpus (`<script>`, `<img onerror>`, raw HTML blocks, `javascript:`/`data:` however written or entity-encoded, 5,000-deep nesting, >1 MB input), offsets, every prefix of a streamed document. Tuna links it like gerbil-libghostty (`make deps`, `GERBIL_MD4C`); the static `tuna` exe gets `-I<md4c>/native` (`build.ss`).
   `plugins/markdown/`: contract `Markdown` with `(markdown-blocks source) => list`, `(markdown-update-blocks nodes source) => list`, `(markdown-style-text! text) => void`. Node kinds `markdown-paragraph`, `-heading` (`level`), `-code` (`language`), `-quote`, `-list`, `-item` (`marker`, `task`, `checked`), `-table` (one item; projection: cells by tab, rows by line), `-rule`, `-links` (a block's links as `<a target=_blank rel=noopener>`, after its text). Text blocks hold one text node whose inline styles are spans in the layer `markdown`; a face names every style a run has (`markdown-strong-emphasis`, `markdown-heading-1-marker`), and `rules.css` matches each part in the class. Top-level nodes carry `key` (index) and `markdown` (their source); update reuses a node whose key and source are unchanged. `markdown-style-text!` keeps texts in a weak table and restyles them on `after-change-hook`, parsing the whole text (fine for a prompt). Demo `demo/markdown.ss` (`C-c m`, `*markdown*`): the preview redraws through `markdown-update-blocks` on each edit of the source below it. Tests: `plugins/markdown/tests/unit/style-test.ss`, `plugins/markdown/tests/integration/markdown-test.ss`.
   Left for later stages: drawn blocks are ordinary editable text until stage 2's `read-only` attribute; a link's text in a block is styled but only the list under the block is clickable; code has no syntax colouring.
2. **Groundwork** (independent of 1): process library extraction (terminal tests stay green); `read-only` node attribute; files contract additions; program-status by buffer.
3. **The chat.** `plugins/pi/`: helper with replay, RPC client job, chat buffer (messages, thinking, tool blocks with file targets and edit diffs, status bar, prompt, send / queue / steer / abort, `M-p` history), extension dialogs as inline questions, setStatus in the bar, session slot and reconnect, idle exit, reboot reopen, Pi exit shown with stderr. Acceptance: fake-Pi tests for streaming, tools, queue, dialogs, restart mid-reply, reboot reopen; a real Pi chat in the browser with a cheap model at low thinking; restart Tuna mid-reply.
4. **Menu, sessions, integrations.** Chat menu (`C-c C-p`: model, thinking, compact, auto-compact, new, resume from this project's session files, fork, clone, rename, export, reload, thinking shown/folded); `pi-send-region` with a chat picker; `@` file picker; program status and notifications (working, blocked, done, error). Acceptance: each from the browser; `make test` green.

## As built

**Stage 2 (groundwork, branch `chat-groundwork`, 2026-10-28):**

- *Process library:* `tuna/lib/unix.ss` (private folders, Unix sockets with the `SO_PEERCRED` user check, raw device reads and writes, a session of one's own, standard ports dropped) and `tuna/lib/helper-processes.ss` (a kind's private socket folder and per-helper socket paths, detached start through `setsid -f` and `systemd-run --user --scope`, waiting for the socket, a device writer thread). Pi on plain pipes needs no C: Gambit's `open-process`, standard error left to the helper's log. The terminal keeps the pseudo-terminal, libghostty and its framed protocol. Not moved: a line reader for JSONL, which the Pi helper will write over `device-read-some`.
- *Read-only nodes:* the buffers contract's `node-read-only?` (the node or one above it has a true `read-only` attribute) and `check-writable` (now exported), which refuses "Text is read-only" when the focused text node is read-only; `insert`, `delete-region` and the `undo` command call it, so typing, yank, `delete-selection`, transpose, case changes, kills (which still copy) and dictation all refuse. Voice dictation remembers the node of its last piece and no longer attaches punctuation to it once it is read-only. The owner writes with `text-replace!`.
- *Files contract:* `file-completion-table FROM` (moved from the private `files/picker.ss`, where it was `file-table`), `find-file-at-line PATH LINE COLUMN other-view?:` (from the terminal's link opener, which now calls it), and `find-file-references TEXT EXISTS?` (moved from `terminal/links.ss`, which now uses it): `(START END PATH LINE COLUMN)`, LINE and COLUMN digit strings or `#f`.
- *Program status by buffer:* `program-status-report` moved from the terminal contract to the program-status contract, which now has a service, `program-status-service`, with one entry point, `report-program-status! BUFFER REPORT`; the program-status plugin provides it, and its handler of the terminal's report hook goes through the same procedure. Records are kept by buffer, `program-status-change-hook` runs with the buffer, and notifications uses only the buffer. The status-line part is now named `program-status` (it was `terminal-status`), so in a terminal it shows before the terminal's title. So that the terminal and program-status packages do not import each other, `terminal-program-status-hook` now runs with the record's fields (id, state, kind, progress, app, title, message) instead of a report, and the program-status plugin makes the report.

**Stage 3 (the chat, branch `pi-chat`, 2026-10-28):**

- *Placement:* `plugins/pi/` only; the kernel, the process library and every other plugin's code are unchanged (the starter's and demo's `init.ss` declare `markdown` and `pi` before the layout, and two order tests follow). `plugin.ss`'s imports: kernel, `tuna/lib/{jobs,timers,plugin-options,helper-processes}`, and the commands, keys, settings, buffers, session, clients, stylesheets, markdown, minibuffer, completion, buttons, layout, files and program-status contracts. Requires commands, input, settings, buffers, session, markdown; optional layout, minibuffer, completion, completion-ui, files, file-system, program-status. Private files: `jsonl.ss` (framing), `replay.ss` (the helper's replay state), `helper.ss` (`tuna-pi-helper`, `build.ss` `exe:`), `connection.ss` (launching, the socket, the reader's inbox), `tool-text.ss` (headers, previews, ANSI, diffs), `transcript.ss` (the nodes). The contract imports only the kernel and the buffers contract.
- *Helper protocol:* `tuna-pi-helper --socket --directory --log --idle-exit [--model] [--thinking] [--trust] [--session] -- PI-COMMAND…`; it runs `PI-COMMAND --version` first (Pi < 1.4.0, or one that cannot run, gets `helper_hello {error}` then `helper_exit {status 127, stderr: why}`), then `PI-COMMAND --mode rpc [--approve|--no-approve] [--model M] [--thinking L] [--session FILE]`. Lines from Tuna are Pi's commands verbatim; `helper_detach`, `helper_kill` are the helper's. A second Tuna gets `helper_refused`; the plugin retries every 0.2 s (at most 50 times). Responses to a Tuna arriving before its snapshot are held until after it. A Tuna more than 16 MB behind is dropped (Pi is always read) and replays on reconnecting. The log is deleted on exit unless Pi failed on its own.
- *Tuna side:* a job per connection reads the socket, parses each line on its own thread and posts `records` when its inbox (16 MB) was empty; records apply only while their link is the chat's link or reload candidate. Request ids are `PREFIX-N`, PREFIX random per connection; pending requests fail when the link ends or Pi stops. A prompt sent while idle marks the chat busy at once (so a second `RET` queues) unless Pi answers `handled`.
- *Drawing:* the root's children are the messages, open questions, the status bar (`pi-status`, one item) and the prompt (`pi-prompt` holding the text node, keymap on it). Messages carry the transcript keymap (TAB, RET, n, p, C-c C-k) and `read-only`; tool and thinking headers carry a keymap whose `<mouse-1>` folds. A tool with no output has no body node. Following the bottom: a view counts as at the bottom while its placement is the one the chat last made, or a client that used a chat measured the prompt or bar as its last visible item; after each batch and flush those views are placed with the prompt's last line at the bottom; after a snapshot every view showing the chat is.
- *Choices left open by the plan:* `select` offers its first option as the default (so `RET` picks it without a candidate list); `confirm` is a yes/no completion; `editor` is a prefilled minibuffer prompt with `S-RET` for a new line. A question's timeout removes it. `C-c C-k` puts the cleared queue back in the prompt. Session slot `pi-chats` version 1: `(ID SOCKET BUFFER-NAME SESSION-FILE DIRECTORY DRAFT HISTORY)`, at most 100 prompts kept; a new chat's session file is used only once Pi has written it. Reload starts the new helper with `--session FILE` (Pi's equivalent of `switch_session`) and sends the old one `helper_kill` only after the new snapshot arrives.
- *Tests:* `plugins/pi/tests/unit/{jsonl,replay,tool-text}-test.ss`; `plugins/pi/tests/integration/{chat,dialog,editor,restart}-test.ss` against `tests/support/fake-pi.ss`, a Gerbil script run with `gxi` through `pi-command` (scenarios by the prompt's first word). Every helper and fake Pi is stopped by pid (`tests/support/chats.ss`), orphans of a killed run too. Real Pi (`anthropic/claude-haiku-4-5`, low thinking) checked in the browser: tools, streaming, and a Tuna restart mid-reply that reconnected and kept streaming (screenshots in `/home/jay/Code/workbench-gerbil/scratch/pi-chat/stage3/`).
- *Known limits:* tool durations are not in Pi's history, so after a reconnect finished tools show no time; a bare `notes.txt:3` (no slash) is not a file reference (the files contract's finder, after ghostel, needs one); typing through the browser's `insertText` (as agent-browser's `keyboard type` does) does not reach the prompt, a page-input matter outside the plugin.
