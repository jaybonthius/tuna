# Prior art for Tuna user configuration

Read-only survey, evidence as of the pinned commits below. Labels: **Fact** (read in source or docs), **Inference** (my reasoning from facts), **Unverified** (not checked). Tuna context: ADR 2 (plugins, receipts, init.ss last), ADR 5 (custom.ss, data files are never evaluated), ADR 12 (small kernel, startup/live tiers, safe mode).

## Answer

Configuration is a **plugin plus a thin boot step, not a kernel feature**, and plugin selection should be **data first, code second**. Cordis, the model Tuna borrows, keeps its loader out of `core` (a separate package; core never mentions it), models "which plugins, with what options" as plain data entries, and keeps code inside plugins. Tuna ships a **starter configuration** the user copies and owns (Doom copies `init.example.el`; lazy.nvim ships an example spec); it is a starting point, never a fallback, and an absent config means no plugins.

Per owner direction, recovery must need **no stored history**. The prior art that does this treats the **running system as the last good state**: nginx, Caddy, Home Assistant and Cordis validate the new configuration first, apply it as a diff, and keep the old parts running if a part fails; Kubernetes and Erlang supervisors isolate failure per unit and retry. All of these are reload designs. **Cold start has no running system to keep**, so the guarantee must come from elsewhere: (1) each entry is activated independently, failures roll back atomically and are skipped, dependents are skipped and reported, and everything else runs; (2) the process **stays up** with whatever came up, reports every failure to the terminal it was started from (a surface that needs no plugin; Tuna already does this when no Messages provider exists), and accepts a reload from outside the app (`tuna reload`/SIGHUP, as nginx and Helix do) so a failed cold start becomes an ordinary live reload after the user edits the file in any editor; (3) `tuna check` runs the whole load pipeline without applying it (nginx `-t`, `caddy validate`, Home Assistant's config check). An optional in-app recovery page, built as an ordinary plugin in the starter config (Home Assistant's `recovery_mode` is itself an ordinary integration), covers users who cannot reach a terminal. Nothing here needs a kernel change.

## Findings

### 1. Cordis / Koishi (pinned: cordis `c261dd2`, koishi `97d5c39`)

- **Fact:** `cordis/packages/core` has no reference to a loader and depends only on `@standard-schema/spec` and `cosmokit`. The loader (`packages/loader`) is `class Loader extends EntryTree`, installed with `await root.plugin(MockLoader)` in its own tests and registered as a service (`ctx.reflect.provide('loader', …)`). **Inference:** Cordis's answer to "kernel or plugin?" is plugin. Something still has to call `ctx.plugin(Loader)`, so a bootstrap exists outside it.
- **Fact:** `EntryTree` is abstract; `commit()` (persistence) is supplied by subclasses. The root `Loader.commit()` is a no-op; `Include` is a file-backed tree with a journal, atomic writes, an `initial` fallback only for a missing file, and a watcher through the hmr service. **Inference:** reading/writing the config file is one more replaceable plugin, not part of selection logic.
- **Fact:** An entry is data: `id, name, config, group, disabled, inject`. `Entry.update` diffs old and new options (`deepEqual`); if only `config` changed it calls `fiber.update(config)` rather than tearing down; if `disabled` it disposes the fiber. Group entries nest, ids are namespaced with `:`. Koishi 4's YAML uses `name:ident` keys, a `~` prefix for disabled, `$if` expressions, and `${{ env.X }}` interpolation (`shared.ts`).
- **Fact:** Koishi 4's `Loader` is *not* a plugin: the worker does `new Loader()`, reads config, then `loader.createApp()` and `app.provide('loader', this)`. It writes config back (debounced, `.tmp` then `rename`) when a plugin's config changes through the UI, preserving disabled state by renaming the key to `~name`. **Inference:** the Cordis rc loader is the newer design; Koishi 4 shows the "host reads file, builds context" shape that Tuna's `main.ss` already has.
- **Fact (validation):** Plugins declare `Config` as a Standard Schema; `resolveConfig` validates before running the plugin and throws `ValidationError` listing each issue with its path. Koishi 4 uses `Schema` (schemastery) for the same role and calls `schema.simplify(config)` to write only non-default values. The hmr package still depends on `schemastery`.
- **Fact (isolation):** A plugin that throws in its apply is caught, logged, and its fiber becomes `FiberState.FAILED`; a failed fiber stays registered with its config and can recover through a later config update (loader test "failed entry recovery"). Dependents on a service that went away become inactive rather than crashing (`_checkImpl`, `_refresh`).
- **Fact (HMR, `packages/hmr/src/index.ts`):** reload is staged. Stage 1 re-imports the module graph all-or-nothing and restores the module caches on failure, "before any plugin has been touched". Stage 2 disposes affected plugins. Stage 3 reloads each; the comment says there is **no rollback**: "a plugin that fails to load is left failed, exactly as it would be on a cold start" and the next file change retries. Changes to framework ("external") modules force a full process restart instead. HMR is its own plugin, injected with `loader` and `timer`.
- **Fact:** Koishi's worker installs `uncaughtException → exit(1)`. **Unverified:** what restarts it (a `fullReload` exit code 51 and a `daemon` plugin exist).
- **Gap Cordis leaves open:** no safe mode or bisect found. Failure isolation is per plugin only; a bad *file* (unparseable YAML) is fatal at startup.

### 2. Emacs, Doom, Spacemacs (local Emacs checkout `541f693`; doom `59cdaa3`; bug-hunter `31a2da8`)

- **Fact:** `early-init.el` is loaded before the package system and GUI, for settings that affect package initialisation (`package-enable-at-startup`, `package-load-list`); the manual says not to put anything there that can live in init.el (`doc/emacs/custom.texi:3150`). `startup.el` calls `package-activate-all` between early-init and init.el. **Inference:** Emacs already needed a pre-user-code phase for startup-time selection; Tuna's equivalent for startup-tier services is a data file, not a second code file.
- **Fact:** An error in init.el is caught once around the whole file (`startup--load-user-init-file`): the rest of the file is skipped, a warning says "investigate and remove the cause", and `init-file-had-error` is set. `--debug-init` enters the debugger instead; `-Q` skips init, site files, and splash. `unload-feature` is documented as best effort (relies on `FEATURE-unload-function` and hook/autoload cleanup). **Inference:** partial-apply-then-stop is the Emacs failure mode: effects before the error remain, with nothing to revert them.
- **Fact (bug-hunter):** external package; bisects the init file by running separate Emacs processes, automatic for errors, interactive ("did it show the problem?") otherwise. **Inference:** it must split source text by top-level forms because Emacs has no unit smaller than the file; a declarative plugin list bisects trivially.
- **Fact (Doom):** `doom!` block in init.el lists modules; `packages.el` declares packages; `config.el` is code. `doom sync` must run after changing either declarative file (installs, prunes, regenerates metadata). The docs state private declarations take precedence over module declarations. `doom/reload` runs `doom sync`, re-evaluates modules and config under `with-demoted-errors`, and its docstring says it is "experimental, and likely always will be" and "isn't a perfect replication of the startup process", recommending a restart. **Inference:** this is the clearest evidence that reload without receipts is unreliable; it also shows Doom splits declaration (needs processing before startup) from code.
- **Unverified/shallow:** use-package (in tree: `:disabled`, `:defer`, `use-package-verbose`) and Spacemacs layers were not examined beyond keyword listings.

### 3. Lisp-hosted apps (lem `877c683`, nyxt `aeb6c72`, stumpwm `902d5c2`)

- **Lem, Fact:** `init` runs `load-init-file` (`~/.lem/init.lisp`, then `.lemrc`) after `*before-init-hook*`, before `*after-init-hook*`, skipped by `-q`; `toplevel-command-loop` wraps the init function in `with-error-handler` so an error does not kill the editor. A separate `config` plist file is autogenerated, labelled "S-Expressions in this file are not evaluated", i.e. the same split as ADR 5's custom.ss. No declarative plugin list; extensions are loaded by code.
- **Nyxt, Fact:** `load-config-file` calls `clean-configuration` (clears `define-configuration`/`customize-instance` handlers; "Load or reload the CONFIG-FILE") then loads the file; errors are caught, the backtrace shown in a new "*Config file errors*" buffer, and under a REPL a retry restart is offered. `--no-config` and `--no-auto-config` skip the files. `restart-with-message` relaunches the program with `--no-config --no-auto-config` and a hook that shows the original error; it fires from `with-protect` only when `*restart-on-error*` is true, whose default is `nil`. **Inference:** Nyxt's auto-fallback is the closest analogue to what Tuna needs, though it is opt-in there and Nyxt's cleanup is a hand-written partial inverse (what receipts generalise).
- **StumpWM, Fact:** `load-rc-file` takes `catch-errors` (default true); at startup a failure becomes an on-screen message with the file and error; the `loadrc` command re-loads (with a restarts menu) and reports success or error. Nothing undoes the previous run. **Inference:** reload by re-evaluation accumulates duplicates unless the host cleans first; not verified in StumpWM source.

### 4. Neovim, Helix, Zed, VS Code

- **Neovim + lazy.nvim (lazy `306a055`; nvim doc `a054b69`):** **Fact:** lazy plugin specs are Lua tables with `opts`, `config`, `cond`, lazy-load triggers; `lazy-lock.json` pins revisions after updates and `:Lazy restore` returns to it; `install.missing` installs on start; `:Lazy reload` is labelled "(experimental!!)" and is implemented as deactivate → re-run `init` (wrapped in `Util.try`) → reload if it had been loaded. `nvim --clean` mimics a fresh install; `-u NONE` skips init. **Inference:** a lockfile solves reproducibility of *versions*, which matters for Tuna only once packages come from outside the repo.
- **Helix (`ba40e54`):** **Fact:** `config.toml`/`languages.toml` are data; `:config-reload` or SIGUSR1 reloads. `refresh_config` builds the new config first; on error it shows the error and the old config stays; startup with a bad config prints "Bad config … Press ENTER to continue with default config". Project-local `.helix/config.toml` merges over user, which merges over built-in. **Inference:** validate-then-swap with defaults fallback needs no extra machinery when config is data.
- **VS Code:** **Fact:** extensions run in a separate extension-host process so "the cursor always blinks"; "Start Extension Bisect" halves the enabled extension set, like git bisect. **Inference:** bisect works because enable/disable is data and reversible. Tuna is single-process (ADR 10 trusts plugins), so isolation comes from receipts and the quit lane, not processes.
- **Zed:** **Fact (shallow):** docs describe user and project settings layering, `settings.json`, and profiles; "invalid regexes are logged and ignored" per setting. Live reload and safe mode not verified.

### 5. Recovery that needs no stored history (nginx, Caddy, Home Assistant, Kubernetes, systemd, OTP, Cordis)

- **Cordis live update, Fact (`packages/core/src/fiber.ts:486`):** `fiber.update(config)` validates the new config (`_resolve`) *before* assigning it, so an invalid config throws and the old one keeps running. A valid config that then fails at runtime does not roll back: `update` unloads and reloads, the fiber ends FAILED, and "a failed fiber only recovers through update()". Koishi's loader additionally diffs entries and applies only changed ones (§1). **Inference:** Cordis gives validate-before-apply and per-unit isolation, but not rollback of runtime failure; Tuna's atomic activation rollback could add it.
- **nginx, Fact (nginx.org "Controlling nginx"):** on HUP the master "first checks the syntax validity, then tries to apply new configuration, that is, to open log files and new listen sockets. If this fails, it rolls back changes and continues to work with old configuration." `-t` tests syntax and opens referenced files without starting. Old workers finish serving while new ones start (overlap, not teardown first).
- **Caddy, Fact (caddyserver.com/docs/api, /command-line):** `POST /load` "blocks until the reload completes or fails... If the new config fails for any reason, the old config is rolled back into place without downtime." `caddy validate` loads and provisions all modules "but the config is not actually started", "a stronger error check than merely serializing". **Inference:** validate-by-provisioning is the right strength for Tuna's check (activation without commit), at the cost that provisioning may have side effects.
- **Home Assistant, Fact (`homeassistant/bootstrap.py` at core `1ab6184`; docs "The configuration.yaml file"):** a configuration check runs automatically on reload and restart. Recovery mode is entered, with nothing stored, when `configuration.yaml` fails to parse, core integrations fail to set up, or any of `CRITICAL_INTEGRATIONS` (`frontend`) did not load; the instance is torn down and rebuilt with only `DEFAULT_INTEGRATIONS_RECOVERY_MODE` = `backup`, `cloud`, `frontend`, plus the `recovery_mode` integration, which just posts a notification "Check the error log". **Inference:** HA discards the whole config in recovery mode (it is whole-config fallback, not per-unit), and it depends on a built-in component set and a fixed critical list, which Tuna's no-standard-set rule rules out; two ideas transfer: recovery is just a normal integration, and recovery triggers on "the console did not come up".
- **Kubernetes, Fact (kubernetes.io/docs/concepts/architecture/controller):** controllers are control loops moving current state toward desired state; "your cluster never reaches a stable state... As long as the controllers... are running and able to make useful changes, it doesn't matter"; many small controllers rather than one interlinked set. **Inference:** level-triggered reconcile means a failed unit is simply retried on the next pass, so cold start and reload are the same operation.
- **systemd, Fact (systemd.unit(5), systemd.special(7)):** `Wants=` is a weak requirement; `Requisite=` fails the unit immediately if the dependency is not already started; `BindsTo=` stops a unit whose bound unit goes inactive. If the default target cannot start systemd starts `rescue.target`; `emergency.target` "does not pull in other services or mounts", is the minimal path to a shell, and can be requested on the kernel command line. **Inference:** the OS's last-resort surface is a shell outside the system's own services; for Tuna the analogue is the terminal that launched the process.
- **Erlang/OTP, Fact (erlang.org design principles, supervisor behaviour, release handling):** `one_for_one` restarts only the terminated child; `intensity` and `period` (default 1 and 5 s) stop a child that "repeatedly dies for the same reason", escalating to the parent supervisor; the counter is in memory. Release handling can fall back to the old release only because `RELEASES`/`start_erl.data` record old and permanent versions: that is the stored-history design the owner rejects, listed for contrast. The `config_change(Changed, New, Removed)` callback applies a config diff to a running application.
- **Not found:** a system that restores a *previous* configuration with no stored record. What exists without history is (a) keep running state (nginx, Caddy, Cordis validation), (b) isolate and retry per unit (k8s, OTP, Cordis), (c) a minimal out-of-band surface (HA recovery mode, systemd rescue/emergency).

## Prior Tuna attempts (evidence only)

- **Fact:** `tuna-old` loaded a code `config.ss` that imported packages by name and mutated global values (`(set! (value tuna-initial-state) …)`, a `load-module` call) in one shared namespace. `tuna-old-2026-10` planned "`config.ss` selects packages loaded dynamically" with `use-package`-style syntax (its `docs/overview.md`), then built language-level customisation instead: live-replaceable `def`s (`function-ref`), `redefrule` macro advice, a 117-line macro registry (`tuna/macro-registry.ss`). Its `docs/customization.md` says "performance acceptance is blocked" by unexplained benchmark slowdowns and that macro reload "does not persist" across compiler processes.
- **Inference:** configuration became an interposition problem on the language's bindings rather than a registration problem on a runtime, so there was no ownership, no inverse, and nothing to disable or reload cleanly; failure and recovery were never designed. Separately, `agents/research/workbench-gerbil/gerbil-config-import-injection-options.md:455` records that Gerbil source reload and prelude evaluation are "sequential and nontransactional" (not re-verified here). That bounds how far Tuna can lean on module reload.

## Recommendations (ranked)

1. **Loader is a plugin over existing kernel calls; the first read is boot code in `main.ss`'s successor, not in the kernel.** *Decision for owner* (it answers the owner's first question). Evidence: Cordis core never references its loader; the only things the loader needs (activate, deactivate, hooks) are already kernel exports, so ADR 12's amendment rule is not triggered. Boot code reads the selection data and activates plugins; a `config` plugin (one among others, replaceable) owns `reload-config`, `describe-config`, enable/disable commands, and the bisect command; since the user may have no input plugin that reaches it, rec. 8 also exposes them outside the plugin world. Confidence: high on "not kernel", medium on exactly where the boundary between boot code and the plugin falls.
2. **Plugin selection is data; user code is a plugin that comes after.** *Decision for owner* (second question). A `plugins.ss` (name is engineering detail) holds entries equivalent to Cordis's: plugin name, `disabled`, options, optionally `if`. It is read with `read`, never evaluated (ADR 5), so a typo cannot hang or crash boot. `init.ss` stays code and ADR 2's "activated last, re-evaluation reverts first" applies unchanged. Reasons from evidence: boot must pick startup-tier providers before user code (Emacs needed early-init for the same reason); data bisects and validates for free (VS Code, Helix, Doom); a UI or `M-x` toggle can edit it. Cost: two files to explain. Tuna ships a **starter configuration** (data file + `init.ss`) that the user copies and owns; it is a template, not a fallback, and nothing loads it implicitly. An absent data file means no plugins are selected, and the loader says so on the terminal and points at the starter. Precedent: Doom copies `init.example.el` into the user's directory (`getting_started.org`).
3. **Startup-tier choices live only in the data file; `init.ss` cannot change them.** *Decision for owner.* If init.ss asks for a different startup provider, record the request, tell the user "takes effect after restart", and do not swap live (ADR 12 already says startup services refuse live replacement). Alternative: init.ss writes the choice into the data overlay for next boot. Doom's `doom!`-in-init.el and Emacs's early-init both place such choices before ordinary config; neither lets later code change them live.
4. **Layer order: plugin defaults < `plugins.ss` options < `custom.ss` (UI) < `init.ss` (code).** *Decision for owner* on whether code beats the UI (Emacs's `custom-set-variables` problem; Doom tells users not to use Customize). Recommend code wins and help shows "set by init.ss:LINE, overriding custom.ss". Implementation is an engineering detail: each layer is an owner with a priority in ADR 2's entry model.
5. **Cold start: activate each entry independently; skip what fails; report everything; keep running.** *Engineering detail.* Entries activate in dependency order. A failure (validation, activation error, timeout) rolls the entry back atomically (already true in Tuna), is recorded as `failed` with error, file and line, and dependents are recorded as `skipped (needs X)`; everything else runs (Cordis dependents, OTP `one_for_one`, systemd `Wants=`). Add a per-entry activation timeout enforced by the loader (**Inference**; systemd has start timeouts, **Unverified** here), because with a broken input plugin no `C-g` exists to stop a hung `init.ss`. `init.ss` is one entry: *Decision for owner*, whether a failing `init.ss` reverts whole (recommended; code-only systems' partial keep is the cause of half-configured sessions) or keeps effects before the error. Report is held in memory and printed; see rec. 8 for where it goes.
6. **Reload is the Cordis/nginx/Caddy pattern: validate, diff, apply per unit, running system is the rollback.** *Engineering detail, with one Gerbil risk.* (a) Validate everything with no live effect: parse the data file, check each option set against the plugin's declared settings (Cordis `resolveConfig`), compile/import changed modules; any failure aborts the whole reload and the running system is untouched (Helix, Caddy, Cordis `update`). (b) Diff desired entries against the loader's in-memory table of what is applied (K8s desired vs current; OTP `config_change(Changed, New, Removed)` for option-only changes through the plugin's settings handler). (c) Apply per unit: deactivate old, activate new; if the new activation fails, its receipt rolls back and the loader **re-activates the old entry from the in-memory copy of its options**, so the old part keeps running; nothing is written to disk. Unlike nginx the overlap is not possible in general (ports, timers, command names), but owner-tagged entries (ADR 2) may allow overlap for pure registrations (**Inference**). Failed entries are retried on every later reload (level-triggered, as in Kubernetes and Cordis, where "a failed fiber only recovers through update"). **Risk:** re-importing a changed Gerbil *module* is nontransactional (prior research; not re-verified), so "old code keeps running" holds for option changes and for restoring registrations, not for code reload; code reload falls back to Cordis HMR semantics (stage (a) can abort cleanly, later failures leave that plugin failed and retried). Needs a spike.
7. **Per-plugin options validated against a schema the plugin declares.** *Engineering detail.* Cordis `resolveConfig` shape (collect all issues with paths), using Tuna's typed settings declarations (ADR 9), run in stage (a) from the static manifest.
8. **Cold-start recovery surface: terminal report, a surviving process, external reload, and `tuna check`; no stored history.** *Decision for owner* (supersedes ADR 12's safe mode; this is the answer to "what guarantees the user can see errors and edit the config when their own input or display plugin failed"). Option A of the table above:
   - The process stays up after a partial boot, prints the per-entry report to stderr, and also writes it to a log file in the state directory, overwritten each boot (a diagnostic log, not a configuration record; the owner should confirm this is not "extra state").
   - `tuna reload` (control socket) and SIGHUP re-run rec. 6 on the live process; the user edits files in any external editor, then reloads. A failed cold start is therefore just a reload problem.
   - `tuna check` runs the cold-start pipeline in a throwaway kernel and exits non-zero on any `failed`/`skipped` (nginx `-t`, `caddy validate`). Caveat as Caddy: provisioning has side effects (ports, files); plugins should keep activation side-effect light or honour a dry-run flag.
   - Generic trigger, no plugin names: the kernel already consumes the `Input`, `Display` and `Messages` services (ADR 12). If Input or Display is empty after boot, the loader prints a prominent "no console" notice, since nothing in the user's config provides one. This replaces Home Assistant's fixed `CRITICAL_INTEGRATIONS` list (**Inference**).
   - If a startup-tier provider failed, the slot is empty; allow filling an *empty* startup-tier slot by reload (nothing runs against it) while replacing a filled one still requires restart (**Inference**; ADR 12 says startup services "refuse live replacement"; engineering detail, confirm).
   - **Owner decision, extra surfaces:** terminal-only fails for users who launched Tuna headless with no log access. Options from the table: D (an ordinary recovery plugin shipped in the *starter* config, with its own listener, user-owned and deletable) is the lowest-cost extra; C (`tuna recover`, systemd-emergency style) survives a crashed main process; B (boot-level page) needs a kernel/boot HTTP server and I recommend against it.
9. **Bisect with state held only in the running process.** *Engineering detail.* Per-entry isolation already attributes crashes and validation errors, so bisect is only for behavioural bugs or interactions. A bisect session (in-process, lost on exit) disables half of the entries (finally `init.ss`) through receipts, asks "still broken?", and re-enables on finish. It is reachable by in-app command and by `tuna bisect` over the control socket, since the user's input plugin may be the culprit. VS Code halves extensions; bug-hunter uses separate Emacs processes and keeps state in the driving Emacs (**Inference** from its README). An assertion form (`tuna check --assert`) can automate it (bug-hunter's assertion mode).
10. **Rejected: crash-loop marker, generations, last-known-good snapshots.** Each needs persisted history (NixOS, OTP release handler, lazy.nvim lockfile for revisions, any "healthy boot" marker); excluded by owner. Crash-loop protection, if wanted, belongs to whatever supervises the process (OTP/systemd style intensity limits, **Unverified** for systemd).

### What is guaranteed when config fails

Not a plugin set and not a stored config. Guaranteed: (1) the user's own entries that can come up do come up, independently; (2) every failure is reported with cause, file and line on the launching terminal (and the boot log); (3) the process stays up and accepts an external reload and check; (4) the files on disk are never rewritten by recovery. **Inference/limit:** if the user cannot reach a terminal or log and has no user-owned recovery plugin, nothing in-app can help; that is the cost of having no built-in surface, and the owner decision in rec. 8.

## Contradictions and open points

- Koishi 4 puts the loader outside the app context; the Cordis rc loader puts it inside. Recommendation 1 follows the newer one, with boot code as the outside piece.
- Doom splits declarative and code files and recommends restart over reload; Cordis HMR reloads without restart. The difference is receipts: Doom has none (Inference).
- Nyxt auto-restart exists but defaults to off. No surveyed system restores a previous configuration without stored records (OTP releases, NixOS, lockfiles all store them).
- ADR 12's "safe mode starts Tuna with only the standard plugins" conflicts with the owner's corrections (no standard setup, no stored fallback) and is superseded by recommendation 8; the ADR needs an edit if the owner agrees.
- Home Assistant's recovery mode, systemd's rescue target and Nyxt's relaunch all fall back to a built-in minimal set; that is the model the owner excluded, so only their *triggers* and *surfaces* are borrowed.
