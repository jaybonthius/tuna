# Research: per-tab state in Datastar apps — Discord export and Northstar

Scope: read-only. Sources: the local Datastar Discord export (`/home/jay/Code/datastar-discord-export`, queried through its SQLite index at `exports/corpus.sqlite3`, export runs through 2026-08) and `/home/jay/Code/northstar` (HEAD `cb759ec`, 2026-08-04). Discord links use guild `1296224603642925098`. Abbreviations: **SSE** = Server-Sent Events; **CQRS** = Command Query Responsibility Segregation (here: commands are short POSTs that return 204, and every view update arrives on one long-lived SSE stream); **KV** = key-value.

## Summary

- **Tab identity convention: a random tab-id signal created when the page loads.** Anders Murphy's shared page shell does `data-signals-tabid="self.crypto.randomUUID().substring(0,8)"` and generates the id in the browser. It is a non-local signal, so Datastar sends it automatically with every request, including the stream request. Delaney Gillilan said the same thing earlier: "send down a uuid signal on the page load, use that as per tab." A reload creates a new id. Nobody in the export used `sessionStorage` for this except one community member.
- **Per-tab state belongs on the server, keyed by tab id, not held in signals.** Anders (2025-08 onward): "put your tab state in your db and look up with tab id"; "the client is mostly a session cookie, a csrf token, a tab-id and some contextual data the server wants to know (view height/width x/y scroll)." He stores scroll position and virtual-scroll state per tab.
- **The authors push per-tab state to be small.** Delaney asks "why do you have state per tab and not per user?" and calls per-tab state "dumb… if you really need it." Anders first called per-tab state "an anti pattern in multiplayer" (2025-03), then adopted per-tab rows for UI state such as scroll (2025-08 and 2025-11). Both lean towards shared state by default.
- **Broadcast "re-render", not HTML.** Anders (2026-08-12): "You shouldn't be broadcasting html to all connections. You should broadcast that a connection should re-render and let it generate the html from its context." Delaney replied: "this is accurate." Each connection holds a render function plus its context. A change wakes every connection, throttled or batched to about 100–200 ms.
- **Every (re)connect must send the whole current view.** The authors say to design on the assumption that events get lost: "always return the latest version of the whole view with morph" (Anders); "server is in charge, when they reconnect they'll get back to sync'd state" (Delaney).
- **Background tabs disconnect by design.** A GET stream closes when its tab is hidden (`openWhenHidden` defaults to false for GET and true for other methods since RC7; Tuna's vendored `datastar-v1.0.2.js` matches). The server must treat a disconnect as "tab asleep", not "tab gone".
- **Known bug (issue #900): retries resend stale signals.** When a stream is retried after a network or server error, Datastar sends the signals from the first request, not the current ones. A visibility reconnect rebuilds them correctly. People reported it as still present in 2026-06, and Delaney said "this is a bug if confirmed." **Do not keep per-tab facts in signals that the stream request depends on.** Keep them on the server and send only the immutable tab id.
- **Northstar has no per-tab concept at all.** Upstream Northstar (v0.16.0) keeps all Todo state, including the view filter and the "editing" index, in a NATS KV entry keyed by a cookie session id. Every tab watches that key and re-renders the whole Todo view, so all tabs mirror each other. The owner's fork (HEAD) does the same per user, with a NATS subject per user and a refetch-then-fat-morph loop. Delaney cites it as the reference: "northstar todo is a simple example using a KV as a shared state event bus."

## Source 2: Northstar (`/home/jay/Code/northstar`)

The checkout's recent commits (`387933c` onward) are the owner's own changes. Upstream is zangster300/northstar v0.16.0 (`c290e4c`, Nicholas Zanghi). Both were read.

**Upstream v0.16.0 (the "northstar todo" Delaney cites)**
- **Session**: a gorilla `CookieStore`, HttpOnly, SameSite=Lax, 30 days (`cmd/web/main.go:46-51` @c290e4c). `upsertSessionID` stores a random `id.NextEncodedID()` in cookie session `"connections"` (`features/index/services/todo_service.go:165-174`). This is per browser profile, not per tab.
- **State**: the whole `TodoMVC` (todos, `EditingIdx`, `Mode` filter; `features/index/components/todo.templ:25-28`) is JSON in a NATS JetStream KV bucket `"todos"` with a 1-hour TTL (`todo_service.go:36-39`), keyed by that session id (`kv.Put`, line 147; `kv.Get`, line 61).
- **Stream and broadcast**: `GET /api/todos` opens the SSE stream. It calls `kv.Watch(ctx, sessionID)` (`todo_service.go:86-87`, `handlers.go:43`), and on each entry it re-renders `TodosMVCView` and sends `PatchElementTempl` (`handlers.go:54-63`). A NATS KV watcher first delivers the current value, so connect and reconnect get a full render without extra code *(interpretation, from NATS KV semantics)*. Commands such as `PUT /mode/{mode}`, `POST /{idx}/toggle` and `GET /{idx}/edit` mutate and `Put` the KV entry and return nothing. The watch fans the change out to every tab on that cookie.
- **Signals**: only the input text (`data-signals="{input:…}"`, `todo.templ:50`) and fetch indicators. Commands read signals only for the input (`handlers.go` `SaveEdit`, `datastar.ReadSignals`).
- **Per-tab**: none. The view filter and editing state are shared across tabs, which is the behaviour Delaney defended in item 15. The stream opener is `data-init="@get('/api/todos')"` on `#todos-container`, and that element is itself the morph target (`pages/index.templ:12`; `todo.templ:47`).
- The upstream `counter` feature is request/response, not a stream. It keeps a global count in an in-process `atomic.Uint32` and a per-cookie count in the cookie session, and returns `MarshalAndPatchSignals` (`features/counter/handlers.go:19-103` @c290e4c). There is no broadcast.

**Owner fork (HEAD `cb759ec`)**
- **Session**: an opaque 32-byte token in the HttpOnly cookie `northstar_session`, stored hashed in SQLite (`web/services/identity/session.go:19-43`, `middleware.go:15-34`, `migrations/00002_create_sessions.sql`). The user is resolved per request (`middleware.go:56-80`).
- **State**: `counter_state` per user id in SQLite (`migrations/00003_create_counter_state.sql`; `web/features/counter/data.go:13-31`).
- **CQRS and fat morph**: `POST /counter/increment` writes, publishes to NATS subject `counter.changed.<userID>`, and returns 204 (`handlers.go:72-90, 105-107`). `GET /counter/subscribe` subscribes to that subject, sends an immediate `patchMain`, and re-reads and re-renders `<main id="counter-page">` on each message (`handlers.go:34-70, 92-103`). The notification carries no data (`Publish(…, nil)`), which is exactly "broadcast re-render, not HTML."
- **Stream opener on `<body>`**, outside the morph target: `data-init="@get('<path>', {retry: 'always'})"` (`web/core/base.templ:8-14, 35`). There is no tab id and no per-tab state, so all tabs of one user mirror each other.

## Implications for Tuna (inference, not source statements)

**How a tab identifies itself**
- Mint the tab id when each page load runs, as a plain non-local signal in the page shell, outside the morph target: `data-signals-tabid="crypto.randomUUID()"` (Anders's pattern). Datastar then attaches it to the stream request and to every key or command POST with no extra code. A reload or a duplicated tab gets a new id, because the shell runs again. *Do not* persist it in `sessionStorage`: browsers copy `sessionStorage` into a duplicated tab, so two live tabs would share one id (general browser behaviour; not verified in this export). A server-rendered id in the initial HTML would also work, since Tuna does not cache its shell. It is weaker only if a browser restores the page from cache on "duplicate tab" (unverified).
- Keep the cookie or session for "which editor session" and the tab id for "which frame". Never put per-tab values in cookies (item 24).

**Where per-tab state lives**
- Keep it on the server, keyed by tab id. In Emacs terms each tab is a **frame**: buffers, their contents, the kill ring, modes and every other editor state stay shared and global. The per-tab list should be short and explicit. My proposal for the candidate list: tab id; measured viewport facts (width/height or columns/rows, font metrics); the scroll and visible window-start that the browser reports; the frame's window layout and selected window; window-level point and start where Emacs keeps them per window; and which tab last received input (Emacs's selected frame). This matches Anders's "session cookie, csrf, tab-id, view height/width, x/y scroll."
- Signals only carry measured facts up, through throttled or debounced POSTs that include the tab id. The server stores them. Because of #900, the stream request should depend only on the tab id, which never changes after load, so a stale retry cannot reset anything.
- **Lifecycle**: a stream disconnect means "asleep" (hidden tab or network loss), not "closed". Keep frame state for a grace period and collect it with a time to live (TTL) after the last disconnect. Anders never collects because he uses a database; Tuna holds frames in memory, so it needs a TTL. A reload creates a new frame. Decide whether the new frame inherits the old one's layout (Emacs has no direct equivalent).

**Broadcast vs per-tab render**
- On any shared-state change, notify every attached tab's stream with a payload-free "redisplay" (Northstar fork, Anders item 16). Each stream renders its own fat morph from shared state plus its frame. Throttle or batch per stream; Anders uses 100–200 ms. If two tabs have identical frames, the render could be cached, but only as an optimisation.
- Send the full screen on every (re)connect and on the first batch after connect. Never rely on deltas or `Last-Event-ID` replay for correctness.
- Commands from tab A that change shared state, such as editing a buffer shown in tab B, redisplay B too. Commands that change only frame state (scrolling, resizing, window splits) redisplay only that tab.

**Pitfalls to design against**
- **Duplicate streams**: keep the `@get` opener in the shell, outside the fat-morph target. Tuna currently puts `data-init="@get('/screen')"` on `<html>` (`plugins/web/plugin.ss:336`). Check that a whole-screen morph never re-adds or changes that attribute (item 23).
- **Background tabs**: GET streams close when hidden. A stream that must stay live needs `openWhenHidden: true` or POST. Hidden tabs should cost nothing to render, which argues for leaving the default.
- **Stale retry signals (#900)**: still unresolved upstream as of 2026-06 according to the export, and present in v1.0.2.
- **Many tabs**: HTTP/1.1 allows about 6 connections per origin. Visibility closing helps, and HTTP/2 removes the problem.
- **Two tabs typing at once**: input from different tabs interleaves on the server. Each command must name its tab so the server routes it to that frame's selected window. This is my inference; the sources do not discuss it.

## Contradictions

- **Anders changed position.** 2025-03-19: "No, I don't believe in tabs. Just an entry per user per page" and "Storing state per tab or even per connection is an anti pattern in multiplayer" ([link](https://discord.com/channels/1296224603642925098/1333801016642244739/1351925064676806716)). From 2025-08 onward he stores per-tab state keyed by tab id (items 8–11), and in 2026-02 he says "isolate your tab state on the server by tab id" ([link](https://discord.com/channels/1296224603642925098/1296225449260879973/1468645860354035925)). The later position is the current one.
- **Delaney is sceptical but supportive.** He calls per-tab state "dumb… over complicated" and prefers the URL or shared state, yet prescribes the uuid signal when it is needed. He also said "well since i support this i can telll you it's possible" (2025-08-23).
- **Community dissent.** romshark argues that tab-scoped view state, such as search, should stay in the browser or be returned directly from the action. Anders answers that this "doesn't work the minute you have out of bounds updates" (2026-02-04).
- **#900 fix status.** "Fixed in the next RC" (Anders, 2026-02-19) is contradicted by reports on RC.8 (2026-03) and 2026-06.

- Datastar documentation and Hyperlith source were not read; a parallel research lane covers them. The current status of GitHub issue #900 was not fetched.
