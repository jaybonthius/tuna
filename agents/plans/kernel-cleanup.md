# Plan: kernel cleanup

Owner-approved contract: ADR 12's "Kernel contract" section ([`agents/adr/0012-kernel-boundary-and-replaceability.md`](../adr/0012-kernel-boundary-and-replaceability.md)) and [`docs/briefs/2026-10-kernel-contract.md`](../../docs/briefs/2026-10-kernel-contract.md). Evidence: [`agents/research/kernel-audit-2026-10-12.md`](../research/kernel-audit-2026-10-12.md) and [`agents/research/kernel-contract/`](../research/kernel-contract/) (lane 3 gives per-export verdicts). Behavior must not change: every existing test keeps passing, adjusted only for moved names.

## Steps

Each step is a separate implementer task in its own worktree (AGENTS.md), merged only after the primary agent reads the whole diff for placement and a fresh read-only reviewer checks it against ADR 12. Each task brief names the layer that owns every moved piece.

1. **Mechanical checks first.** Built as `tuna/kernel/boundary-test.ss`, run by `make test`: `tuna/kernel/` may hold only `.ss` files and the baseline; non-test kernel source (`tuna/kernel.ss` and every `.ss` under `tuna/kernel/`; `test-fixtures.ss` was excluded until step 7 moved it out) may import only `:gerbil`, `:std`, and kernel modules, may include only checked kernel files, and its hits of ADR 12's forbidden nouns, command-registry names, and plugin names may not exceed the entries in `tuna/kernel/boundary-baseline.sexp`. It is a ratchet: the test fails on any new hit and on any entry larger than what remains, so each later step must delete or lower its entries. Merge review must confirm the baseline diff only removes or lowers entries. Each step, when done, also removes its tag from baseline-steps in boundary-test.ss.
2. **Opaque input.** *Done.* Replace `key-event` in `kernel/loop.ss` with opaque items wrapped in a private queue struct (`queued-input`); `submit-event!` became `submit-input!`, taking any item (step 7 replaced it with `input-submitter`). `Input` gets `arrival` (queue or interrupt, replaces `quit-event?`) and `resolve!` (replaces `resolve-event!`). Move `key-event` and the browser fields to `tuna/services/keys.ss`; the web plugin builds it; the keys plugin interprets it. Keep `input-pending?` and `discard-input` (ADR 3 lists both); they count and drop only input items, never queued tasks or job results.
   Remove its baseline entries (`step 2`) in `tuna/kernel/boundary-baseline.sexp`.
3. **Commands out.** *Done.* `command`, `context-define-command!`, `define-command`, `defcommand`, `command-entry`, and `command-ref` moved to `tuna/services/keys.ss`, dispatching through new `Keys` methods `define-command!` and `command-entry` (the `keymap-set!` pattern); the keys plugin owns the command table (`global-keys` field `commands`) and registers through `context-add-entry!`, so deactivation still removes a plugin's commands. The kernel's `commands` field and `kernel-commands` are gone. `Input-resolve!` returns `(name . thunk)` or #f; the loop runs the thunk as a task with that name. `current-command-name` became `current-task-name`. The kernel tests resolve items to `(name . thunk)` directly; the registry tests moved to `tuna/plugins/keys-test.ss`.
   Its baseline entries (`step 3`) are removed.
4. **Hooks owned by hook objects.** *Done.* Each hook holds its callbacks (a list replaced under the hook's mutex); the kernel's `hooks` field and `kernel-hooks` are gone. Because module-level hooks outlive a kernel, each callback records the kernel whose plugin added it, and `run-hook` and `hook-callback-names` see only the current kernel's callbacks. `context-add-hook!` and `run-hook` moved from `kernel/hooks.ss` to `kernel/plugins.ss` (they report through `message`); failing callbacks are still removed and reported. New lifecycle hooks: `plugin-activated-hook` (plugin), `plugin-deactivated-hook` (plugin), `service-changed-hook` (service, old provider or #f, new provider or #f) in `kernel/plugins.ss`, announced in order once the outermost activation or deactivation finishes; `task-started-hook` (id, name) and `task-finished-hook` (id, name, how: `returned`, `raised`, or `quit`; exactly once per started task, and a task cancelled before it starts announces nothing) in `kernel/loop.ss`, run on the loop thread while no task runs. Lifecycle callbacks must not activate or deactivate plugins (the call raises and the callback is removed); while the loop runs they can queue a task with `spawn-task!` instead, and while it is stopped they cannot cause a plugin change. The facade no longer exports `make-hook`, `hook::t`, `hook-name-set!`, or `hook-doc-set!`.
5. **Libraries.** *Done.* `tuna/lib/` holds shared libraries that use only the public kernel facade `:tuna/kernel` (plus `:gerbil`, `:std`, and other libraries); callers import them directly. `tuna/lib/timers.ss` (`context-run-with-timer!`, `timer?`, `cancel-timer`) moved unchanged. `tuna/lib/jobs.ss` holds jobs (keying, coalescing, owner cancellation, cleared dynamic environment); the kernel keeps `result-poster`, and its `jobs` field and `kernel-jobs` are gone. `start-job` became `job-group-start!`, which takes a job group: a plugin makes one with `(new-job-group ctx)` at activation and holds it, and the group's one `context-defer!` closes it and cancels its jobs on deactivation. Keys coalesce per group, so per owning plugin; a closed group refuses new jobs with an error. No module-level job state remains. Validity is the target's knowledge: `JobTarget-job-changes-since` became `(job-rebase result revision) => (Maybe :pair)`; the library keeps `exact-revision` and `target-alive` and asks the target for `rebase`. `change`, `span`, and `rebase-spans` moved from `kernel/ids.ss` to the buffers contract (`tuna/services/buffers.ss`), whose `text` implements `job-rebase` with `rebase-spans`. The timer tests moved to `tuna/lib/timers-test.ss`, the `rebase-spans` test to `tuna/services/buffers-test.ss`. `boundary-test.ss` also checks `tuna/lib/`: it may hold only `.ss` files, and library source may import only `:gerbil`, `:std`, `:tuna/kernel`, and library modules.
   Its baseline entries (`step 5`) are removed.
6. **Session slots out.** *Done.* `session-slot` and `context-add-session-slot!` moved from the deleted `kernel/slots.ss` to the session contract `tuna/services/session.ss`, dispatching through the new `Session` method `add-session-slot!` (`session-slots` was dropped: only tests used it, and they now observe slots through saved files and restores); the session plugin owns the slot table (`session-store` field `slots`) and registers through `context-add-entry!`, so deactivation still removes a plugin's slots and a same-named lower-priority slot becomes effective. The kernel's `slots` field and `kernel-slots` are gone. Plugins that register slots must require `session-service` and restart with it (not adapt), so their slots move to a new provider: `single-window-plugin` and `two-windows-plugin` (through `context-add-windows-session-slot!`; `autosave-plugin` already did); a configuration without persistence provides a session that saves nothing (tests whose plugins register slots without testing the session import `tuna/plugins/test-session.ss`, now `tuna/test-support/session.ss`). The slot tests moved from `tuna/kernel/plugins-test.ss` to `tuna/plugins/session-test.ss`.
   Its baseline entries (`step 6`) are removed.
7. **Kernel object private.** *Done.* `tuna/kernel.ss` no longer exports `kernel`, `kernel?`, `new-kernel`, or `current-kernel`, and lists its 79 exports one by one under the four ADR 12 items (it had 179, most re-exported wholesale). `submit-input!` became `input-submitter`, which returns a procedure bound to the current kernel; the web plugin captures one at activation (before the loop starts) and calls it from request threads, which no longer select a kernel (ADR 12 amended). Dead exports were deleted: the revision counter (`revision-counter`, `new-revision-counter`, `revision-bump!`; `kernel/ids.ss` keeps only `next-id!`), `active-plugin-names` (and its definition), `hook`, `hook?`, `hook-name`, `hook-doc`, `hook-callback-names`, the `service` accessors other than `service-name`, `make-service`, `StartupServiceError`, `startup-service-error?`, the other `plugin`/`entry`/`service-info` constructors, predicates, and setters, `entry-priority`, `entry-table?`, `context?`, `context-plugin-name`, `task?`, `suspension?`, `quit-condition-forced?`, `call-with-inhibit-quit`, and the generated `Input`/`Display`/`Messages` companions other than `Input-arrival` and `Input-resolve!`. Kept because lifecycle hooks pass plugins and services: `plugin`, `plugin-name`, `plugin-doc`, `plugin-source`, `service`, and `service-name`; `describe-services` keeps `service-info-doc` for the help plugin. Kernel tests import the internal names they check from the kernel modules directly. Entry tables use name/names: `entry-table-keys` became `entry-table-names`, and `context-add-entry!`'s parameter is `name`.
   Test support lives in `tuna/test-support/` (modules, outside `build.ss`, so the package never compiles them; tests import them by relative path, such as `"../test-support/kernel"`): `kernel.ss` (the test-only kernel facade: `call-with-fresh-kernel plugins thunk`, which selects a fresh kernel, activates the plugins, and in `finally` stops the loop and deactivates every plugin; and `wait-until`), `string-input.ss` (from `kernel/test-fixtures.ss`: `test-input-plugin`, `test-bindings`, `make-test-input`, `current-message`), `keys.ss` (from `plugins/test-keys.ss`: `press`, `type!`), and `session.ss` (from `plugins/test-session.ss`: `no-session-plugin`). `with-buffers`, `with-keys`, both `with-editor`s, `with-settings-plugins`, `with-renderers`, `with-windows`, `with-demo`, `with-editing`, `call-with-test-kernel`, and `call-with-editor` are gone; their call sites call `call-with-fresh-kernel` with a named plugin list. Wrappers that also reset test state or boot in a particular order (`with-loop`, `with-jobs`, `with-minibuffer`, `with-tuna`, `run-tuna`, `with-session-only`) now build on it. `boundary-test.ss` checks that no non-test file under `tuna/` imports or includes test support, that `build.ss` lists none of it, and that outside `tuna/kernel/` and test support no file, tests included, imports a kernel module other than the facade `:tuna/kernel`; it reads `#lang` preludes as Gerbil does, and no longer excludes any kernel file. Its baseline entries (`step 7`) are removed.
8. **Failure reporting and consumed-seam wording.** *Done.* No failure hook was added (it would be a new kernel export, and nothing consumes it); the `Messages` seam stays the only consumed UI-ish service, and nothing was added to it or to `Display`. Failures that `message` reports (failing hook callbacks, tasks, input resolution) go to the `Messages` provider, or to stderr while there is none. Plugin and service failures (`report-failure!`, `hand-over!`) go through the private `report-failure-message!`: to stderr always, exactly once and first, then to the `Messages` provider when there is one. A failing redisplay goes to stderr only. The `Display` seam is reworded (`redisplay!` "brings what the user sees up to date"; the service doc is "Shows the current editor state to the user"), the `Messages` method parameter is `message` and `message`'s is `string`, and the kernel no longer mentions the echo area. No public name changed.
   Fixed the two reporting bugs from step 4's review: (a) `(displayln text (current-error-port))` wrote the text and the port object to stdout (`displayln` takes rest arguments); the sites in `kernel/plugins.ss`, `kernel/loop.ss`, and `tuna/main.ss` now write to stderr. (b) `run-hook` treated a quit as a callback failure; inside a task a quit now propagates and unwinds the task, and the callback stays registered. Outside a task (the loop thread, startup, shutdown) nothing can unwind, so a quit there still counts as a failure. The review then found that the other kernel catchers (`run-receipt!`, `activate-wanted!`/`settle!`, `hand-over!`, `reconcile-adapters!`, and the lifecycle announcement loop) also swallowed quits, and that a quit escaping one announcement dropped the operation's later events. So a plugin operation (`call-as-plugin-operation`: the outermost activate, deactivate, or deactivate-all) is now atomic with respect to quitting: it runs with quit inhibited, so one or two interrupts wait for its end, while a third overrides as everywhere; each catcher first calls the private `hold-quit!`, which holds a quit in the operation's box (`held-quit`) and lets the step count as done, without a report or a removed callback (a plugin whose own activation quit is rolled back and turned off, unreported); after every event has been announced, the held quit is raised in a task and dropped outside one. A forced quit keeps its flag, so the loop still reports "Quit (forced: ...)". Because plugin operations need the task's quit checks, the task class, `current-task`, `quit-condition`, `check-quit`, `signal-quit`, and `call-with-inhibit-quit`/`with-inhibit-quit` moved from `kernel/loop.ss` to a new `kernel/tasks.ss`, which both `kernel/plugins.ss` and `kernel/loop.ss` import; the facade exports nothing new. The session plugin's `report!` now writes stderr once and calls `message` only when a provider exists.
   Its baseline entries (`step 8`) are removed; only the three permanent entries remain, and `baseline-steps` is empty, so every entry must give a `permanent:` reason.
9. **Update docs:** ADR 2/3/8 references where names moved; `docs/overview.md` and `docs/diagrams/kernel-layers.svg` status to built, and `kernel-layers.d2` gains a contracts -> libraries arrow (the buffers contract uses the jobs library); `docs/emacs-equivalents.md` if any concept changed.
