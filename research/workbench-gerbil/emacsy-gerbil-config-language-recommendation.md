# Emacsy Gerbil configuration language recommendation

## Decision

Adopt an explicit Gerbil configuration language:

```scheme
#lang :workbench/config

(defun workbench-greeting (who)
  (string-append "configured " who))

(setq workbench-site-name "configured-site")
```

Use:

- a custom prelude selected by `#lang`;
- Emacs-shaped, kind-specific forms: `defun`/`fset` for function cells and `setq` for value cells;
- one flat public naming layer with conventional package prefixes;
- runtime lookup by `(kind, public-name)`;
- `%%begin-module` to lower the whole file into one registry transaction;
- an `extern`-bound executable-owned dispatcher, not a runtime import of the stateful registry;
- `import-module canonical-path #t #t` for repeatable source reloads.

Do **not** preserve FPO at the cost of qualified runtime calls, raw Gambit semantics, or compiled-only user configuration. Normal and `-O` custom-prelude behavior are verified; the proposed exact `#lang` design still needs its MWE, while related runtime-expander fixtures already fail under FPO with `Unbound variable: __eval-import`. Treat FPO as unsupported for this feature unless that MWE later proves otherwise.

## Recommended surfaces

### Library author

Keep ordinary Gerbil identifiers in application code while explicitly declaring stable public customization names:

```scheme
(defcustom-function (greeting who)
  public: workbench-greeting
  (string-append "default " who))

(defcustom-value site-name
  public: workbench-site-name
  "default-site")

(def (describe who)
  (list site-name (greeting who)))
```

The explicit public name is worthwhile: it remains stable if the Gerbil module or internal identifier moves. A package may offer an inference convention, but the declared public symbol is the API.

### User

```scheme
#lang :workbench/config

(defun workbench-greeting (who)
  (string-append "configured " who))

(setq workbench-site-name "configured-site")
```

Expression-oriented function replacement uses `fset`:

```scheme
(fset workbench-greeting replacement-procedure)
```

A procedure-valued **value** remains unambiguous:

```scheme
(setq workbench-transform
  (lambda (value) (string-append "value:" value)))
```

`setq` always addresses the value domain even when its result is a procedure. `defun` and `fset` always address the function domain.

### Application code

Application code remains ordinary Gerbil:

```scheme
(greeting "Ada")
site-name
(describe "Ada")
```

No application call is qualified through the customization runtime. The indirection remains inside the declarations generated by `defcustom-function` and `defcustom-value`.

## Naming and collision rules

Registry identity should change from one symbol key to:

```text
(function, public-name)
(value, public-name)
```

Rules:

1. Public names occupy one flat, shared API namespace and use package prefixes such as `workbench-greeting`.
2. A duplicate declaration of the same `(kind, name)` is a startup error citing both declaration locations.
3. The same public symbol may have both function and value cells, matching Lisp-2 configuration semantics.
4. `defun`/`fset` choose the function cell; `setq` chooses the value cell.
5. Unknown names fail immediately; they never create config-local definitions or pending overrides.
6. Do not resolve “currently unique” unprefixed leaf names. Adding another library could silently make an existing config ambiguous.
7. Gerbil library source remains Lisp-1. If both public cells share a name, they may map from distinct internal Gerbil identifiers. Splitting the external registry does not itself create source-language Lisp-2 behavior.

The current registry cannot yet represent cross-kind coexistence because it rejects a duplicate symbol before considering kind (`playground/runtime.ss:17-21`). This is a semantic gap, not a reason to weaken the user surface.

## Lowering to the current architecture

The current stable-cell design should remain the substrate:

- function declarations create boxed implementations and stable forwarders (`playground/runtime.ss:53-63`);
- value declarations create boxed values exposed through identifier macros (`playground/runtime.ss:65-77`);
- ordinary same-library reads and calls use those seams (`playground/lib.ss:13-14`);
- current replacement operations already enforce unknown-name, kind, and procedure checks (`playground/runtime.ss:31-48`).

The language should lower top-level forms approximately as follows:

```scheme
(defun workbench-greeting (who) body ...)
=>
(config-entry
  'function
  'workbench-greeting
  (lambda (who) body ...)
  source-location
  '(who))

(fset workbench-greeting expression)
=>
(config-entry
  'function
  'workbench-greeting
  expression
  source-location
  #f)

(setq workbench-site-name expression)
=>
(config-entry
  'value
  'workbench-site-name
  expression
  source-location
  #f)
```

`%%begin-module` should aggregate entries into one call to an executable-owned transaction dispatcher. This avoids globally replacing nested Gerbil `def` and permits whole-file duplicate and rollback checks. Gerbil supports this hook and whole-body transformation (`research/gerbil-custom-language-config.md:64-105`).

The generated call should reach the already initialized registry through hygienically captured `extern` bindings. A prototype that imported the registry module during runtime expansion recreated registry state; using `extern` avoided that reset and passed `gxi`, normal compilation, and `-O` (`research/gerbil-config-import-injection-options.md:132-156`).

## Runtime reload contract

The executable should initialize the expander once and reload the canonicalized config path as a module:

```scheme
(gerbil-load-expander!)
(import-module canonical-config-path #t #t)
```

Here:

- the first `#t` bypasses the cached module context;
- the second evaluates the newly expanded module;
- loading the same edited path repeatedly therefore re-expands and reapplies it.

Evidence: `research/gerbil-custom-language-config.md:310-354`.

Recommended successful-load semantics are Emacs-like overwrite semantics:

- declarations in the new load replace the named cells;
- loading the same definitions repeatedly is idempotent;
- a form removed from the file does not automatically reset its prior cell.

Unlike literal Emacs loading, cell updates should be staged and committed only after all names, kinds, and replacement values validate. Failure preserves the previous cell state. Arbitrary side effects performed while evaluating expressions cannot generally be rolled back, so configuration remains trusted code.

The current playground proves two loads in one process but uses two paths, not one edited path (`playground/main.ss:17-24`). The proposed MWE must exercise `v1 → v2 → v1` through the same canonical path.

## Why `defun`/`setq`, not overloaded `def`

An overloaded Gerbil-shaped `def` looks concise:

```scheme
(def (workbench-greeting who) ...)
(def workbench-site-name "configured")
```

It is nevertheless the wrong primary surface:

- native Gerbil `def` defines or rebinds; it does not mean “replace an existing registered customization” (`research/emacsy-config-surface-options.md:79-98`);
- a value containing a procedure is ambiguous with function replacement;
- replacing a function from a procedure expression needs another operation;
- one overloaded form cannot select same-named function and value cells cleanly.

A configuration-language `def` could be made safe, but only by adding typed companions and explaining that it is not Gerbil’s `def`. `defun`/`setq` communicates the Lisp-2 operation directly and best matches actual Emacs ergonomics.

Module-scoped forms such as:

```scheme
(in-customization playground/lib
  (defun greeting (who) ...)
  (setq site-name "configured"))
```

mainly compress qualification. They bind user configuration to internal module organization and do not provide Emacs’s stable, flat public symbol layer (`research/emacsy-config-surface-options.md:272-302`). They should not be the primary interface.

## Realistic designs

### 1. Explicit `#lang` source configuration — recommended

```scheme
#lang :workbench/config

(defun workbench-greeting (who)
  (string-append "configured " who))

(setq workbench-site-name "configured-site")
```

**Strengths**

- Explicit and self-describing.
- No imports or target-library knowledge.
- Full ordinary Gerbil expressions inside replacements.
- Supports typed operations, source locations, whole-file validation, and transactions.
- Uses an officially supported Gerbil language extension point.
- A custom reader is not required on the researched Gerbil 18.2 implementation (`research/gerbil-custom-language-config.md:183-196`).

**Constraints**

- `#lang` must be at the first byte (`research/gerbil-custom-language-config.md:132-158`).
- Runtime deployment needs the expander plus language `.ssi` and phase artifacts.
- FPO is not currently supportable with confidence.

### 2. Implicit prelude in an application-owned config directory — acceptable secondary mode

`~/.config/workbench/gerbil.pkg`:

```scheme
(prelude: :workbench/config)
```

`~/.config/workbench/config.ss`:

```scheme
(defun workbench-greeting (who)
  (string-append "configured " who))

(setq workbench-site-name "configured-site")
```

This can expose the same language with no header and still use `import-module path #t #t`. It is reasonable only when Workbench fully owns the directory and its `gerbil.pkg`. Prelude inheritance is otherwise ambient filesystem behavior, so moving or copying the config can silently change its language. Explicit `#lang` is more predictable (`research/gerbil-custom-language-config.md:198-218`).

Loader-injected imports are an inferior ambient variant:

```scheme
(eval `(begin
         (import :workbench/config-facade)
         (include ,config-path)))
```

They passed `gxi`, normal, and `-O`, including repeated reloads, but failed under FPO and can re-evaluate stateful imported modules (`research/gerbil-config-import-injection-options.md:3-30,109-156`). They also hide the file’s language at the loader boundary. Do not choose them over `#lang`.

### 3. Ahead-of-time compiled config plugin — deployment fallback

Source can retain the recommended syntax:

```scheme
#lang :workbench/config

(defun workbench-greeting (who)
  (string-append "configured " who))

(setq workbench-site-name "configured-site")
```

It is compiled before the application loads it.

**Use only when** distributing the runtime expander is unacceptable and a compiler/build step is acceptable.

**Costs**

- It is not an edit-and-reload source configuration experience.
- Loading the same module object is cached and does not rerun it.
- Reload requires a newly versioned object.
- Default FPO still failed; it worked only after broadly disabling dead-definition elimination, substantially undermining FPO’s purpose.

Evidence: `research/gerbil-config-import-injection-options.md:331-358`.

## Rejected mechanisms

| Mechanism | Decision |
|---|---|
| Current qualified Gambit calls | Keep only as an internal/diagnostic low-level API. They pass FPO but fail the owner’s ergonomic requirement. Current spelling is visible at `playground/config.scm:1-8`. |
| Loader-injected imports | Technically viable but inferior to an explicit language: ambient semantics, registry reinitialization risk, and the same FPO failure. |
| `gerbil.pkg` implicit prelude | Offer only for a Workbench-owned directory; do not make it the canonical format. |
| Raw Gambit wrapper | Reject. It passed compiled normal, `-O`, FPO, and reload, but failed under `gxi`, creating two language modes (`research/gerbil-config-import-injection-options.md:234-273`). |
| Direct imported-global `set!` | Reject. It bypasses the cell API, conflicts with value identifier macros, and forces provider modules into Gambit’s `separate` optimization contract. |
| Compiled plugins | Retain as an operational fallback, not the primary user experience. |

## FPO decision

**Sacrifice FPO rather than force bad configuration UX.**

Verified facts:

- The current qualified plain-`load` playground passed `gxi`, normal, `-O`, and FPO (`research/gerbil-config-import-injection-options.md:43-60`).
- Custom-prelude prototypes using `extern` passed `gxi`, normal, `-O`, and repeated `v1 → v2 → v1` (`research/gerbil-config-import-injection-options.md:275-310`).
- Runtime-expander fixtures failed under FPO with `Unbound variable: __eval-import` (`research/gerbil-config-import-injection-options.md:109-130`).
- The exact proposed `#lang` plus `%%begin-module` transaction has not received an end-to-end executable matrix. FPO also risks dynamically loading a second registry module (`research/gerbil-custom-language-config.md:424-443`).

Therefore:

- normal and `-O` are the supported target for the proposed MWE;
- FPO should be a characterization test, not an acceptance requirement;
- FPO support may be restored only after proving expander retention, singleton registry identity, and visibility through statically compiled accessors;
- broadly disabling dead-definition elimination merely to claim FPO is not a compelling result.

## Minimal MWE required before implementation approval

The MWE should contain:

1. a `:workbench/config` language prelude;
2. an executable-owned typed registry and transaction dispatcher;
3. one library with an ordinary customizable function and value;
4. one same-named function/value public pair;
5. one procedure-valued value;
6. one config path rewritten and reloaded `v1 → v2 → v1`.

It must prove:

- `#lang` requires no user imports;
- ordinary same-library and cross-library calls/reads observe updates;
- a captured stable function remains live while a captured value remains stale, matching the current playground;
- `defun`, `fset`, and `setq` select the correct kind;
- a procedure-valued value does not affect a same-named function;
- duplicate same-kind declarations, unknown names, wrong-kind operations, and non-procedure `fset` fail with config path/line;
- a failed multi-entry load changes no cells;
- `import-module path #t #t` reloads the same path;
- runtime loading does not replace or reinitialize the registry object;
- required language phase artifacts are explicitly identified;
- normal and `-O` executables pass;
- FPO either passes all singleton/visibility assertions or fails as a documented unsupported mode.

### Focused validation

Given fixtures beneath `/tmp/wb-config`:

```sh
set -eu
gxc -O -d /tmp/wb-config/lib \
  /tmp/wb-config/customization-runtime.ss \
  /tmp/wb-config/config-lang.ss \
  /tmp/wb-config/library.ss

GERBIL_PATH=/tmp/wb-config \
gxi -e '(begin
          (import :gerbil/expander :workbench/mwe)
          (run-reload-mwe! "/tmp/wb-config/config.ss"))'
```

`run-reload-mwe!` should perform the same-path `v1 → v2 → v1` sequence and all Lisp-2/procedure-valued-value assertions.

### Executable matrix

```sh
set -eu

gxc -exe -o /tmp/wb-config/main-normal /tmp/wb-config/main.ss
/tmp/wb-config/main-normal /tmp/wb-config/config.ss

gxc -O -exe -o /tmp/wb-config/main-O /tmp/wb-config/main.ss
/tmp/wb-config/main-O /tmp/wb-config/config.ss

# Characterization only until proven:
gxc -O -full-program-optimization -exe \
  -o /tmp/wb-config/main-fpo /tmp/wb-config/main.ss
/tmp/wb-config/main-fpo /tmp/wb-config/config.ss
```

For FPO, additionally assert registry object identity before and after loading, preservation of pre-registered cells, and visibility through statically compiled ordinary accessors. These commands follow the authoritative matrix in `research/gerbil-custom-language-config.md:478-519`.

## Review findings

- **High — FPO:** runtime Gerbil expansion fails under FPO on the researched toolchain; the exact proposed language MWE is still absent.
- **High — singleton registry:** runtime imports can reconstruct and evaluate stateful modules. The language must call an executable-owned dispatcher through `extern`, not import the registry.
- **High — trusted code:** re-exporting ordinary Gerbil expressions makes configuration trusted code, not a sandbox.
- **Medium — Lisp-2 gap:** the current one-key registry prevents same-name cross-kind coexistence.
- **Medium — transaction limits:** cell changes can be atomic, but arbitrary expression side effects cannot be rolled back.
- **Medium — diagnostics:** current errors lack config and declaration provenance (`playground/runtime.ss:13-48`).
- **Medium — deployment:** language phase artifacts must accompany normal and optimized executables.
- **Medium — version compatibility:** the current expander supplies a default reader, while older tutorial wording suggests otherwise; verify the production Gerbil release.
- **Low — module identity:** canonicalize paths before `import-module` reload.

## Residual risks and confidence

- Advice, reset, source-layer removal, concurrency, and arbitrary procedure arity introspection remain outside this recommendation.
- Whether removed forms remain active or are reset should stay explicit; this recommendation chooses Emacs-like persistence with atomic successful cell commit.
- Same-name Lisp-2 behavior is guaranteed at the public registry surface, not automatically inside Gerbil’s Lisp-1 source namespace.
- Confidence is **high** in the surface and naming recommendation, current-cell lowering, and normal/`-O` feasibility; **medium** in exact `#lang` deployment until the MWE runs; **low** in FPO support.
