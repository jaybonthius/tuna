# Plan: user configuration

Owner-approved brief: [`docs/briefs/2026-10-configuration.md`](../../docs/briefs/2026-10-configuration.md) (decided 2026-10-12). Evidence: [`agents/research/configuration/`](../research/configuration/). Owner rules: no standard setup, no magic (Tuna never creates or edits the user's config on its own), no stored history, kernel unchanged.

## Invariants (every stage)

- **Loading `init.ss` has no effect on the running editor.** Loading only produces a value: the declared plugins (with options and `config:` blocks) plus the user's own code as one more plugin. Every effect happens when those plugins are turned on, so receipts undo it. This is what makes the "trial run" a load, not a staging kernel. Prefer a configuration language (`#lang :tuna/config` or a macro) whose body becomes plugin activation code; a staging kernel instance needs a new kernel export and is the fallback, justified in an ADR 12 amendment only if the first approach cannot work.
- **Each load of `init.ss` gets a fresh module namespace in memory** (research 01, finding 8), so the version currently running stays loaded and can be turned back on. Nothing is written to disk except the start-up report log.
- **Loading runs on a worker thread with a timeout** and is always a reload (`import-module path #t #t`), so an endless loop or a failed load never leaves a stuck module (research 01, findings 6-7).
- **Failure isolation:** a plugin, or a `config:` block, that fails to turn on is undone and recorded; plugins that need it are recorded as skipped; everything else proceeds.
- **Placement:** finding and reading the file, boot activation, and reload live in program code (`tuna/boot.ss`, `tuna/main.ss`, outside the kernel); the `reload-config` command lives in an ordinary configuration plugin. `tuna reload` and `tuna check` are program code too (`tuna/control.ss`, `tuna/main.ss`): they must work without any plugin, for example when the user's input plugin is broken. The `reload-config` plugin's import of `:tuna/boot` was a recorded exception (ADR 12 amendment, checked by the boundary test) until stage 3 added the configuration contract; it is gone. Any kernel export added or restored (for example a plugin's `requires` for the "skipped: needs X" report) is justified in the merge report; no new kernel feature.
- `make test` stays green with the boundary checks unchanged; each stage is checked in a real browser in an isolated run.

## Stages

1. **Start from `init.ss`.** Link the Gerbil expander into the `tuna` executable. `main` finds the config (`--config PATH`, then `TUNA_CONFIG`, then `$XDG_CONFIG_HOME/tuna/init.ss`); with none, it turns nothing on, says how to get one, and keeps running. `use-plugin` (no options yet) plus `config:` blocks plus top-level user code, per the invariants. Boot activates declared plugins with isolation, then the user-code plugin. Start-up report to stderr and to a log file in the state directory replaced each start. A starter `init.ss` in the repository reproducing today's hard-coded set; `tuna init` copies it to the default path only when run (refuses to overwrite). Delete the hard-coded list. `tuna check` (load + validate without turning anything on) if cheap here, else stage 2.
   **Done 2026-10-12** (branch `config-stage1`). The language is `#lang :tuna/config` (`tuna/config.ss`): `import` and `use-plugin` forms run at load and only collect declarations (`tuna/lib/configuration.ss`); every other top-level form becomes the body of the plugin `init`; `(use-plugin p config: body ...)` makes `body` its own plugin `p/config`, kept on while `p` is on by the `config-blocks` plugin (`tuna/plugins/config-blocks.ss`, since moved to `tuna/config-blocks.ss` beside the start-up code; during start-up, boot brings blocks in line after each activation). `use-plugin` takes only a name, the generated plugins declare `requires: []`, and a file whose first line is not `#lang :tuna/config` is not run; imported modules' bodies and macro code still run at load and are documented as such. The language defines no module-level names, so each load yields fresh plugin values; loading is `import-module path #t #t` on a worker thread with a 10 s limit. Start-up (`tuna/boot.ss`, called from `tuna/main.ss`): discovery, load, then each declared plugin as soon as its services are provided (5 s limit each; a hung activation is interrupted once so its receipt rolls back, and is never terminated: if it ignores the stop, start-up says so on stderr and waits; each report line's status is what the kernel says at the end), its block after it, the user code last; the report goes to stderr and `$XDG_STATE_HOME/tuna/startup.log`. `tuna init` and `tuna check` (load and validate only) are built. Kernel change: the facade exports `plugin-requires` (ADR 12 amendment). Start-up from the starter takes about 0.8 s instead of 20 ms: the expander loads in about 85 ms, the rest is reading the imported modules' compiled metadata (`.ssi`), about 0.4 s of it for the web plugin.
2. **Reload.** `reload-config` command in a configuration plugin and `tuna reload` from a terminal (a control channel; pick the simplest robust mechanism: signal or local socket, justified). Reload = load new version (trial), diff declarations against what is running, turn off/on only the differences; a failed new plugin or block is undone and the running version turned back on; the user-code plugin likewise. Changing a startup-tier provider is reported as "takes effect at next start". `tuna check` if not done in stage 1.
   **Done 2026-10-13** (branch `config-stage2`). One procedure, `apply-configuration!` in `tuna/boot.ss`, serves start-up and reload: it compares the new load with the running configuration (`running-configuration`, kept in memory) by plugin name. Not declared any more: off. New: on. Another plugin object (its module was read again): replaced. Same object but off (failed or skipped before): turned on again. A `config:` block or the user's code is replaced when its code as written (quoted by the language) differs, or when any user module was read again; otherwise left alone. Replacing turns the running unit off and the new one on; if the new one fails it is undone and the running one, still in memory, is turned back on. While the editor loop runs, removing or replacing a provider of a startup-tier service is reported `deferred` ("takes effect at next start") without touching it, and a plugin the kernel refuses for taking over such a service is rolled back and reported `deferred`; filling an empty startup-tier slot is allowed because the kernel allows it. User modules: before each load, every source module the expander loaded whose file text changed, and every source module importing one, is dropped from the expander's registry, so it is read again and its plugins become new values; Tuna's compiled modules are never reloaded. Activations now run on the calling thread (the reload task holds the baton) with a watchdog thread that interrupts once and never terminates. The report has the start-up report's format plus `replaced`, `deferred`, and an `unchanged` count; it goes to the requester only. `reload-config` is a command of `reload-config-plugin` (`tuna/plugins/reload-config.ss`), declared and bound to `C-c R` in the starter. `tuna reload` (`tuna/control.ss`, program code beside boot, no plugin needed): each Tuna listens on `$XDG_RUNTIME_DIR/tuna/<pid>.sock` (directory mode 700; falls back to `$XDG_STATE_HOME/tuna/control/`); `tuna reload` asks every listening Tuna, prints each report, exits 0 only if all succeeded, and deletes socket files nothing listens on. When the editor loop is not running, `main` reloads on its own thread and starts the loop once input is provided (walkthrough step 4). Kernel unchanged, no new export. Tests: `tuna/reload-test.ss`. Review fixes (2026-10-13): the session plugin restores the slots of a plugin a reload turns on and keeps a removed slot's latest data for its replacement; a turn-off the kernel refuses (something a startup-tier provider needs) is reported `deferred` and the old version, block, or code kept; `init.ss` is recognized by its normalized path; dependents the kernel restarted are listed `restarted`; a C-g during a reload still delivers the report; the control directory must be the user's with mode 700, sockets have mode 600, and `tuna reload` waits at most 30 s per Tuna. One limit is documented and pinned by a test: a changed user module imported by path is loaded again in place, so its definitions replace the running version's as soon as it loads, even if the reload then fails (giving each load its own namespace would need copies on disk or expander internals).
3. **Options and the report inside Tuna.** `use-plugin` options validated against a schema each plugin declares (all problems collected with their lines, research 02 rec. 7), passed to the plugin at activation. Show the start-up/reload report inside Tuna when something can display messages, plus a command to show it again.
   **Done 2026-10-13** (branch `config-stage3`). A plugin module declares its options after the plugin with `(defplugin-options PLUGIN (name default "doc" type) ...)` and reads them while it is turned on with `(plugin-option PLUGIN 'name)` (`tuna/lib/plugin-options.ss`); types are `string-type`, `boolean-type`, `symbol-type`, and `(integer-type low high)`, a description plus a predicate. Options are not settings: settings are resolved by a service that start-up-tier plugins come before, and an option belongs to one declaration; the declaration shape (name, default, doc, type) follows ADR 9 so settings can take the same types when they get schemas. `(use-plugin p key: value ... config: ...)` values are data, never evaluated (`leader: SPC` is the symbol `SPC`; `'x` is `x`). Loading checks each option (unknown, wrong type, given twice) and fails with every problem, one line each, starting with the option's own line (`init.ss line 6: modal option leader must be a string`); a failed load changes nothing, and `tuna check` reports the same. Start-up and reload install a declaration's options just before turning its plugin on (a kernel restart reads the same values); a changed option makes the same plugin object `replace` (off, new options, on; on failure the old options and the running version come back). The web transport's `port` option (default 0, any free port) is in the starter; `tuna --port N` (now also 0) overrides it. The configuration contract `tuna/services/configuration.ss` (reload, last report) is provided by the start-up code's own `config-service` plugin (`tuna/boot.ss`), turned on before the declared plugins; `reload-config-plugin` now needs it and adds `show-config-report` (bound to `C-c C-r` in the starter), which shows the last start-up or reload report in the echo area, as the reload report already is. After start-up, `main` puts a one-line summary of failed and skipped units, naming `show-config-report`, in the echo area when a plugin provides messages. The boundary test has no exception. Kernel unchanged, no new export. Tests: `tuna/options-test.ss`. Review fixes (2026-10-13): options are compared by their values (given or default), so reordering or writing out a default touches nothing; a `config:` block re-run only because its plugin was replaced is `restarted`; `tuna --port` is a program override of the option (`override-plugin-option!`), noted in the report, and a change to an overridden option is reported instead of applied; declaration problems (declared twice, not a plugin, reserved name) are collected with option problems; a keyword at the top level of a `config:` body is a syntax error; the start-up summary lists every status but on and restarted, names the log, and names `show-config-report` only when that command exists; the option tables have weak keys; ADR 9 records options versus settings.

Later, each with its own plan: bisect (in memory), reloading plugin code itself, package installation. The STATUS item "demo out of default startup" becomes a one-line choice in the starter `init.ss`.
