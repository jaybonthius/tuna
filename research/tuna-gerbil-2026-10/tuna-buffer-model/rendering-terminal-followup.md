# Research: non-editable terminal-style browser input

## Summary
There is no browser primitive that turns a genuinely non-editable, non-input element into a full text editor merely by listening to `keydown`. `keydown` can transport ordinary key identities and shortcuts, but is not a reliable source of entered text, particularly for IME, dead keys, mobile keyboards, or composed Unicode. For Tuna’s strict constraints, a first milestone can support key-command transport plus explicit plain-text clipboard commands, but must state that printable text/IME composition are not yet supported as general text entry. `EditContext` is the closest platform primitive for composing text on a non-contenteditable rendered surface, but it makes the host an editing host, is a Working Draft with constrained implementation availability, and entails browser-side transient text/selection state—not an immediately server-round-tripped keystroke model.

## Findings

1. **Current implementation transports commands, not text.** `/home/jay/Code/workbench-gerbil/tuna/frontend/tuna-keyboard.ts` captures keydown fields (`key`, `code`, modifiers, repeat, composition flag), prevents default for non-composing keys, and POSTs one event at a time to `/commands`. `/home/jay/Code/workbench-gerbil/tuna/tuna/input.ss` validates that event shape and currently maps unmodified Enter to `hello`; neither commits text. `KeyboardEvent.key` is a layout/modifier-sensitive key value, not an input transaction; MDN documents text entry’s normal `keydown` → `beforeinput` → `input` sequence. Preventing default keydown suppresses that normal browser editing path. **Source-backed:** those file paths/current code; [MDN KeyboardEvent.key](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/key).

2. **Constrained no-input proposal.** Keep a focusable, noneditable semantic editor surface (`tabindex="0"`, accessible name/description, visible focus) with server-rendered content. The existing keydown transport can route navigation/commands, and server state/rendering remains authoritative. Add explicit copy/cut/paste event transports: for copy/cut, selected content comes from server selection and browser clipboard write occurs synchronously inside the user-gesture event handler (`ClipboardEvent.clipboardData.setData`); cut sends a server delete command only after successful/accepted clipboard handling. For paste, synchronously read `event.clipboardData` as plain text in the gesture handler and send that payload to the server. Avoid relying on asynchronous `navigator.clipboard.readText()` due to secure-context/permission/user-activation variation. Pointer selection commands can be derived from click/drag coordinates against rendered line/character geometry, but require explicit hit-testing and server position mapping; they are not provided by a noneditable element’s native text selection. The literal shared-state requirement means every tab displays the same server selection/cursor too; pointer or key actions from any tab update that shared selection globally, which can cause apparent cursor movement in other tabs. **Recommendation/inference:** this is feasible for commands and clipboard but is a specialized terminal protocol, not ordinary browser editing.

3. **EditContext is a genuine alternative, not a magical event listener.** The platform exposes `HTMLElement.editContext`, allowing EditContext attachment to supported non-contenteditable elements and turning the host into an editing host. Its `textupdate`, selection and composition facilities address OS text services, but the user agent maintains a transient text/selection/composition interaction in order to communicate with IME. Thus it conflicts with a strict interpretation of “each key goes to server and committed state/rendering stay server-side” unless transient composition state is explicitly accepted and reconciled. Do not attach it to an element documented as unsupported; MDN says unsupported element types can throw `NotSupportedError`. The W3C EditContext specification is a Working Draft; support is not a cross-browser contract. If IME is required before ordinary-browser editing can be deferred, owner must choose an explicit target browser/platform set and permit testing EditContext there; no broad support claim is justified here. **Sources:** [MDN HTMLElement.editContext](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/editContext); [W3C EditContext](https://www.w3.org/TR/edit-context/).

4. **IME constraint / no-go line.** Without an input-capable editing host (input/textarea/contenteditable/EditContext), the browser’s OS text-input/IME pathway has no declared text editing target. Composition events are not synthesized reliably from keydown; `isComposing` only signals composition context and does not deliver committed composed text. Therefore ordinary keys might be sent as commands, but “full Emacs text entry” or general text entry cannot be promised. Under current hard constraints, defer IME and disclose it; if it is a requirement, reconsider EditContext plus a transient composition exception, or relax the no-editing-host constraint. That choice needs browser experiments.

5. **Clipboard and pointer boundary.** Copy/cut/paste events can be handled on the focused noneditable surface when user gestures invoke them; script can access event clipboard data synchronously, subject to browser security rules. Plain text only should cross the server boundary; never send clipboard HTML as trusted content. There is no native text selection/caret in a noneditable rendered buffer, so pointer selection requires app-defined hit-testing and server commands (pixel-to-line/cell-to-code-point mapping); selection overlays remain rendered from shared server state. If server response is delayed, a gesture may feel laggy, but optimistic local selection/text would violate literal shared authoritative state unless explicitly allowed. **Sources:** [MDN paste](https://developer.mozilla.org/en-US/docs/Web/API/Element/paste_event); [MDN copy](https://developer.mozilla.org/en-US/docs/Web/API/Element/copy_event); [MDN Clipboard API](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API).

## Owner-visible trade-offs
- **No-input milestone:** preserves strict server authority and current architecture; supports key commands and possibly plain-text clipboard, but not general printable text entry or IME. Precisely label it command/navigation prototype, not usable text editor.
- **EditContext milestone:** plausible custom-rendered text/IME path without textarea/contenteditable, but introduces a local transient OS input buffer, browser-version constraint, event reconciliation/latency questions, and broader browser testing. It does not mean committed application state moves client-side.
- **Relax constraint:** native editor surface restores mature browser input pathways, but owner explicitly ruled it out; not recommended unless the target platform decision requires it.

## Browser test matrix (future; no experiments run)
On each owner-selected browser + OS: ordinary printable key, modifiers/repeat, dead key, Japanese IME composition and commit/cancel; EditContext support/attachment on the exact chosen host; two tabs sharing cursor/selection under alternating key/pointer actions; clipboard copy/cut/paste under keyboard and context menu with plain/rich clipboard sources; clipboard denial/no permission; server latency/disconnect/retry; screen-reader name/focus and visible selection/focus. Verify no lost/duplicate committed text and no divergence between tabs. Record precise browser/OS/version.

## Missing evidence / genuine decision
No browser target policy was supplied. Primary docs establish EditContext API semantics, but this run did not establish an authoritative current per-browser support matrix, and did not run browser experiments. Genuine owner choice: either accept explicit no-IME scope for first milestone, or choose target browsers/platforms and authorize testing an EditContext transient-composition design. The constraint set itself does not permit a responsible claim of full text entry.
